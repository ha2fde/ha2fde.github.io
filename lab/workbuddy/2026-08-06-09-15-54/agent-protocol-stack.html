PART 1 · TOOLS

Tools（Function Calling）：一切的开始

核心事实：LLM 从不执行工具，它只输出一个「调用请求」的 JSON，由宿主程序执行后把结果回填

一个 Tool 的三要素

  • name —— 函数名，模型决策的依据之一
  • description —— 自然语言说明「何时用、怎么用」，写得好坏直接决定调用准确率
  • parameters —— JSON Schema 定义的入参结构

为什么这是范式级突破

把「模型输出文本」变成「模型输出结构化的、可执行的意图」。从这一刻起，聊天机器人变成了可以行动的系统 —— 这正是从 Chat 到 Agent 的那个分水岭。

{
  "name": "get_weather",
  "description": "查询指定城市的实时天气，
    当用户问到天气、温度、
    是否下雨时使用",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string"}
    },
    "required": ["city"]
  }
}

模型看到的不是代码，而是这份 Schema + 描述。所以 Tool 设计本质上是「写给模型看的 API 文档」。

PART 2 · MCP

MCP 不只有 Tools：三种原语 + 两种传输

按「谁来决定使用」区分 —— 这是 MCP 设计的精髓

Tools 模型决定

可执行的函数。模型在循环中自主决定调用。
例：create_issue、run_query
最常用，前几张图讲的都是它

Resources 应用决定

只读数据，类似 GET。由应用/用户挑选后塞进上下文。
例：file:///log.txt、db://schema
不占工具决策，按需挂载

Prompts 用户决定

预置的提示词模板，用户主动触发（类似斜杠命令）。
例：/code-review
Server 可以把「最佳用法」打包分发

传输：stdio（本地）

Host 用 npx/uvx 把 Server 拉起来当子进程，走标准输入输出。零网络配置、进程隔离，本地工具首选。你在 mcp.json 里写 command + args 就是这种。

传输：Streamable HTTP（远程）

Server 部署在远端，走 HTTP + SSE 流式回传，配 OAuth 鉴权。企业级 / 多用户共享服务的标准姿势。

底层消息格式统一为 JSON-RPC 2.0。另有两个进阶能力：Sampling（Server 反向请求 Host 的 LLM 补全）与 Roots（Client 告诉 Server 可访问的目录边界），了解即可。

PART 3 · CLI

CLI：最古老、也最暴力的 ACI

思路反转：不为每个能力写工具，而是给 Agent 一个 bash —— 整个 Unix 生态瞬间都是它的工具

工作方式

  • Agent 只有一个核心工具：run_shell_command(cmd)
  • 模型生成命令 → 执行 → stdout/stderr 纯文本回填 → 模型读懂文本继续
  • 代表：Claude Code、Codex CLI、Aider、Gemini CLI

优势

  • 零适配成本：git、curl、jq、ffmpeg… 装好就能用
  • 组合性：管道让模型自己拼装工作流
  • 模型在训练语料里见过海量 CLI 用法，先验知识极强

代价

  • 输出非结构化：靠模型解析文本，脆弱
  • token 消耗大：一次 ls 也可能几百 token
  • 危险面大：rm、git push 都在射程内 → 权限/沙箱成必备
PART 4 · 共通本质

Tools / MCP / CLI：一张皮的三张脸

三者差异只在「能力在哪里、怎么连」，对模型而言循环完全一致

ToolsMCPCLI
能力在哪应用进程内的函数进程外的标准 Server操作系统的一切命令
连接方式代码直接调用JSON-RPC（stdio / HTTP）fork 子进程，读写管道
Schema 来源开发者手写tools/list 动态发现无显式 Schema，靠模型先验 + --help
结果形态结构化 JSON结构化 JSON / 内容块非结构化文本流
复用范围本应用内跨应用、跨厂商跨一切（OS 级）

共通循环（换皮不换骨）

① 能力声明进上下文 → ② 模型决策并输出结构化意图 → ③ 宿主执行 → ④ 观察结果回填 → ⑤ 回到 ① 直到任务完成

差异只是第 ① 步的声明方式（手写 Schema / tools/list / 模型先验）和第 ③ 步的执行位置（进程内 / 进程间 / 操作系统）。

PART 4 · 共通本质

ACI：Agent-Computer Interface

a16z 提出的概念：正如 HCI 决定人用软件的效率，ACI 决定 Agent 用计算机的效率

工具不是给人用的 API 套个壳，
而是为模型重新设计的接口。

视角转换

传统 API 设计假设调用方是「写代码的工程师」；ACI 假设调用方是「读描述、一次填参、会犯错的模型」。设计标准因此完全不同。

为什么 Skills / MCP 都是 ACI 话题

它们都在优化同一件事：单位 token 内，模型能调用的有效能力密度。上下文窗口就是 ACI 的带宽。

ACI 设计六要点

  • 命名与描述即文档 —— 模型靠它决策，写烂 = 调错
  • Schema 收紧 —— 枚举、范围、互斥约束写进 JSON Schema，别指望模型猜
  • 输出要省 token —— 返回摘要而非原始大对象，支持分页/截断
  • 错误信息可操作 ——「参数 city 不支持拼音，请用英文城市名」而非「400」
  • 幂等与确认 —— 写操作要求确认回路（human-in-the-loop），读操作自由
  • 粒度面向任务 —— 宁可 search_and_summarize，不要 5 个底层 API 让模型自己拼
PART 5 · SKILLS

Skills：不是协议，是「给 Agent 的操作手册」

2025.10 Anthropic 推出 Agent Skills 并开放为标准 —— 本质：把领域知识、流程、脚本打包成文件夹，按需注入上下文

my-skill/                  ← 一个 Skill 就是一个文件夹
├── SKILL.md             ← 唯一必需文件
│   ├─ YAML frontmatter
│   │   name: pdf-report
│   │   description: 生成 PDF 财报，
│   │     当用户要求导出/下载
│   │     报告时使用      ← 触发决策全靠它
│   └─ Markdown 正文
│       （步骤、规范、禁忌、示例）
├── scripts/               ← 可执行脚本（确定性工作交给代码）
│   └── render.py
├── references/            ← 参考文档，按需读入
│   └── style-guide.md
└── assets/                ← 模板、素材（不读入上下文）
    └── template.docx

Skills 教 Agent「怎么做」，Tools 给 Agent「能做什么」

MCP Server 告诉你「能创建工单」；Skill 告诉你「我们团队创建工单的规范流程是…先查重、字段这样填、最后通知值班群」。前者是能力，后者是方法论与组织记忆。

为什么不用超长 System Prompt？

把所有知识常驻上下文 = 浪费 token + 互相干扰。Skills 的思路是渐进式披露：只花 ~100 token 常驻元数据，命中才加载正文，资源文件用到才读 —— 下页详解。

与 MCP 的关系

正交互补：MCP 连能力，Skills 教用法。一个 Skill 里可以写「使用某某 MCP 工具时遵守以下步骤」，也可以自带脚本完全不依赖 MCP。

PART 5 · SKILLS

Skills 的分发渠道 与 编写要点

分发 = 文件夹往哪放；编写 = description 决定生死

分发渠道（由近及远）

  • 个人级：~/.claude/skills、~/.workbuddy/skills —— 跨项目生效，自己的武器库
  • 项目级：<repo>/.claude/skills —— 随 git 仓库走，团队共享规范的首选
  • 插件/市场：插件包内捆绑 skills，一键安装（各家 IDE/CLI 的 marketplace）
  • 开源仓库：anthropics/skills（官方示例集）、社区精选 awesome 列表 —— git clone 即用
  • 企业内部：私有 registry / 内部 Git，沉淀组织流程资产

因为 Skill 只是纯文件，所以天然兼容 git 的一切：版本管理、code review、PR 协作 —— 这是它作为分发格式的隐藏优势。

编写五要点

  • description 是触发器：用第三人称写清「做什么 + 何时触发」，塞入用户可能说的关键词 —— 写差了模型永远不调用
  • 单一职责：一个 Skill 干一件事；「代码审查」和「发布部署」别混
  • 确定性逻辑写成脚本：模型不该做的（排序、格式转换、校验）交给 scripts/，正文里只写「运行 xx.py」
  • 正文具体可执行：步骤化、给正反例、写清禁忌；模糊建议 = 没有建议
  • 控制层级：正文 <500 行，超出拆进 references/，正文里留指针

一个判断标准

把 Skill 给一个聪明但第一天上班的实习生看 —— 他能照做不出错，就是好 Skill。模型就是那个实习生。

PART 5 · SKILLS

Skills 的应用场景 与 未来走向

典型应用场景

  • 文档工厂：docx / pptx / xlsx / pdf 生成（Anthropic 官方四件套），模板与规范全在 Skill 里
  • 团队规范固化：代码审查清单、发布流程、SQL 规范 —— 新人新模型都一致
  • 领域工作流：投研报告、法律文书、病历摘要 —— 行业 know-how 的载体
  • 工具编排：教 Agent「什么时候、按什么顺序」组合多个 MCP 工具
  • 自我进化：Agent 把刚踩过的坑写成新 Skill —— 经验可积累

未来发展（已在发生）

  • 走向开放标准：agentskills.io 发布，OpenAI（Codex）、VS Code Copilot、Cursor 等相继兼容同一格式 —— 一次编写，处处运行
  • 生态市场化：Skill 市场 / registry 出现，像 npm 包一样被发现、评分、安装
  • 与 MCP 融合：MCP Server 分发时自带 Skill 说明「本工具的最佳实践」，能力与方法论一体分发
  • 自动生成与进化：Agent 自动把成功会话提炼成 Skill，组织知识飞轮转动
  • 治理与安全：Skill 可注入指令 → 供应链审计、签名、权限分级会成为刚需

判断：MCP 标准化了「能力」，Skills 正在标准化「经验」。后者离业务价值更近，可能是企业侧更快落地的一个。

PART 6 · A2A

A2A：Agent 与 Agent 之间的协议

2025.4 Google 发布，后捐给 Linux Foundation —— 回答的问题变了：不是我的 Agent 怎么用工具，而是我的 Agent 怎么委托别的 Agent 干活

为什么需要它

  • 现实系统由多家厂商、多个团队的 Agent 组成：订票 Agent、报销 Agent、法务 Agent…
  • 它们不可能共享同一个 LLM 循环和上下文 —— 需要跨组织边界的协作语言
  • 把对方 Agent 包成 MCP Tool 理论上可行，但丢失了多轮协商、长任务状态、产物交付的表达能力

与 MCP 的定位差异（关键！）

  • MCP：纵向 —— Agent → 工具/资源（我调你，你是能力）
  • A2A：横向 —— Agent ↔ Agent（我委托你，你是同事）
  • 两者互补：一个 A2A 远程 Agent 内部照样用 MCP 连自己的工具

核心设计：不透明（Opaque）

远程 Agent 是黑盒 —— 不暴露内部 prompt、工具、记忆。双方只交换「任务、消息、产物」，像两个公司之间走合同而不是共用大脑。

放回大图：一次真实任务的完整链路

TAKEAWAYS

六句话带走

1. LLM 从不执行，只输出意图 —— Tools 循环（声明→决策→执行→回填）是一切协议的母循环。

2. MCP = 把工具挪到进程外并标准化：Host / Client / Server / 原始服务四实体，tools/list 发现、tools/call 调用、JSON-RPC 传输。

3. CLI 是野路子 ACI：一个 bash 换整个 OS 生态，代价是非结构化输出与安全面。

4. ACI 是统一视角：为「会犯错的模型」设计接口 —— 描述即文档、输出省 token、错误可操作。

5. Skills 不是协议是资产：SKILL.md + 渐进式披露，标准化的是「经验」，description 决定生死。

6. A2A 管横向协作：Agent Card 发现、有状态 Task、Message 协商、Artifact 交付，远程 Agent 是不透明黑盒。
