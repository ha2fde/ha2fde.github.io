Recap · 衔接

回顾：Transformer 给我们的唯一接口

你已经懂 Transformer —— 但请记住一个事实：它只会做一件事

唯一的接口：下一个 token 的概率分布

输入一段 token 序列，Transformer 对词表中每个词输出一个 logits，经 softmax 得到概率分布：

P(xt | x1, x2, …, xt-1) = softmax(W · ht-1)

所谓"生成"，就是反复从这个分布里取样一个 token、拼回输入、再来一次。聊天、推理、调工具——全都建立在这个单调的接口之上。

关键认知

模型没有"回答问题"的原生概念。它只会"续写文本"。后面所有的魔法——聊天、推理、Agent——都是围绕这个接口做的训练设计与协议设计。

注意力再复杂，出口只有一个：最后一个位置上的概率分布

Part 1 · 预训练

预训练：把"压缩互联网"写成一道数学题

原理目标函数朴素到不可思议——但它是后面一切的地基

目标：最小化负对数似然（交叉熵）

L = − Σt log Pθ(xt | x<t)
  • Teacher Forcing：训练时输入永远是"正确的前文"，而不是模型自己生成的——一条语料并行算出所有位置的 loss，一次前向 + 一次反向就完成。
  • 每个位置都是一道 |V| 分类（词表规模，通常 3 万~15 万）的多分类题；万亿 token = 万亿道题。
  • 评估指标：Perplexity（困惑度） = exp(平均 loss)，直觉是"模型在下一个词上平均犹豫几个候选"。

为什么"接龙"能学会知识？

为了降低 loss，模型被迫学习一切有助于预测的东西：语法 → 事实 → 逻辑 → 代码 → 数学模式。预测即压缩，压缩即智能（Ilya 的名言：预测下一个词，逼着你理解产生这些词的世界）。

一条语料在训练中的样子

# 语料: "巴黎是法国的首都"
输入位置:  [巴黎]  [是]   [法国]  [的]   [首都]
预测目标:   是     法国    的     首都   [EOS]
            ↑      ↑      ↑      ↑      ↑
          每个位置都算一个交叉熵 loss，并行计算

Base Model 的"性格"

训练完成后它是一个概率化的互联网文本续写器：你给它问题，它可能续写出"更多相似的问题"——因为在互联网语料里，问题后面经常跟着另一个问题。它能聊天，但它不知道自己在聊天。这就是对齐要解决的问题。

Part 1 · 预训练

预训练工程：真正烧钱的地方全是细节

工程业界共识：算法早就公开，差距在数据与系统工程

① 数据管线（决定上限）

  • 清洗与过滤：去 boilerplate、语言识别、质量分类器（用小型模型给语料打分）。
  • 去重：MinHash / SimHash 模糊去重——重复数据显著拉低效果。
  • 配比是一门玄学：网页 : 书籍 : 代码 : 数学 : 多语言的比例直接塑造能力结构；代码数据被证明显著提升推理能力。
  • Tokenizer：BPE 把文本切成 subword；压缩率影响训练成本与多语言能力。

② Scaling Law（决定预算怎么花）

Loss 随 参数量 / 数据量 / 算力 呈可预测的幂律下降。Chinchilla 结论：模型与数据应同比扩展（约 20 tokens / 参数）。意义：小实验外推大训练，先在 1% 成本上验证再梭哈。

③ 分布式训练（决定能不能训完）

并行策略切什么解决什么
数据并行 DP / ZeRO / FSDPbatch 与优化器状态吞吐量
张量并行 TP单层权重矩阵横切单层放不下
流水并行 PP按层切段到不同机器整模型放不下
  • 混合精度：bf16 计算 + fp32 主权重，省显存不掉点。
  • MFU（算力利用率）是核心 KPI，优秀团队 50%+。
  • 万卡集群必然天天坏：周期性 checkpoint + 自动故障恢复 + loss spike 监控（发散就回滚重来）。

一句话总结

预训练 = 好数据 × 大算力 × 不翻车。产出 Base Model，此时它只会"接龙"。

Part 1 · 对齐

第一次跃迁：为什么"接龙"≠"聊天"

原理问题不在能力，在分布：互联网文本里"问答对话"只是很小一部分

# 直接问 Base Model：
输入：中国的首都是哪里？

可能的续写（都是"合理"的接龙）：
A. 美国的首都是哪里？英国的首都是哪里？  ← 续写"题库"
B. 这个问题困扰了很多人。首先要明确……  ← 续写"论坛帖"
C. 北京。                              ← 碰巧答对，但风格不可控

症结

模型学的是互联网上文本的分布，而"一个乐于助人的助手直接回答用户问题"这种分布在原始语料里占比极低。对齐 = 扭转输出的条件分布：给定同样的前文，让"助手式回答"的概率压过其他一切续写。

对齐要解决的三件事（H 原则）

  • Helpful（有用）：理解指令、直接作答、不打太极。→ 主要靠 SFT
  • Honest（诚实）：不知道就说不知道，不编。→ SFT + RLHF
  • Harmless（无害）：拒绝危险请求。→ 主要靠 RLHF / 安全数据
Base Model互联网接龙机
→
SFT学会"对话格式"
→
RLHF / DPO学会"人的偏好"
→
Chat Model可发布的产品

经验法则

SFT 教格式，RLHF 调味。能力的 95% 来自预训练，对齐做的是"解锁"与"塑形"，而不是"注入新知识"。

Part 1 · 对齐

SFT：用"对话模板"把接龙改造成问答

原理核心技巧只有两个：结构化模板 + Loss Mask

① Chat Template：把对话序列化成"一种新文档"

<|im_start|>system
你是一个乐于助人的助手。<|im_end|>
<|im_start|>user
中国的首都是哪里？<|im_end|>
<|im_start|>assistant
中国的首都是北京。<|im_end|>

特殊 token（<|im_start|> 等）在预训练中从未出现，从零学起、语义干净。模型学到：看到 assistant 开头，就进入"回答模式"；生成 <|im_end|> 就停止——聊天有了"句号"，这是它能成为产品的前提。

② Loss Mask：只在"助手该说的部分"上算损失

token:  system...  user问题...   assistant  回答   <|im_end|>
mask:    0（不算）   0（不算）      0      1      1（算！）

问题部分的 token 不作为训练目标（用户说什么不该由模型"负责"），但仍在上下文中提供条件。EOS token 必须算 loss，否则模型永远学不会停下。

本质

目标函数没变，还是 next-token 交叉熵。变的是数据分布：几万~几百万条高质量 (指令, 回答) 对。模型把"接龙能力"重新聚焦到"助手行为"上——这就是行为克隆（Behavior Cloning）。

Part 1 · 对齐

SFT 工程：数据质量是唯一护城河

工程LIMA 论文的震撼结论：1000 条精修数据，胜过高量低质

数据侧

  • 质量 ≫ 数量：标注一致性差的数据会教会模型"精神分裂"。
  • 多样性覆盖：问答 / 写作 / 代码 / 数学 / 拒答 / 多轮，配比即产品性格。
  • 蒸馏是捷径：用更强的模型（GPT-4 级）生成回答，人工抽检后微调小模型——行业标配。
  • 去污染：严格剔除评测集泄露，否则 benchmark 全是虚高。

常见坑

  • 灾难性遗忘：SFT 学太猛会损失预训练的通用能力 → 混入少量通用数据 + 小学习率。
  • 长度偏置：训练数据全是长回答，模型就会变得啰嗦。

训练侧超参（与预训练完全不同）

项典型做法原因
学习率1e-5 ~ 2e-5（预训练的 1/10）只塑形，别破坏
轮数2~3 epoch多了立刻过拟合
Packing多条对话拼满 4k/8k 上下文GPU 利用率翻倍
Attentionpacking 内样本间要 mask 隔离防止串味
显存不够LoRA / QLoRA 只训低秩增量成本降一个量级

里程碑

SFT 之后模型已经"会聊天"了——事实上很多开源模型只做到这一步就发布。但距离"聊得好"还差最后一步：对齐人类偏好。

Part 1 · 对齐

RLHF / DPO：把"我觉得更好"写进模型

原理很多偏好转不成规则（哪个回答"更好"？）——但可以比较，比较就能学

RM 怎么学？——Bradley-Terry pairwise loss

L = − log σ( r(x, y好) − r(x, y差) )

不需要绝对分数，只要"好的比差的分高"。

PPO 的不稳定 → DPO 的优雅

PPO 要同时维护 4 个模型（actor/critic/RM/ref），调参地狱。DPO 直接从偏好对推导闭式目标：

LDPO = − log σ( β·log π(y好)/πref(y好) − β·log π(y差)/πref(y差) )

不需要 RM、不需要 RL，一次监督式训练搞定——现在开源界事实标准。

工程警示

Reward Hacking：模型会找到刷分捷径（如回答变长、堆奉承话）。对策：RM 集成、长度惩罚、定期换 RM。对齐税：过度对齐会变怂变啰嗦，需权衡。

Part 1 · Chat 诞生

Chat 上线：推理侧的工程同样决定体验

工程模型文件只是半成品——服务层让它变成"你感受到的那个 Chat"

① 自回归解码 + KV Cache

每生成 1 个 token 都要完整跑一次前向。朴素实现复杂度 O(n²)；KV Cache 缓存历史 token 的 Key/Value，每步只算新 token 的注意力 → 近 O(n)。

  • 代价：KV Cache 吃显存（与 序列长 × batch 成正比）→ GQA / MLA 压缩 KV 头。
  • PagedAttention（vLLM）：像操作系统管内存一样分页管理 KV Cache，吞吐量数倍提升。
  • Continuous Batching：请求不等齐步走，谁生成完谁下线、新请求随时插入。

③ 采样参数 = 产品的"性格旋钮"

参数作用直觉
Temperature分布锐化/摊平0=最确定，越高越野
Top-p只在累计概率 p 内采样砍掉长尾胡话
Repetition penalty惩罚已出现 token防复读机

② 停止与流式

  • 模型生成 <|im_end|>（SFT 教它的）即触发 stop；同时设 max_tokens 兜底。
  • Streaming（SSE）：每出一个 token 立刻推给前端——首 token 延迟（TTFT）比总耗时更影响体感。
  • 多轮对话没有魔法：每轮把全部历史按 chat template 重新拼接再喂进去。上下文长度就是这样被吃掉的。
# 一个请求在服务端的生命周期
用户消息 → 拼接 chat template(全量历史)
        → prefill（一次算完全部 KV）     # 算力密集
        → decode 逐 token 生成 + 流式推送  # 显存带宽密集
        → 命中 EOS / stop → 释放 KV 槽位

至此，Chat 诞生

预训练给能力，SFT 给格式，RLHF 给品味，推理工程给体验。但它只会"说"，不会"想"，更不会"做"。下半场开始。

转折点

Chat 的天花板：一次前向，一次机会

"9.11 和 9.9 哪个大？" —— 模型必须在一个 token 的时间里给出答案。

三个结构性短板

  • 算不动：复杂推理需要多步计算，但生成是"脱口而出"，没有打草稿的机会。
  • 不知道：知识截止于训练数据，且无检索手段 → 幻觉。
  • 做不到：不能查数据库、发邮件、跑代码——输出只有文本。

下半场的三个补丁

  • CoT：让它把思考写下来 → 解决"算不动"
  • ReAct：让思考与外部交互交替 → 解决"不知道"
  • Tool Call：把交互协议化、结构化 → 解决"做不到"

三者合体，套上一个循环 → Agent。

Part 2 · CoT

Chain-of-Thought：把"打草稿"变成输出的一部分

原理Wei et al. 2022：在回答前先生成推理步骤，数学/逻辑任务暴涨

# 直接回答（错）
Q: 小明有 3 箱苹果，每箱 24 个，吃了 15 个，还剩几个？
A: 57 个。 ✗

# CoT（对）
Q: 小明有 3 箱苹果，每箱 24 个，吃了 15 个，还剩几个？
A: 先算总数：3 × 24 = 72 个。
   再减去吃掉的：72 − 15 = 57…… 
   等一下，3 × 24 = 72，72 − 15 = 57。
   所以还剩 57 个。 ✗→✓ 中间步骤让每一步只需"局部正确"

为什么有效？三个机制

  • 串行计算预算：Transformer 一层只有一次"思考"，中间 token = 额外的计算步数。想得越久，能解的题越难。
  • 分解降低单步难度：每步只是简单算术/局部推理，落在模型可靠区内。
  • 草稿即上下文：中间结果写出来后，成为后续生成的条件——相当于外置工作记忆。

三种用法

  • Few-shot CoT：在 prompt 里给几个"带推理过程"的示例。
  • Zero-shot CoT：一句咒语 Let's think step by step（Kojima 2022）。
  • Self-Consistency：采样多条推理路径，对最终答案投票——推理路径可错，答案多数为王。

演进：从 prompt 技巧到训练目标

推理模型（o1/R1 路线）：用 RL 直接奖励长 CoT + 正确答案，模型自己学会反思、验证、回溯。CoT 从"提示词"内化为"能力"——代价是推理 token 暴涨，工程上要有 thinking budget。

Part 2 · ReAct

ReAct：让"想"和"查"交替进行

原理Yao et al. 2022：Thought → Action → Observation 循环，专治"闭门造车"

Question: 现任苹果公司 CEO 出生的城市，2023 年人口大约多少？

Thought 1: 我需要先查苹果现任 CEO 是谁。
Action 1: search["current CEO of Apple"]
Observation 1: Tim Cook，自 2011 年起担任 CEO。

Thought 2: 查到了，是 Tim Cook。接下来查他的出生地。
Action 2: search["Tim Cook birthplace"]
Observation 2: 出生于美国阿拉巴马州莫比尔（Mobile）。

Thought 3: 出生城市是莫比尔。现在查它 2023 年人口。
Action 3: search["Mobile Alabama population 2023"]
Observation 3: 约 18.3 万人。

Thought 4: 信息齐全，可以回答了。
Action 4: finish["约 18.3 万人"]

设计精髓

  • 推理轨迹显式化：Thought 让模型规划"下一步查什么"、解读"查到了什么"。
  • 外部信息锚定：Observation 是真实世界的反馈，把幻觉拽回地面——纯 CoT 容易"一本正经地推错到底"。
  • 实现就是 prompt + 解析：few-shot 示例教格式，程序正则解析 Action、执行、把结果拼回上下文。零训练即可跑。

ReAct 的工程痛点（引出 Tool Call）

  • 格式脆弱：模型输出稍走样（少了冒号、多了废话），正则解析就崩。
  • 参数是自由文本：search["..."] 里的参数没有类型、没有校验。
  • 错误难处理：解析失败只能"重新问一遍"，没有结构化错误通道。

→ 需要把"调用"从文本风格升级为协议：Tool Call。

Part 2 · Tool Call

Tool Call（上）：模型是怎么"学会"调工具的

原理不是魔法，还是 SFT：把"调用"变成一种带特殊 token 的结构化文本

训练视角：三件事教给模型

  • 认识工具：工具的 JSON Schema（名称/参数/说明）注入 system prompt，模型学会"有哪些工具、参数什么意思"。
  • 决定调不调：训练数据里既有"直接回答"也有"发起调用"的样本 → 模型学会路由判断。
  • 生成合法调用：用特殊 token 包裹的 JSON 作为训练目标（同样只在 assistant 段算 loss）：
<|im_start|>assistant
<tool_call>
{"name": "get_weather",
 "arguments": {"city": "北京", "unit": "celsius"}}
</tool_call><|im_end|>

数据从哪来

人工构造 + 强模型蒸馏：给定工具集，让强模型生成"何时调、传什么参、多轮怎么串"的轨迹，过滤校验后训练。校验必须机械化：JSON 可解析 + 参数过 Schema，才准入训练集。

对比 ReAct：从"风格"到"协议"

ReAct 文本解析Tool Call 协议
格式保障靠 prompt 自觉特殊 token + 训练内化
参数类型自由文本JSON Schema 强类型
解析可靠性正则，易碎可约束解码：生成时强制合法 JSON
并行调用难一次输出多个调用
错误通道无结构化错误回填

关键工程点：约束解码（Constrained Decoding）

生成 tool_call 段时，用 Schema 构造状态机，每一步把不合法的 token 概率清零（logit mask）。语法 100% 合法由解码器保证，语义正确性由模型能力保证——分工明确，各管各的。

Part 2 · Tool Call

Tool Call（下）：工程闭环的完整时序

工程模型只负责"提出调用"，执行与回填全是你的代码——这个循环就是 Agent 的发动机

必须做对的工程细节

  • Schema 即文档：参数描述写得越清楚，模型传参越准——description 是写给 LLM 的 prompt。
  • 执行层防护：超时、重试、幂等键、权限最小化；模型输出永远不可信，校验后才能执行。
  • 结果回填要"消化"：大结果先截断/摘要，否则上下文爆炸。

高频坑

  • 死循环：模型反复调同一失败工具 → 必须设 max_iterations + 失败计数。
  • 错误吞掉：把异常文本原样回填（含 stack trace），模型会模仿报错风格 → 回结构化的、可行动的错误信息。
  • 并行调用顺序依赖：有依赖的调用别放同一批。
Part 2 · Agent

Agent 诞生：把循环升级为系统

原理Agent = LLM（大脑）+ Tools（手）+ Memory（经验）+ Loop（意志）

本质上它就是那个 while 循环

while not done and steps < max_steps:
    resp = llm(messages, tools)          # 感知+决策
    if resp.tool_calls:
        results = execute(resp.tool_calls) # 行动
        messages += to_tool_msgs(results)  # 观察回填
    else:
        done, answer = True, resp.text

与 ChatBot 的分水岭

ChatBot：一问一答，单轮无状态，输出即终点。
Agent：目标驱动，多轮闭环，输出是中间态——只有"任务完成"才是终点。模型没变，是外部的循环与状态管理让它"有了意志"。

Part 2 · Agent

Agent 工程：Demo 到产品之间隔着这五座山

工程让 Agent 跑起来只要 50 行代码，让它可靠需要一整套系统

① 上下文管理（最硬的仗）

  • 长任务几轮就爆 context：分层压缩——工具结果即时摘要、历史滚动摘要、关键事实外置记忆。
  • Context 即 prompt 预算：塞得越多，注意力越涣散（lost in the middle），不是越多越好。

② 规划与可靠性

  • 复杂任务先 Plan 再 Execute（或 Plan-Act 混合）；子任务可分派 子 Agent 隔离上下文。
  • 错误恢复三件套：重试、换工具、回退一步重规划。

③ 成本控制

每一步都是一次全量推理：分层模型（规划用强模型、杂活用弱模型）、缓存、step/预算硬上限。

④ 安全与护栏

  • 最小权限：工具按能力分级，危险操作（写/删/付款）强制人工确认（human-in-the-loop）。
  • Prompt Injection 是 Agent 的头号威胁：工具返回的内容=不可信输入，可能挟持后续行为 → 内容隔离 + 行为白名单。
  • 全程可观测：trace 每一步 thought/action/observation，否则无法调试。

⑤ 评估（比训练更难）

  • 没有标准答案 → 用 任务成功率 + LLM-as-Judge + 人工抽检。
  • 回归测试：固定任务集，每次改 prompt/模型后重跑——Agent 系统任何小改动都会蝴蝶效应。

经验之谈

80% 的提升来自更好的工具描述、更干净的上下文、更狠的评估集，而不是换更强的模型。
