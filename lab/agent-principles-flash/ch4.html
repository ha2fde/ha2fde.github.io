Agent 的协议层

模型只会输出文本。要让文本变成动作，需要一份「约定」——它由谁写、写在哪里、由谁执行，是这一层的全部问题。这一讲给你五套具体答案，样样能徒手画关系、看懂真实报文。

开场本讲问题：让文本变成动作的「约定」
模型只会输出文本。要让文本变成动作，需要一份「约定」。
问题一

约定由谁写？

是你自己定义 schema，还是协议标准定，还是工具作者早就写好了？

问题二

写在哪里？

在宿主进程里、在某个 server 上、在命令语法里，还是跟着项目走？

问题三

由谁执行？

模型永远不执行——真正动手的执行权，握在谁手上？

五样机制各给了一套不同答案。带着三个问题往下读，读到哪一套都能立刻对上号。

本讲只讲「接口怎么定义与传递」；评估、上线保障、「人在环」的审批设计不是本讲内容。

同一族 · 工具tools：模型看到一份「能调用的东西」清单
一份清单

模型能看到「能调用的东西」清单——每个工具的名字、用途、参数。

模型自己决定

要不要调、调哪个、传什么参数，由模型按任务需要现场决定。

宿主负责执行

模型只输出「调用意图」；真正跑工具的永远是宿主 Host。

术语：函数调用 Function Calling 是模型 API 的能力；工具 Tools 是宿主提供的可调用项。两者合起来，就是「能做什么」的清单。

下一页看清单的真实形态（schema），再下一页看一次完整往返。

同一族 · 工具tools 的 schema：name + description + parameters

一个工具 = name + description + parameters（JSON Schema）。这是 OpenAI 函数调用 tools 数组里的真实结构：

{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询指定地点的实时天气",
    "parameters": {
      "type": "object",
      "properties": {
        "location": { "type": "string", "description": "城市名，如：北京" },
        "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
      },
      "required": ["location"]
    }
  }
}

选对：模型靠 name 与 description 判断「该不该调、调哪个」。description 就是写给概率模型看的语义。

填对：模型靠 parameters（JSON Schema）知道参数类型、取值范围、哪些必填。

为什么写 schema：模型不是人，没法「看着按钮猜」。描述得越清楚，选对、填对的概率越高。

同一族 · 工具tools 一次完整往返：宿主在中间跑腿

注意第 ②③ 步：模型不执行、不连真实服务——「发意图」与「执行」永远由宿主切开。

同一族 · 工具看懂真实报文：tool_calls 与 role=tool 回填
模型返回 · assistant 消息里的 tool_calls 
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "get_weather",
        "arguments": "{\"location\":\"北京\",\"unit\":\"celsius\"}"
      }
    }
  ]
}
宿主回填 · role=tool 的工具结果 
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "{\"temperature\":22,\"condition\":\"晴\"}"
}

宿主把工具输出原样作为新消息塞回对话，模型据此继续。

字段名取自 OpenAI Chat Completions API：tool_calls / tool_call_id / role: tool，未编造。报文里没有「模型自己动手」，只有「意图」与「结果」。

同一族 · 工具tools 正反面：什么时候该用，什么时候别上
该用
  • 能枚举的确定性动作：查天气、算数、查库、发消息
  • 动作能被 JSON 精确表达，参数边界清楚
  • 宿主已有现成实现，只差一个入口
不该用
  • 权限敏感：删除、转账只靠文本描述 → 容易越权
  • 工具太多：description 全部吃上下文 context
  • 动作无法用 JSON 表达：复杂图形编辑、物理操作
判别一句话：「schema 能不能把这件事说清楚？」能 → tools；不能 → 换一种机制，或加人确认。
同一族 · MCPMCP 为什么出现：从「手动接一遍」到「标准插座」

痛点：每个工具都要宿主「手动接一遍」——定义 schema、写调用代码、处理认证。换一个宿主，全部重来。

需要一个「标准插座」

Model Context Protocol（模型上下文协议 MCP）：统一「工具如何被发现与调用」的开放协议。

统一定义与调用

工具怎么描述、怎么列举、怎么调用，都有标准方法：tools/list、tools/call。

统一连接

stdio（本地子进程）与 Streamable HTTP（远程）两种 transport，基于 JSON-RPC 2.0。

一句话：tools 是「一个宿主自带的插件」；MCP 是「通用的插座标准」——server 写一次，任何 MCP 客户端都能接。

2024-11 由 Anthropic 开源；后纳入 Linux Foundation 主导的开放标准项目（Agentic AI）继续演进。官网：modelcontextprotocol.io · 规范 specification/latest

同一族 · MCPMCP 实体分清：Agent 不直接连 Gmail

关键分层：Agent 不直接连 Gmail——中间隔两层：Client 在 Agent 进程里负责协议，Server 把真实服务封装成工具。

分清四者：Agent 发起 · Client 说协议 · Server 封装服务 · 原始服务真正干活。MCP 只管「Client ↔ Server」这一段。
同一族 · MCPMCP 一次完整往返：从握手到结果回传

要点：模型从不直接碰真实服务。最后一步由 Client 把结果塞回上下文，模型据以回答。

同一族 · MCP看懂真实 MCP 配置：.mcp.json

真实形态：Claude Code 项目级配置 .mcp.json（各客户端大同小异，字段取自官方文档）：

{
  "mcpServers": {
    "playwright": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest"]
    },
    "notion": {
      "type": "http",
      "url": "https://mcp.notion.com/mcp"
    }
  }
}

stdio：client 启动一个本地子进程（如 npx），父子进程用 stdin/stdout 说话——适合本地工具。

http：client 连接一个 URL（Streamable HTTP），可跨机器——适合远程服务。

连上之后自动走一遍 initialize 握手，再 tools/list 拿工具清单——协议方法名见上一页泳道图。

MCP 基于 JSON-RPC 2.0；核心方法：initialize · tools/list · tools/call。规范：modelcontextprotocol.io/specification/latest

同一族 · MCPMCP 正反面：别把每个工具都搬上 MCP
过度设计
  • 单机、单工具、一次性：写个函数就能调，别上 MCP
  • 引入 server 进程、协议版本与连接生命周期，代价不小
生态参差
  • 社区 server 的质量与维护水平参差不齐
  • 有的 server 工具定义粗糙，反而干扰模型判断
信任边界
  • 接外部 server = 把「谁能调什么」交给对方
  • 第三方 server 可能接触到你的 token 与数据
判断
  • 「这个能力要不要被多家复用？」要 → MCP；否 → 直接调
  • 先做直达，长出第二个使用方再抽象
同一族 · CLICLI：最老也最普适的「工具接口」
它是什么

Command Line Interface（命令行接口 CLI）：模型直接生成 shell 命令，宿主负责去执行。

为什么天然

人类几十年的既有工具几乎都是命令行：grep、git、curl、jq、sqlite3…不用重新定义 schema。

工具集免费：宿主只需给一个沙箱，整个 shell 世界就是工具库——命令语法早已写好，无需为每个动作写 JSON。

代价：命令没有「参数校验」，任何字符串都可能被执行 → 下一页讲风险与防护。

同一族 · CLICLI 一次完整往返：命令进，stdout 出

真实命令：

$ grep -n "TODO" src/app.py
src/app.py:12:    # TODO: 换掉这个临时实现
[stdout 上一行 · exit code 0]
模型从不执行命令。宿主管执行、管沙箱、管审计；exit code ≠ 0 就是给模型的失败信号。
同一族 · CLICLI 的风险与防护：命令有破坏力
破坏力
  • rm -rf 删文件、curl 发请求、git push 动远端
  • 命令没有「参数校验」，输出还可能被注入进下一步
防护
  • 沙箱：容器 / 子进程 / 专用目录
  • 只读挂载、权限隔离、预算上限
  • 命令审计日志
什么时候不该用：没有沙箱与审计的裸 shell，不要开放给模型。命令能到的地方，就是模型权限的边界。
共通点抽共通点：约定写在外，执行在宿主
机制定义写在哪执行权在谁模型发什么
Tools宿主请求里的 schema宿主（解析 tool_call）tool_call：{name, arguments}
MCPServer 暴露 · Client 发现Client → Server → 原始服务tools/call：方法名 + 参数
CLIshell 命令语法（早已存在）宿主（沙箱内执行）命令字符串
三条同一种分工：「约定」定义在外面，执行权握在宿主手里。模型永远只「发意图」，不执行。差别只在约定的载体：JSON schema · 协议方法 · 命令语法。

记住这一条主线，后面两样（Skills、A2A）是在这条主线上各自换了维度。

抽象层 · ACIACI：接口是写给概率模型看的

Agent–Computer Interface（ACI）是什么

计算机为 Agent 提供接口的抽象：把「工具、上下文、状态、反馈」组织成模型能读懂的界面。它不是一个具体协议。

核心差异：接口是写给「概率模型」看的，不是写给编译器或人。人看文档靠直觉，编译器靠类型，模型靠「语义描述 + 概率推断」。

由此推出的设计原则：

  • 可发现 Discoverable：能力清单本身要能进入上下文
  • 容错 Tolerant：格式小瑕疵应能被猜回，而不是直接失败
  • 明确的失败反馈：报错要能告诉模型「为什么、怎么办」
  • 少歧义：一个意思只给一种写法
  • 给足上下文：缺上下文时模型只能靠猜

ACI 是一把「看穿工具类接口」的钥匙；具体机制怎么做，还是看前一组。

抽象层 · ACIACI 的定位：背后抽象，不是本讲总纲

ACI 是理解工具类接口的一把钥匙：看前一组时用得上；它不替代任何一样，也不包揽后一组。

换维度 · SkillsSkills 换的维度：该怎么做，而不是能做什么
管什么

Skill 管「该怎么做」（how-to），而不是「能做什么」（what）。它教 Agent 执行某类任务的方法。

载体

一个 skill = 一组指令 / 模板 / 参考 / 脚本，通常是目录里的 SKILL.md + 配套文件。

与工具一句话点破：工具回答「能做什么」——可调用的动作；skill 回答「该怎么做」——执行某类任务的流程。工具改不了模型的做法，skill 可以。

触发方式：description 写清楚 what + when，模型按需加载；也可用 /技能名 手动调用。

换维度 · SkillsSkills 的真实形态：一个目录 + SKILL.md

真实形态：一个 skill 就是一个目录，SKILL.md 必选，其余可选（Anthropic Agent Skills 约定）：

目录结构 
.claude/skills/pdf-filler/
├── SKILL.md          ← 必选：触发条件 + 步骤
└── scripts/
    └── fill.py       ← 可选：可执行脚本
SKILL.md 
---
name: pdf-filler
description: 填写 PDF 表单；用户提到
  PDF、表单、签字时使用。
---

# PDF 表单填写
1. 读取表单字段
2. 用 scripts/fill.py 填入
3. 校验后交付

分发渠道：客户端内置、市场、GitHub 仓库（如 anthropics/skills）、随项目打包 .claude/skills/。

省 context：启动时只把 name + description 放进上下文；触发后才读取全文。

换维度 · SkillsSkills 编写要点与应用场景
编写要点
  • 明确的触发条件：description 写清楚 what + when
  • 分步骤：把流程写成能照做的步骤
  • 给示例与反例：让模型照着对
  • 小而聚焦：一个 skill 只干一类事
应用场景
  • 需要固定流程 / 固定格式的重复性任务
  • 需要内部知识的任务（品牌规范、代码规范）
  • 要保证输出一致的团队流程
什么时候不该用：一次性的简单任务，一段 prompt 就够——上 skill 反而多一层加载与维护成本。
换维度 · SkillsSkills 的未来发展：点到即止
  • 资产类型更丰富：脚本、模板、校验器、参考文档都能打包进 skill，agentskills.io 正在统一约定
  • 生态与市场：官方仓库（anthropics/skills）、IDE 与客户端的一键安装
  • 与工具和 MCP 组合：skill 管「怎么做」，MCP 管「连哪」，工具管「动作」——三者叠加使用
趋势：skill 正在成为「可复用的方法论」的携带单位——把经验写进目录，而不是写进每次对话。

参考：code.claude.com/docs/en/skills · agentskills.io

换维度 · A2AA2A 换的维度：对端是另一个 Agent

对端是另一个 Agent，不是一台机器。发现靠 AgentCard（能力声明），任务靠 Task / Message 报文（下一页）。

换维度 · A2A看懂真实 A2A 报文：Task 对象

真实结构：A2A 规范里的 Task 对象（字段名取自规范，非虚构）：

{
  "id": "task-report-7f3a",
  "contextId": "ctx-conversation-abc",
  "status": { "state": "TASK_STATE_WORKING" },
  "message": {
    "role": "user",
    "parts": [
      { "text": "请把这份数据整理成季度报告" }
    ]
  },
  "artifacts": [],
  "metadata": {}
}

Task 状态机：submitted → working → completed / failed / canceled / input-required / auth-required。

Part：text / raw / url / data 四种内容；Message 有 role（user / agent）与 messageId。

什么时候不该用：两个 agent 的事，用一个 agent + 工具就能做完时，别上 A2A——它解决的是跨组织、跨信任域的长期任务。

规范：a2a-protocol.org/latest/specification/ · 由 Linux Foundation 维护。

收尾收尾：五样机制，用同一套问题看穿
机制约定由谁写写在哪里由谁执行
Tools宿主 / 厂商按 API 约定定义 schema宿主进程内，随请求进上下文宿主（解析 tool_call）
MCPServer 实现者Server 暴露 · 配置注册（.mcp.json）Client → Server → 原始服务
CLI工具作者（命令语法早已存在）shell 命令字符串宿主（沙箱内）
Skillsskill 作者.claude/skills/<name>/SKILL.md宿主按步骤代跑
A2AA2A 协议 + 对端 AgentTask / Message 报文对端 Agent（服务端）

主线没变：模型只发意图、不执行；约定写在外、执行在宿主——五样全符合，差别只在「约定」的载体。

本讲边界：只讲接口怎么定义与传递。评估、上线保障、「人在环」的审批设计，不是本讲内容。
