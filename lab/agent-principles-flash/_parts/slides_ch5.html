AGENT 原理与实践 · 第五章

从 demo 到生产

Demo 问「能不能做到」，生产问「每单多少钱、出错谁负责、停了怎么办」。这一讲教你用一张控制权连续谱定位自己的项目，再据此决定要不要上框架，并给你一份能直接抄的上线前清单。

决策型 · 会被反复回查先定位、后工具评估先行
开场主线与顺序：先控制权、后工具
为什么顺序不能反

编排（orchestration）方式，决定了你需要什么工具。先想清楚「谁来决定下一步」，再谈 API / SDK / 框架。

顺序反了会怎样：还没定位就选框架 → 框架替你做了你没想过的决定，项目被框架牵着走。

本讲边界（讲到哪为止）

只讲下周就要做的决定：在谱上定位、上不上框架、上线前清单。

不讲趋势判断、协议细节、长期路线。出现的术语一律就地交代清楚。

一句话主线：先在控制权连续谱（agency continuum）上找到自己的位置 → 据此决定工具 → 再按「谁在问」逐项备齐上线条件。

本讲自足，不引用其它章节；只讲正面做法与自限边界。

预测（明确标注，非现状）

到 2027 年底，超过 40% 的 agentic AI 项目会被取消 —— 原因：成本失控 · 业务价值不清 · 风控不足。

来源：Gartner 新闻稿（2025-06-25）。这是预测，不是今天的现实——但它是给「要不要投入生产」敲的警钟。

先记住：试点几乎普及，能过生产关的很少。卡点不在模型能力，在运营条件。
卡在哪死因三件套与失败模式
成本失控

每次调用都在花钱，任务越多越收不住。

业务价值不清

做了，但没人说得清省了什么、赚了什么。

风控不足

出事没人管、没有止损与退出机制。

三件套口径：Gartner 预测（2025-06-25）对「>40% 项目被取消」的原因归类（Gartner）。

结论：多数项目不是「模型不行」，是运营模型缺失——没有评估、没有止损、没有状态管理、没有可观测性。
卡在哪为什么难：提问的人换了
Demo 阶段

提问人：开发者

「能不能做到？」

验收标准：演示顺、能跑通、看着对。输入自己挑，错了重来就好。

生产阶段

提问人：业务方

「每单多少钱？出错谁负责？停了怎么办？」

验收标准：单位经济、责任边界、可用性与恢复。输入是真实的，错一次就有成本。

换提问人，就是换验收标准。demo 里通过的「能跑」，到生产里要重新过一遍：每一道题都要有数据、有责任人、有兜底。

控制权控制权连续谱：先定位，再谈别的

谱上每个位置都是一种「交换」：你买的是左端的确定性，还是右端的灵活性？先认账，再落位。

控制权谱上的三种编排：谁决定下一步
① 代码全决定

流程写死在代码里，模型只在指定位置填空。下一步是谁，代码说了算。

谱位：左端。

② 代码定骨架 · 模型定局部

代码定步骤顺序，每步内的动作与内容由模型决定。两边分权。

谱位：中段。

③ 模型每步自己决定

模型自己规划、自己选工具、自己看结果定下一步（ReAct：Reason + Act）。决定权几乎全给模型。

谱位：右端。

分类标准只有一个：「下一步由谁决定」。规则、骨架、自主，对应谱上的左、中、右。

控制权真实产品几乎都是混合的

正面：先定步骤骨架，每步细节交给模型——流程可预测，细节能应变。

反面：全自主 demo 好看但不可控，出错难定位；全写死跟传统软件没区别，AI 的灵活性白买。

所以真实产品几乎都落在中段：把步骤写死、把内容放开。全自主是演示用的，全写死是传统软件。

控制权在谱上找自己的位置：决策三问
问 1 · 确定性

任务确定性高不高？流程是否基本固定、输入是否规整？

问 2 · 代价

错误代价大不大？错了是小麻烦，还是事故级？

问 3 · 响应

需要多快应变？要不要随输入随机应变？

三问的结果谱上位置做法
高确定 · 低代价 · 要快靠左（流程全写死）规则 + 少量模型填空
中确定 · 中代价 · 可控中段（混合）代码定骨架、模型定局部
低确定 · 高代价 · 要应变靠右（模型多决定）必须配评估 + 人在环兜底
位置不是天赋，是逐点定出来的：任务里的每个决策点，先问「这一步能不能写死」——能写死就靠左，不能就靠右，剩下的自然落在中间。
工具用不用框架，是另一个维度
API · 原始请求

你直接发请求、处理返回，控制一切。适合简单、线性、靠左的任务。

代价：状态、重试、记忆全自己写。

SDK

软件开发工具包（Software Development Kit），封装模型调用与常见参数，省样板代码，流程仍由你定。

适合中等复杂度。

框架 framework

编排 + 脚手架：状态、工具、记忆、评估、重试一整套。

适配中段到右段、多工具、要长期迭代。

工具层替你做主的部分你在谱上偏哪一段用得上
API无——一切自己写左端 / 简单线性任务
SDK调用与序列化中段偏左
框架状态、工具、记忆、评估、重试、恢复中段到右段 / 复杂多步任务
别把两个问题混成一个：「谱上放哪」是决定，「用什么工具」是执行。先定位，再选 API / SDK / 框架；三者可叠加，不是互斥。
工具什么时候该上框架：判断清单
该上框架
  • 谱位靠右：模型参与决策多
  • 任务复杂：多步骤、多工具
  • 需要记忆 / 重试 / 评估：状态与恢复是刚需

例：客服工单多步 + 调工具 + 要审计——框架把状态与重试现成给你。

裸代码就够
  • 谱位靠左：线性流程
  • 简单一问一答一存：无状态、无重试需求
  • 改造老系统：不想引入新依赖

例：把一份文档翻译成三条要点——一个 API 调用就够，上框架是负担。

方向性信号（MIT NANDA / Deloitte 口径，2026，generative AI pilots 广义口径）：外购或与厂商合作（~67% 成功）比自建（~33%）更易落地——买来的框架也算「外购」（MIT NANDA）。

判断标准不是「酷不酷」，是「要自己维护的东西有多少」。维护成本由你自己扛的部分越大，框架越值。

凭什么上线评估 Evaluation：放最前
元问题：没有评估（evaluation），其它一切改进都无法验证——换模型、调提示词、加记忆，怎么知道变好了？demo 里「看着对」≠ 生产里「可度量」。

个真实任务——从生产环境挑，不是编的。

三档

打分：对 / 部分对 / 错，别用 100 分制造错觉。

1 个

核心指标：任务完成率（如 ≥90% 才算可上线）。

  • 先立基准，再谈优化。没有基准的「调优」都是碰运气。
  • 评估集随生产一起长：每次真实翻车，就把那条任务补进评估集。
  • 评估指标要贴着任务定义：完成率、正确率、达标比例，选一个能对业务说的。
一句话：先回答「什么叫做好了」，生产才有入场券。
凭什么上线记忆 Memory：模型会「忘」，你要替它记住
为什么需要记忆

模型的知识有截止时间，对话一长还会「忘」早先的上下文。记忆（memory）= 把状态与知识存起来、需要时取回。

参数里的知识是「记」出来的，会过期；记忆系统是「查」出来的，随取随新。

RAG：一句话

检索增强生成（Retrieval-Augmented Generation，RAG）：先检索、再生成——先从你的知识库里取相关片段，再让模型基于它作答。

给模型「看资料再答题」，而不是让它背题库。

什么时候该上：知识要新（今天的内容）、私有（外部查不到）、变化（会改）——三条中一条，就要考虑记忆 / RAG。

代价：检索质量决定上限——检索不到对的片段，模型再强也没用。烂库 + 好模型 < 好库 + 一般模型。

上线前问一句：它需要的知识，是「背下来的」还是「查得到的」？查得到的先做检索，别指望模型记。
凭什么上线安全 Security：三个坑、四个对策
坑 1 · 提示注入

提示注入（prompt injection）：恶意指令混进用户输入或工具返回，诱导 agent 越权行动。

坑 2 · 工具权限放大

agent 能访问的工具，比任务需要的多——权限越大，出事面越大。

坑 3 · 敏感数据外泄

上下文里带出密钥、PII，或写进外部工具、日志、提示词。

四个对策（照着做）
  • 最小权限（least privilege）：只给任务必需的工具与数据。
  • 沙箱（sandbox）：agent 在隔离环境里跑，影响不了外面的系统。
  • 输入输出过滤：进系统前过滤指令，出系统前过滤敏感内容。
  • 禁止回显密钥：API Key、密码一律不回显、不进提示词、不写日志。
假设：攻击者已经看过你的系统提示词。所有安全设计都要按「提示词可以被注入」来写。
凭什么上线治理 Governance：有行为的系统要有负责人
治理（governance）四件事
  • 谁负责：有明确的负责人与责任边界
  • 留记录：行为日志，出事后查得到
  • 可撤销：一键停用，随时下线
  • 审批流：高风险动作走审批
为什么要管

agent 是有行为的系统——会发消息、写数据、花钱。没有负责人与日志，出事没人接、事后查不了。

demo 不用管，因为错了可以重来；生产管的是「出错了怎么办」。

三个必须：一个负责人 · 一份行为日志 · 一个一键停用按钮。三者齐了，才谈得上「治理」。

审批流的细节（谁来批、批几次）不在本讲展开；先保证「有」这套机制。

凭什么上线成本与延迟 Cost & Latency：先算每单多少钱
成本估算公式 
每任务成本 ≈（输入token×输入单价
  + 输出token×输出单价）× (1 + 重试率)

数字例子：平均 20k 输入 + 2k 输出；单价参考 Claude Sonnet 5（核对 2026-08）$2 / $10 每百万（platform.claude.com）。

0.04 + 0.02 = $0.06 / 任务；重试率 20% → ≈ $0.07；1 万任务/天 ≈ $720/天。

延迟构成
  • 模型响应：首 token 延迟
  • 工具调用：每次往返 + 网络 + 服务端处理
  • 重试 × 步数：每多一步都累加，重试让延迟翻倍式上涨

demo 只测一步，生产是多步连乘——单步很快 ≠ 整个任务很快。

很多项目不是技术不行，是单位经济算不过来。上线前先算「每单多少钱、单次要多久」；算不清，别上线。
凭什么上线可观测性 Observability：能复盘、能回滚

可观测性（observability）≠ 评估。

评估问「好不好」（这次平均正确率多少）；可观测问「这次到底发生了什么」（哪一步、哪个工具、什么输入）。

每步记录什么
  • 输入 / 输出
  • 工具调用（哪个工具、参数、返回）
  • 耗时 / 花费 / 重试次数
为什么必须：demo 里出问题重跑一次就好；生产里出问题，要能复盘（先定位是哪一步），再回滚（回到上一个可用版本）。没有记录，两件事都做不到。
落地：从第一天就把每步日志带上 trace id——比事后补日志便宜一百倍。
凭什么上线人在环 Human-in-the-loop：高风险动作前有人
审批点放哪

高风险动作之前——发消息、写库、花钱、对外承诺。

低风险动作不拦，否则没人用：每步都问，等于没有 agent。

粒度多大

整任务批一次 vs 每步都批：粒度越细越安全，也越费人。

多数系统只在高风险步设闸：前几步放行，最后一关人点。

与控制权连续谱直接挂钩：越靠右（模型决定越多），越需要人在环（human-in-the-loop）兜底。「全自主」不意味着没人——自主度越高，人应该站在更关键的位置。

审批设计（谁来批、批几次、超时怎么办）点到为止，不在本讲展开。
