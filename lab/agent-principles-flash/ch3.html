AGENT 原理与实践 · 第三章

从 chat 到 agent

一个只会「预测下一个词」的架构，是怎么一步步长成会思考、会动手、会把活干完的 Agent 的。

预训练对齐 · 对话思维链ReActTool callAgent
主线主线预览：能力是怎么长出来的

本讲边界：只讲「能力是怎么长出来的」；tool call 讲到「模型发意图、宿主执行」为止，不展开 schema、报文格式与协议标准。

起点起点：预训练——预测下一个词
自回归 Autoregressive

输入一段上文，模型预测下一个 token；预测完拼回去，再预测下一个——一个接一个，「接龙」式地生成。

"今天天气真好，" → 预测下一个 token → "我"
三个要素
  • 自回归 Autoregressive：从左到右，逐个生成
  • 下一词预测 next-token prediction：目标是「续写」，不是「回答」
  • 架构 Transformer（Attention Is All You Need, 2017）+ 海量无标注文本
预训练 Pre-training 产出的不是「会聊天的助手」，而是一台会续写的引擎——它学的是「接下来该写什么字」。

数据来自网页、书籍等，无需人工标注——这是它能「学」到海量语言与知识，却不需要人一句句教的根本。

起点预训练的产物：一个文本续写器
会什么
  • 语言模式：语法、措辞、风格
  • 世界知识：海量文本里的常识与事实
  • 续写、概括、翻译都「会一点」
致命缺陷
  • 你问它问题，它默认在「续写更多文本」，而不是「回答问题」
  • 没有「对话」概念：不懂「你问我答」

真实的样子：

你问：北京和上海，哪个离南京更近？
它回：北京是中国的首都，是一座历史悠久的城市，
上海是中国最大的经济中心之一……（还在续写，没有回答）
结论：「会说话」和「会答问」是两回事——下一步，要把这台续写器从「写下去」掰到「答上来」。
对齐对齐第一步：监督微调 SFT

监督微调 SFT（supervised fine-tuning，监督式微调）：用「用户问 → 正确答」的示范对，在预训练模型上继续训练。

补了什么：学会「提问之后该回答」，而不是继续「写」——从「文本续写器」变成「会问答的模型」。

代价：标注贵（人一条条写示范）；依赖示范质量（示范错，模型也学错）；只会「学过的答法」，换种问法可能失灵。

对齐让对话好用：RLHF

RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）——让模型回答更合人类偏好。三步：

补了什么：回答更合人类偏好——有帮助 Helpful、诚实 Honest、无害 Harmless；比 SFT 更少答非所问、更「像人话」。

代价：流程复杂、昂贵（每步都要人工参与）；可能变保守——宁可少说，也不冒险。

出处：InstructGPT（Ouyang et al., 2022）arXiv:2203.02155。细节点到即止——本讲不展开强化学习本身。

定格定格：chat 有了，Agent 还差两步

走到这里，chat 出来了——它会陪你聊天。但它是「一次性问答」：问一句、答一句，输出就是终点，下一步永远由人来做。

现状：一次性问答

问 → 答 → 结束。没有「下一步」，也没有「动手」。

还差 ① 能思考

复杂任务要先拆成多步、自己推下去——需要思维链。

还差 ② 能动手

光想不做没用，要能发起外部动作——需要 ReAct 与 tool call。

顺序：先解决「想」（思维链），再解决「动」（ReAct → tool call）。剩下的篇幅，就按这个顺序走。
思考思维链 Chain-of-Thought
它做了什么
  • 让模型把中间步骤写出来，而不是只给结果
  • 做法：提示词里要求「一步一步推理」，或给出带步骤的示例
  • 出处：Chain-of-Thought Prompting（Wei et al., 2022）arXiv:2201.11903
补了什么
  • 多步计算从「隐藏」变「显式」
  • 算术、常识、逻辑类复杂推理明显变好

提示词与回答的形状：

问：有 6 排座位，每排 4 个，再放 3 个备用，一共几个？
答：一步一步想。先算座位：6×4 = 24；再加备用：24+3 = 27。
所以一共 27 个。
代价：输出变长 → 更贵、更慢；中间步骤不保证正确——「会写理由」不等于「理由对」。
思考CoT 的本质：把计算搬到纸上

同一道真实的多步应用题，正反两遍对比——关键在「中间结果写不写出来」。

无 CoT：直接给答案 
问：6 排座位，每排 4 个，
再放 3 个备用，一共几个？
答：24 个。

算完 6×4 就停了，漏掉备用座位——多步计算全在「脑内」一次带过，容易丢步。

有 CoT：写出中间步骤 
问：6 排座位，每排 4 个，
再放 3 个备用，一共几个？
答：6×4 = 24；24+3 = 27。
一共 27 个。

中间结果写到「纸上」，下一步接着用——丢步就藏不住了。

本质：不是模型变聪明了，而是把多步计算从「脑内」搬到「纸上」——显式化，才可检查、可纠错。
分叉分叉点：让模型「动手」的两条路

CoT 让「思考」可见，但思考完，模型输出的仍然是文字——还是「说」，没有「动」。要让它动手，必须能发起外部动作。两条路：

两条路不互斥、也不互相取代：ReAct 在提示词层「教写法」，tool call 在训练与接口层「定格式」。先分别讲，再点破区别。
ReActReAct：提示词里写循环
它是什么
  • ReAct = Reasoning + Acting（Yao et al., 2022）arXiv:2210.03629
  • 提示词里教模型交替输出：Thought 想 → Action 做 → Observation 看结果
  • 当年的 Action 就是调 API：Action: Search["..."]
补什么 / 代价
  • 补：把「思考→行动→看结果」的循环写进格式，模型照着「写作文」
  • 代价：格式不稳（多写一句就乱）；提示词暴涨；推理与动作混在同一段文本里

格式骨架（模型照着填空写）：

Thought: ...
Action: Search["..."]
Observation: ...
（循环）...
Final: ...
关键：纯提示词、不训练——改提示词就能上。模型只是在「按格式写文本」，它并不真的去执行。
ReAct一个真实的 ReAct 循环
每一步的文本形态（都是模型写的字） 
Thought: 我需要天气数据
Action: Search["Paris"]
Observation: 12°C，有雨
Thought: 问到了
Final: 明天巴黎 12°C，有雨

宿主读懂 Action 就执行，读不懂就停在原地——这正是下一页要讲的脆弱点。

ReActReAct 的真相：执行权在宿主
模型只负责「写」
  • Thought / Action / Observation 全是文本，模型从没「真的去查」
  • 宿主读到 Action 字段，才知道「模型想调什么」
  • 宿主发起真实调用；把结果写回 Observation，塞回上下文
埋下的种子

这一环已经具备 tool call 的雏形：意图由模型发，执行归宿主。

差的只是把「调工具」从提示词里的自由文本，升级成训练好的结构化输出。

记住这句话：「模型只负责说话，宿主 Host 负责做事」——下一页的 tool call，只是把这句话做进训练与接口。
Tool callTool call：把调工具做进训练与接口

工具调用 Function Calling / tool use：把「调工具」做进训练目标与结构化接口——模型需要工具时，直接输出结构化的调用：函数名 + 参数。

补了什么
  • 稳定：输出格式由接口约定，不再「看运气」
  • 可解析：程序直接拿到「函数 + 参数」，不用猜文本
  • 幻觉字段少：参数不合法，接口就报错
代价
  • 需要专门构造带真实工具的训练数据
  • 需要设计接口与协议约定
  • 模型仍可能乱选工具——只是更少、更可控

结构化输出的形状：

{
  "name": "search_weather",
  "arguments": { "city": "Paris", "date": "tomorrow" }
}
对比 ReAct 的 Action: Search["..."]：这里是程序可解析的对象，而不是一段自由文本。
点破点破：ReAct 和 tool call 不是同一层
ReAct · 提示词层
  • 行动是自由文本：写在「作文」里的字
  • 层：提示词（prompt），无需训练
  • 动作靠人 / 宿主「读文本」才能执行
  • 产物：一段对话文本
Tool call · 训练 + 接口层
  • 行动是结构化对象：函数名 + 参数
  • 层：训练目标 + 接口（API）
  • 动作直接可解析，宿主「按对象」执行
  • 产物：程序可消费的调用
关键：后者不取代前者，两者常叠加——先推理（reasoning）决定该做什么，再发 tool call 把它变成程序可执行的动作。混为一谈，就读不懂现代 Agent 的分工。
执行谁执行：模型发意图，宿主去办

无论 ReAct 还是 tool call，动作的真正执行者都是宿主 Host（runtime）——模型只负责「发意图」。

模型发意图，宿主执行。动作的世界归宿主管——这是 chat 与 Agent 的分水岭。

本讲到此为止：不展开 schema、报文格式与协议标准——那些是下一层工程的内容。

AgentAgent：会思考、会动手、会循环

三样东西凑齐，会干活的 Agent 就出来了：(a) 多步推理（思维链）+ (b) 工具调用（tool call）+ (c) 循环直到完成。

和「一次性问答」的本质差别：chat 的输出是终点，Agent 的输出是中间产物——它循环到「完成」才停。
横向横向话题：上下文工程

上下文工程 Context Engineering：不管链上哪一步，真正喂给模型的都是上下文（Context）——它决定模型看到什么、据此怎么做。

它不是链条上的某一步，而是贯穿全程的横向话题——从 system prompt 到工具定义到历史管理，都是工程。
代价代价总表：每一步的补与失
步骤补了什么付出了什么（数据 / 算力 / 提示词 / 成本 / 延迟）
预训练会续写：语言模式 + 世界知识海量数据与算力，一次训练成本可达千万美元级
SFT从「续写」变「问答」标注贵；依赖示范质量；只会「学过的答法」
RLHF回答更合人类偏好流程复杂昂贵；可能变保守
CoT多步推理从「隐藏」变「显式」输出变长 → 更贵、更慢；中间步骤不保证正确
ReAct思考 + 行动循环，纯提示词格式不稳；提示词暴涨；推理与动作混在文本
Tool call稳定、可解析的调用专门训练数据 + 接口设计
一句话记住：每一步都在补一个能力，也都在付一份代价——工程就是在这两者之间挑平衡。
收尾

从 chat 到 agent，能力是这样长出来的

预测下一个词 → 会对话 → 会思考 → 会行动 → 会干活。

本讲讲到这里为止：

  • tool call 的 schema、报文格式与协议标准，不是本讲内容。
  • 关键分清：ReAct 是提示词层的「作文格式」，tool call 是训练 + 接口层的「结构化输出」。
  • 上下文工程是横向话题，贯穿全程——不是链条末端的一环。
