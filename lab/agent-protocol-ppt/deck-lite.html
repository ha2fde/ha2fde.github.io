Agent 的协议层

Tools · MCP · CLI · Skills · A2A
以及把它们统一起来的那个词：ACI

模型只发起，不执行 最终都被拍平成一个 tools 数组 真正的设计对象是接口，不是协议

每页只留一个结论和一张图。展开材料、演进史、反例清单见 deck-deep.html（55 页）。
全部事实核对于 2026-08-06。

你在哪，这一讲补什么

前两段解决"模型有多聪明"，这一段解决"它能用上多少"。

本讲唯一的主角其实只有一个词：ACI（Agent–Computer Interface）。 五套协议都是它的不同实现形态——差别只在"约定写在哪里"。

最关键的一句：模型从不执行

它只输出一段结构化的意图。真正跑代码的永远是你的程序。

推论：安全边界不在模型侧，在宿主侧。"让模型别删库"不是靠提示词，是靠你在执行点上不给它删库的能力。

一个 tool 的全部内容，只有三样

名字、给人（模型）看的说明、给机器看的参数约定。

{
  "name": "search_orders",
  "description": "按客户手机号或订单号查询订单。仅返回近 180 天数据；
                   查历史订单请用 search_orders_archive。",
  "input_schema": {
    "type": "object",
    "properties": {
      "phone":    { "type": "string", "description": "11 位手机号，不带国际区号" },
      "order_id": { "type": "string", "description": "形如 SO-2026-000123" },
      "status":   { "type": "string",
                     "enum": ["pending","shipped","done","refunded"] },
      "limit":    { "type": "integer", "default": 20, "maximum": 100 }
    },
    "required": []          // phone 和 order_id 给其一即可
  }
}

name

模型靠它做第一层筛选。动词+名词，别用缩写。

description

唯一能写"什么时候不该用我"的地方。
这是全部三项里影响最大的一项。

input_schema

标准 JSON Schema。enum / default / maximum 既是约束，也是免费的提示词。

MCP、Skills、CLI 最终都会汇进这个结构。看懂这一页，后面全是变体。

description 就是接口文档，而读者会猜

工具选错，九成不是模型笨，是描述没写清边界。

✕ 常见写法

"description": "查询订单信息"
  • 没说能查多久的数据 → 用户问去年的单子，它照样调，然后拿到空结果反复重试
  • 没说参数怎么组合 → 手机号和订单号都不传，或都传
  • 没说和别的工具怎么分工 → 和 search_orders_archive 混用
  • 没说失败会怎样 → 拿到报错后不知道该换工具还是换参数

✓ 好写法：把四件事写进去

  • 能力边界：能做什么，明确不能做什么
  • 触发条件：什么情况下该选我
  • 负向边界：什么情况下该选别人（点名那个工具）
  • 返回形态：返回什么，空结果意味着什么
经验法则：把它当写给新来的同事的说明，而不是写给编译器的注释。 唯一的区别是这位同事记性好、但会自作主张。
同样的道理，错误信息也是提示词。"错误" 只会让它重试； "phone 需要 11 位纯数字，你传了带 +86 的格式" 会让它下一轮就改对。

MCP 解决的是 N×M 问题

它不是新能力，是把重复的对接工作变成一次性的。

所以 MCP 的价值在生态不在技术：它本身没做任何 Tools 做不到的事， 但它让"某人写一次、所有人能用"成为可能。这类协议，赢家通吃，且只会有一个赢家。

四个实体，一张图分清

大部分 MCP 的困惑，都来自把这四个混成两个。

三个必须掰开的误解：Agent ≠ Client（Client 只是一根管子）· Server ≠ 原始服务（Server 是薄适配层）· Client 与 Server 严格一对一（接三个 Server 就有三个 Client）。

完整流程：从启动到回传

看清这张图，MCP 就没有黑箱了。

注意 B 段：无论接了几个 MCP Server，模型收到的永远是一个扁平数组。 MCP 的复杂度全部止步于 Host——这正是它和 Tools 能兼容的原因。

真实报文：一来一回

JSON-RPC 2.0。看过一次，后面读任何 MCP 文档都不费劲。

① 能力发现 · 请求
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list",
  "params": { "_meta": {
    "io.modelcontextprotocol/protocolVersion": "2026-07-28"
  } } }
② 能力发现 · 响应
{ "jsonrpc": "2.0", "id": 1, "result": { "tools": [
    { "name": "create_issue",
      "description": "在指定仓库创建 issue。",
      "inputSchema": { "type": "object",
        "properties": { "repo": {"type":"string"},
                        "title": {"type":"string"} },
        "required": ["repo","title"] } }
] } }
③ 调用 · 请求
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "create_issue",
              "arguments": { "repo": "acme/web",
                              "title": "登录页 500" } } }
④ 调用 · 响应
{ "jsonrpc": "2.0", "id": 7, "result": {
    "content": [ { "type": "text",
                  "text": "已创建 acme/web#412" } ],
    "isError": false } }
两种错误别混：
isError:true = 工具级错误（仓库不存在），要回给模型让它改；
"error":{"code":-32602} = 协议级错误（参数结构不对）， 是你的 Bug，不该指望模型修。

三大原语：按谁决定来分，不按功能分

这是理解 MCP 设计意图的关键——它在划分控制权。

Tools · 模型决定

模型看到清单后自主判断要不要调、什么时候调。

有副作用、需要门禁的东西放这里。
这是唯一一个模型有主动权的原语。

实践中 95% 的 MCP Server 只实现了 Tools——另外两个支持度远没那么普及。

Resources · 应用决定

一份可寻址的只读数据（文件、表结构、文档）。由宿主应用挑好了塞进上下文，模型不能自己去拿。

适合"背景资料"这类东西——不该让模型花一轮对话去请求它。

Prompts · 用户决定

预置的提示词模板，由用户显式触发（比如在输入框敲一个斜杠命令）。

Server 作者把"这个服务怎么用"打包成一条命令交给用户。

还有反向的三个（Server 反过来请求 Client）：
Sampling 借用模型 · Roots 问文件边界 · Elicitation 向用户追问参数。
记住这条轴：模型决定 / 应用决定 / 用户决定。 当你纠结"这个东西该做成什么"时，先问谁应该有权决定它何时出现。

2026-07-28：把状态拿掉了

现行规范。你在网上读到的多数教程停在 2025 年，已经过时。

被删掉的东西（有破坏性变更）

  • initialize 握手没了，notifications/initialized 也没了
  • 会话没了，Mcp-Session-Id 头不再存在
  • 版本号与能力声明改成挂在 _meta 上随请求带
结果：每个请求都是独立的、自包含的。 需要跨调用的状态？由 Server 自己签发句柄，当作普通工具参数传回来。

怎么解读这次转向

  • 为部署让路。无状态才能随便放在负载均衡后面、跑在 serverless 上、水平扩容。有会话的协议做不到这些。
  • 核心收紧，变化外移。同时引入扩展框架（Tasks、MCP Apps），新功能不再往主干塞。
  • 这是成熟信号，不是折腾。协议在为长期演进做准备。
最实用的一条操作建议：接入前先确认对方实现的是哪个版本。

CLI：最老、也最暴力的 ACI

你不给它十个工具，你给它一个 shell——然后整个 Unix 生态都成了工具箱。

工具定义的全部内容
{ "type": "bash_20250124", "name": "bash" }
注意：没有 input_schema，也没有 description。
接口约定去哪了？写在模型的权重里了。 模型早就在训练数据里见过几百万条 shell 命令——所以这份"文档"不需要你提供。

三条别的方案给不了的优势

  • 可组合：| && xargs 让一次调用完成多步，省下大量往返
  • 自带发现机制：模型能自己 --help / man，你不用预先描述每个能力
  • 覆盖面无限：任何装得上的命令行程序，立刻就是一个工具

代价也同样极端

  • 不可门禁：一个 bash 工具，你无法只批准"读"而拒绝"写"——命令是运行时才拼出来的
  • 难审计：日志里是一行行 shell，不是结构化的动作，事后分析非常痛苦
  • 输出吃 token：一句 cat 大文件就能把上下文冲掉
  • 提示注入面最大：读进来的文件内容里如果藏着指令，而模型手上又有 shell……
缓解手段：跑在容器/沙箱里、命令白名单或黑名单、 默认对输出做截断、危险命令走人工确认。
但请认清：这些都是补丁，不是消除。

分界线：什么时候该从 bash 升级成专用工具

这是本讲最可操作的一页。

出现这个信号就该把这个动作提升为专用工具
需要门禁——这个操作必须人工确认或权限校验专用工具的参数是结构化的，你能在执行点上精确判断
需要渲染——结果要给用户看图、看表、看 diff结构化返回值才能被前端渲染，一坨 stdout 不行
需要审计——事后要能查"谁在什么时候改了什么"工具名 + 参数天然就是审计记录
需要并行——多个同类操作应该同时发出去并行工具调用有明确语义，shell 里靠模型拼 & 不可靠
高频重复——同一串命令模型每天拼几十遍拼一次错一次的概率会累积；封装掉能显著降错误率
危险且不可逆——删除、发布、转账、发消息专用工具能做二次确认、幂等键、干跑模式
推荐路径：从 bash 起步，按日志升级。 先给最小可用的能力，观察 agent 真实怎么用、在哪反复出错， 再把那些高频动作提升为专用工具。你是在用真实数据做接口设计，而不是拍脑袋设计五十个精美工具。

三者对齐：差别只在约定写在哪里

把 Tools / MCP / CLI 放进同一个表，共通的骨架就露出来了。

ToolsMCPCLI
谁定义接口你，写在请求里Server 作者，可能是陌生人没人——约定在模型权重里
谁传输直接在 Messages 请求体中JSON-RPC over stdio / HTTP还是一个普通 tool
谁执行永远是宿主。三者完全一致，没有例外。
模型看到什么永远是同一个扁平的 tools 数组。它分不出来源，也不需要分。
发现新能力你手动加进数组tools/list 自动拉取模型自己 --help
粒度一个动作一组相关动作整个操作系统
换来的最强控制力生态复用最大表达力
付出的每个能力都要自己写依赖第三方，信任面扩大几乎放弃门禁与审计
最后两行是同一件事的两面：控制力和表达力此消彼长。 Tools 在一端、CLI 在另一端、MCP 在中间——选型的本质就是在这条轴上取一个点。

本质：全都是同一个三段式

拆到底，五套协议是同一件事的五种供货渠道。

由此得到本讲的核心概念：ACI（Agent–Computer Interface）

它既不是 API（读者是编译器，写错就报错），也不是 UI（读者是人，看得见摸得着）。 它的读者是一个会猜的概率模型——你没写清楚的部分，它一定会填一个看似合理的答案进去。

所以 ACI 设计的重点全都在「怎么让它少猜、猜错了能自己纠正」： 命名 · 粒度 · 错误信息即提示词 · 幂等 · 输出预算 · 可发现性 · 失败可恢复。

选型决策树

一个动作，到底该放在哪一层？

注意最下面那个虚线框：Skills 和其它选项不是并列关系，它是正交的一层。 前面四个决定"有什么能力"，Skill 决定"这些能力该怎么组合使用"。

Skills 管的不是"能做什么"，是"该怎么做"

前四套协议在给能力。Skills 在给用法。

它长什么样

一个文件夹，里头一个 SKILL.md，可以再带脚本和模板。就这样。

SKILL.md
---
name: quarterly-report
description: 生成季度经营报告。当用户要求出季报、
  月度经营分析，或提到"按公司模板做一份报告"时使用。
license: MIT
allowed-tools: Read, Write, Bash
---

# 季度报告生成

## 步骤
1. 从 `data/` 读取本季度的三张表
2. 用 `scripts/validate.py` 校验数据完整性
3. 套用 `templates/report.docx` 的版式
4. 数字一律保留一位小数，同比用红绿箭头标注

## 禁止
- 不要自己编造缺失月份的数据，标注为「待补」

为什么这是必要的一层

你可以把流程知识塞进 system prompt——但它每一轮都占着上下文， 而且和其它十个流程混在一起。

你也可以塞进工具的 description——但描述属于工具，不属于流程， 一个流程往往要用到五个工具。

Skills 就是把"流程知识"变成一个可独立编写、独立分发、按需加载的单元。

一句话记忆：
MCP 是"我给你一把螺丝刀"。
Skill 是"我们公司装机的标准流程是这样的"。
注意 allowed-tools：一个 Skill 可以声明自己只需要哪些工具， 这是最小权限在这一层的体现。

渐进式披露：装一百个也几乎不花上下文

这是 Skills 设计里最值得偷师的一招。

成本曲线的改变：装 N 个 skill 的常驻成本从「N × 完整内容」 变成「N × 一行描述」——接近常数。
这招在工具侧同样适用。工具太多时，用检索式加载 / 延迟加载 只把候选工具的完整 schema 送进上下文，是同一个思路。

编写要点：description 决定生死

因为它是三层里唯一会被检索到的那一层。写不好，后面两层永远不会被打开。

✕ 写成自我介绍

description: 一个强大的报告生成技能，
支持多种格式，功能丰富，易于使用。

模型读完仍然不知道什么时候该用它。 "强大""丰富""易用"对检索零贡献。

✓ 写成触发条件

description: 生成季度经营报告。当用户要求
出季报、月度经营分析，或提到"按公司模板
做一份报告"时使用。不处理财务审计报表。

动作 + 触发场景 + 用户可能的原话 + 负向边界。 四样齐了，检索命中率立刻不一样。

正文的三条写法

  • 写流程，不写背景。模型不需要知道"季报对公司很重要"， 它需要知道第三步该套哪个模板。
  • 写禁止事项。"数据缺失时标注待补，不要编造"这类约束， 比十句正面描述都管用。
  • 能给脚本就别给文字。校验逻辑写成 validate.py 直接跑， 比用自然语言描述校验规则可靠得多，也省上下文。
一个检验标准：把 SKILL.md 递给一个刚入职的同事， 他能不能照着做出合格产出？
能，模型多半也能。不能，先别怪模型。

已经发生的事

  • 从一个官方仓库，长成多个市场并存（含 Vercel 的 skills.sh、SkillsMP 等）
  • 数量从数千涨到数十万，索引量到百万级
  • 兼容产品从 Claude 一家扩展到十几到几十款（口径不同差异较大）
  • 市场开始配套安全扫描——说明大家已经意识到问题在哪

安全：把每个 skill 当不可信依赖

它能带脚本、能声明工具权限、内容会直接进入模型上下文。 一个恶意 skill ≈ 一个能对你的 agent 说话的第三方。

最低限度：只用可信来源、装之前读一遍正文和脚本、 用 allowed-tools 收紧权限、在沙箱里跑。

我的判断：已有同行评审的基准显示， 写得好的 skill 提升显著，但公开 skill 里写得好的是少数。
所以下一阶段的胜负手不是数量，是策展与信任分层—— 谁能让人放心地装，谁赢。

A2A 换了一个维度

前面全是"agent 向下够工具"。A2A 是"agent 向旁边找同类"。

那三件事是：发现（陌生的 agent 怎么找到、怎么知道它会什么）· 身份（凭什么信它）· 长任务（几小时的活怎么跟踪、怎么取消、怎么续）。 MCP 假设对面是你部署的、你信任的、会立刻返回的——跨组织时这三个假设一个都不成立。

AgentCard：一张可抓取、可验签的名片

发布在 /.well-known/agent-card.json。整个协议里唯一公开的部分。

{
  "protocolVersion": "1.0.1",
  "name": "Invoice Reconciler",
  "description": "对账 agent：把发票批次与银行流水核对，输出差异报告。",
  "url": "https://agents.acme.com/a2a/v1",
  "preferredTransport": "JSONRPC",
  "provider": { "organization": "Acme Finance" },
  "capabilities": {
    "streaming": true,           // 支持 SSE 推进度
    "pushNotifications": true    // 支持 webhook 回调
  },
  "defaultInputModes":  ["text/plain", "application/pdf"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "security": [ { "oauth2": ["invoices.read"] } ],
  "skills": [ {
    "id": "reconcile-batch",
    "name": "批量对账",
    "description": "给定发票 PDF 批次与流水 CSV，输出逐笔差异。",
    "examples": ["把这批 6 月发票和招行流水对一遍"]
  } ],
  "signatures": [ { "protected": "eyJhbGc…", "signature": "MEUCIQD…" } ]
}

这里的 skills 和幕五无关

纯属撞名。这里是"我对外宣称能干的一类活"，粒度接近服务目录条目。

examples 是写给对方模型看的

让 Client Agent 判断"我这个需求是不是它说的这种"。 又一次印证：描述和例子决定接口好不好用。

signatures 是 v1.0 的分水岭

能验证这张名片确实来自那个组织、没被篡改。
没有签名，跨组织场景根本不敢用。

defaultInputModes 用 MIME 声明收发格式—— MCP 没有这层协商，因为它默认对面是你自己装的。

Task 八态：所有复杂度都收进这台状态机

A2A 独有的核心抽象。MCP 里没有对应物。

配套方法一个不多：message/send 委派 · message/stream 流式 · tasks/get 查 · tasks/cancel 撤 · tasks/resubscribe 断线重连 · tasks/pushNotificationConfig/set 配 webhook。 长任务别轮询——在线等用 SSE，不在线用 webhook。

已经落地的

  • 2025-08 IBM 的 ACP 并入，竞争协议收敛为一个——和 MCP 那边一样，这个领域不容忍两套标准
  • Microsoft Copilot Studio、Azure AI Foundry、Amazon Bedrock AgentCore 均已 GA
  • 22,000+ GitHub stars，5 种语言的生产级 SDK
  • 配套推出 AP2（Agent Payments Protocol）——agent 之间要交易，得先能付钱

为什么你（和大多数人）还没用上

  • 你没有跨组织委派的需求。A2A 的价值出现在组织边界上；团队内部直接调用或 MCP 都更简单。
  • 接入成本高。不是协议难，是你要配套做异步任务持久化、回调接收、重试与对账——本质上等于对接一个外部工单系统。
  • 需求侧还没成熟。愿意付钱把活委派给外部 agent 的市场才刚开始。
我的判断：A2A 的协议成熟度已经领先于它的需求成熟度。 不是"要不要学"，而是"什么时候轮到你"。
触发信号很明确：当你开始需要把一件事委派给公司外部的自动化系统时。

五条能带走的判断

如果这 26 页只留五句话。

① 五套协议是同一件事的五种供货渠道

名字 + 参数约定 + 文本回执。无论走哪条路，执行权永远在宿主，模型永远只看见一个扁平数组。

② 真正的设计对象是 ACI，不是协议

选 Tools 还是 MCP 还是 bash 是次要问题。首要问题是你的接口对一个会猜的读者好不好用： 名字、粒度、错误信息、输出预算。这四样没做好，换任何协议都救不了。

③ 从 bash 起步，按日志升级

先给最小可用的能力，看它真实怎么用、在哪反复出错，再把高频动作提升为专用工具或写成 Skill。 这是用真实数据做接口设计。

④ 能力和用法要分开供给

MCP 给能力，Skills 给用法。渐进式披露让"装很多东西"从线性成本变成接近常数—— 这个思路在工具侧同样适用。

⑤ 协议在动，判断要带日期

MCP 现行版 2026-07-28 已删掉握手和会话；A2A 已交给 Linux Foundation 并发到 v1.0.x。 网上多数教程停在 2025 年。接入前先确认对方的协议版本。
