五个名字，一件事——给一个概率模型设计一个它能用得对的接口。

ACI · Agent-Computer Interface

面向 LLM 的接口层。不是给编译器看的 API，也不是给人看的 UI， 而是给一个会读文档、会猜、会出错的概率模型看的接口。

为什么必须单列一层

  • API 的读者不会误解参数名；模型会。
  • UI 的使用者能看见反馈；模型只能看见你返回的那段文本。
  • API 报错给堆栈；给模型报错要给下一步该怎么做。
协议它其实在回答哪个问题
Tools模型怎么说出"我要调用某个函数"
MCP这些函数怎么不写死在你的宿主里
CLI能不能干脆把整台机器给它
Skills怎么告诉它该怎么用，而不只是能用什么
A2A对面不是工具、是另一个 agent 时怎么办

从"只会说话"到"能做事"

工具调用不是模型的新能力，是输出格式的一次约定。

没有工具时

用户：帮我查一下北京天气

模型：（它不知道，只能编或者认怂）
      抱歉，我无法获取实时天气信息。

模型的全部输出就是文本。它无法发起任何副作用。

有工具时

用户：帮我查一下北京天气

模型：（它仍然只是输出文本，但这段文本
       被约定成一个结构化的调用请求）
{"type":"tool_use", "name":"get_weather",
 "input":{"city":"北京"}}

模型依然没有执行任何东西。它只是说出了一个请求。

这就是全部魔法。Function Calling / Tool Use 不是给模型装了手， 是训练它把"我想调用 X"这句话说成一个能被程序解析的格式—— 并且训练它在合适的时候才说。手，始终长在你的代码上。

① 你声明

把可用工具的名字、用途、参数形状随请求一起发给模型。

② 它选择

模型判断该不该用、用哪个、参数填什么，输出 tool_use。

③ 你执行

你的代码真正去调 API / 读文件 / 跑命令，把结果作为下一轮输入喂回去。

一个 tool 的真实长相

三个字段：name 是标识，input_schema 是契约，description 是说明书——而说明书最重要。

request · tools[0]
{
  "name": "search_orders",
  "description": "按条件检索订单。用于回答『我的订单在哪』"
                 "『上个月买了什么』这类问题。只读，不会修改数据。"
                 "一次最多返回 20 条，需要更多请用 cursor 翻页。",
  "input_schema": {
    "type": "object",
    "properties": {
      "user_id":  { "type": "string", "description": "内部用户 ID，形如 u_8f21" },
      "status":   { "type": "string", "enum": ["paid","shipped","refunded"] },
      "since":    { "type": "string", "format": "date", "description": "YYYY-MM-DD" },
      "cursor":   { "type": "string", "description": "上一次返回的 next_cursor" }
    },
    "required": ["user_id"]
  }
}

input_schema

标准 JSON Schema。它同时是两件东西：给模型的提示， 和给你自己的校验。enum 比 description 里写"只能填三个值"有效得多。

description

唯一被模型反复读的字段。它决定的不是"怎么调"，而是 "什么时候该调"——绝大多数工具误用，根子在这里。

注意

schema 是建议不是保证：模型仍可能少填必填项、把日期写成 "上个月"。执行前必须自己校验。

一次完整往返：谁在什么时候动

四个参与者，两次模型调用，中间那段执行完全属于你。

注意第 3 步到第 5 步：模型下线了。它既不知道你怎么执行的，也无法阻止你不执行。 整条链路上唯一有权限的实体，是中间那个橙色的宿主程序。

最容易搞错的一件事：模型从不执行

这句话你现在觉得是废话。它会在 MCP、CLI、A2A 三章里各救你一次。

✕ 常见误解

  • "模型调用了数据库"
  • "给模型开了删除权限"
  • "MCP 让模型连上了 GitHub"
  • "agent 自己跑了 rm -rf"

✓ 准确说法

  • 模型请求调用，宿主执行
  • 权限开在宿主的凭证上
  • MCP 客户端连上了 GitHub
  • 宿主替 agent 跑了 rm -rf

为什么必须较真

因为所有安全设计都落在这个区分上。你能拦截的位置只有一个： 模型说完、你动手之前的那一瞬间。

由此推出的三条工程结论

  • 门禁点只有一个。不要试图用 prompt 让模型"不要删库"——要在执行器里不给它删库的凭证。
  • 幻觉参数是常态。模型会填出不存在的 user_id。执行器要把校验失败作为一条工具结果返回，而不是抛异常终止。
  • 回执即上下文。你返回什么，模型就只知道什么。返回 {"ok":true} 等于什么都没说。
好的错误回执：把失败变成下一步的提示
{ "type": "tool_result",
  "tool_use_id": "toolu_01A…",
  "is_error": true,
  "content": "user_id 'u_月光' 不存在。"
             "user_id 必须形如 u_xxxx（4 位十六进制）。"
             "若只知道用户名，请先调用 lookup_user。" }

// 对比：下面这种回执让模型只能干瞪眼
// { "is_error": true, "content": "400 Bad Request" }

你能施加的控制：tool_choice

从"完全放手"到"必须调这一个"，四档。它不是优化项，是流程控制手段。

取值行为什么时候用
{"type":"auto"}模型自己决定调不调、调几个（默认）对话式 agent 的常态
{"type":"any"}必须调工具，但调哪个由模型定路由分发：这一轮不许闲聊
{"type":"tool",
 "name":"x"}		强制调用指定的那一个把工具当结构化输出用：让模型必须按 schema 填表
{"type":"none"}本轮禁止调用任何工具收尾轮：只让它总结，别再动手
disable_parallel_tool_use: true 可以把一轮多个 tool_use 压回一次一个—— 当工具之间有顺序依赖或写操作不可并发时必须打开。

被低估的用法：拿工具做 schema 约束

强制调用一个只用来"填表"的假工具，是让模型输出严格结构化 JSON 最古老也最稳的手段——它走的是训练过的 tool_use 通道， 比"请只输出 JSON"这种祈使句可靠得多。

一轮多调用

模型可以在一条回复里发出多个 tool_use。宿主应当并行执行、 把多个 tool_result 放进同一条 user 消息里回去。 漏掉任何一个 tool_use_id 的回执，请求会直接报错。

顺序陷阱：并行执行意味着模型没法保证"先查库存再下单"。 有依赖就关并行，或者干脆把两步合并成一个工具。

description 就是接口文档，读者是模型

同一个函数，换个描述，调用准确率能差出一个量级。

✕ 反例
"name": "query",
"description": "查询数据"
  • 名字没有语义，和别的工具区分不开
  • 没说查什么数据、什么时候该查
  • 没说边界：能不能写？会不会很慢？
  • 没说失败长什么样
✕ 另一种反例：写给人看
"description": "本接口由订单中台 v3 提供，"
  "遵循 RESTful 规范，QPS 限制见 wiki。"

全是模型用不上的信息，纯占 token。

✓ 正例
"name": "search_orders",
"description":
  "按条件检索某个用户的订单。"          ← 做什么
  "当用户问『我的订单』『买过什么』"
  "『退款到了没』时使用。"              ← 何时用
  "只读，不修改任何数据。"              ← 边界
  "一次最多 20 条，更多请用 cursor。"    ← 限制
  "查不到会返回空数组，不是错误。"       ← 失败语义
  "不要用它查退款进度，那个用 "
  "get_refund_status。"                 ← 负向边界
负向边界（"不要用它做 X，那个用 Y"）是最容易被忘、收益最大的一句。 工具越多越关键。
一条检验标准：把 description 单独拿给一个没见过你系统的人看，他能不能判断"这个场景该不该用它"。 不能，模型也不能。

工具变多以后：上下文是有预算的

每个工具定义都常驻上下文。100 个工具可能吃掉几万 token，而且会互相干扰。

问题一 · 占地

工具定义在每一轮都要重发。一个中等复杂的工具约 150–400 token， 50 个就是一两万——还没开始对话就烧掉了。

问题二 · 干扰

功能相近的工具越多，选错的概率越高。准确率随工具数下降， 这是比成本更硬的约束。

问题三 · 僵化

工具列表通常在请求开始时就固定了，会话中途想加一个新工具， 传统做法只能重开一轮。

解法一 · 延迟加载 + 工具检索

把工具标记为"不默认加载"，只把一个检索工具放进上下文。 模型先描述自己想干什么，检索工具按名称正则或 BM25 把匹配的几个工具 临时注入，再正常调用。

代价：多一轮往返。收益：工具库可以做到成百上千个。

解法二 · 会话中途增删工具

允许在对话进行到一半时追加或移除工具定义，并且用一个"引用"占位符 指向前面已经发过的定义——避免每轮重发全量 schema，保住提示缓存不失效。

这对长会话尤其重要：缓存一旦被工具列表变动打断，成本会突然翻倍。

解法三 · 别做那么多工具

很多"工具"其实是同一个工具的不同参数。把 20 个 get_* 合并成 1 个带 resource 枚举的工具，通常比任何检索机制都有效。

这条会在 ACI 那一幕展开：粒度是 ACI 设计的第一难题。

幕一验收：Tools 讲清了什么

回到开场那张表的第一行。

Tools 回答的问题：模型怎么说出"我要调用某个函数"。
答案：约定一种输出格式（tool_use），并约定一种回灌格式（tool_result）， 用 tool_use_id 把两者配对。仅此而已。

它没有回答的问题

  • 工具定义从哪来？——现在只能硬编码在宿主里。→ MCP
  • 工具该怎么用（多步流程、组织规范）？→ Skills
  • 如果对面不是函数、是另一个 agent？→ A2A
你必须记住的五件事
① 模型只发起，宿主执行。门禁只有这一个位置。
② description 决定"何时调"，input_schema 决定"怎么调"。前者更重要。
③ 回执就是模型接下来的全部认知。错误回执要写成行动建议。
④ tool_choice 是流程控制手段，不是调优旋钮。
⑤ 工具数量有上下文与准确率的双重代价。合并 > 检索 > 硬塞。

MCP 要解决的是 N × M

不是"让模型能用工具"——那 Tools 已经解决了。是"让工具不必为每个宿主重写一遍"。

这是一个纯粹的工程动机，不是模型能力的进步。MCP 常被类比成"AI 世界的 USB-C"—— 类比成立的部分是统一插口；不成立的部分是，USB-C 传的是电和数据， MCP 传的是模型能读懂的语义，所以描述写得好不好仍然决定成败。

三个必须掰开的误解

这三句话讲错了，后面的时序图就全是糊的。

误解一：Agent 就是 MCP Client

错在哪：Agent 是"模型 + 循环"，它输出的是 tool_use， 用的是普通工具调用格式。它从不发 JSON-RPC。

正确关系：Client 是宿主里的传输层组件。 宿主把 Client 拿回来的工具列表拍平进 tools[] 给模型， 模型选了之后，宿主再让 Client 发出 tools/call。

误解二：MCP Server 就是那个服务

错在哪："GitHub MCP Server" 不是 GitHub。它是一个适配器进程—— 很可能就跑在你自己的笔记本上，靠你的 PAT 去调真正的 GitHub API。

为什么重要：因为出问题时你要知道该查哪一层： 是适配器的工具描述写得烂（模型选错），还是原始 API 报错（适配器转发了错误）， 这是两类完全不同的故障。

误解三：一个 Client 可以连很多 Server

错在哪：协议规定的是一对一：一个 Client 实例 ↔ 一个 Server。 宿主接三个服务，就在自己内部起三个 Client。

由此产生的真实工程问题：三个 Server 各自声明的工具会重名 （都叫 search）。宿主必须自己做命名空间前缀， 否则模型和你都分不清调的是哪个。

一句话记法：Agent 决定做什么，Client 负责怎么送，Server 负责怎么翻译，原始服务负责真的干。 四个动词分给四个实体，不重不漏。

两种传输：本地子进程 vs 远端 HTTP

同一套 JSON-RPC 报文，两种送法。选哪种，决定了部署形态和安全模型。

stdio · 本地子进程

  • 零网络、零鉴权，天然只有本机能连
  • 凭证靠环境变量传给子进程
  • 生命周期 = 宿主生命周期，宿主退出就没了
  • stderr 千万别写日志到 stdout——会污染协议流，这是最经典的 MCP bug

Streamable HTTP · 远端服务

  • 可以多用户共享一个 Server 实例
  • 鉴权走标准 OAuth，token 刷新由 Client 管
  • 能被普通 HTTP 基础设施（网关/CDN/负载均衡）承载
  • 2026-07-28 起：协议级 session 与 Mcp-Session-Id 被移除， 路由信息镜像到 HTTP 头——就是为了让上面这句话真正成立

完整时序：从启动到拿到结果

五个实体，三个阶段。看清楚每一步的发起方是谁。

真实报文（一）：能力发现

JSON-RPC 2.0，一问一答。注意 inputSchema 的驼峰写法——和 Anthropic API 的 input_schema 不是一回事。

→ Client 请求（2026-07-28 无状态风格）
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "_meta": {
    "io.modelcontextprotocol/protocolVersion": "2026-07-28",
    "io.modelcontextprotocol/clientCapabilities": {
      "roots": { "listChanged": true },
      "sampling": {}
    }
  }
}
变了：旧版本要先发 initialize 握手、再发 notifications/initialized， 之后才能问工具。新版本没有握手——协议版本和客户端能力挂在每一条请求的 _meta 里。这是无状态化改造的核心。
← Server 响应
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "tools": [
      {
        "name": "search_issues",
        "title": "搜索 Issue",
        "description": "在指定仓库中按 GitHub 搜索语法"
                       "检索 issue。只读。",
        "inputSchema": {
          "type": "object",
          "properties": {
            "repo":  { "type": "string", "description": "owner/name" },
            "query": { "type": "string" }
          },
          "required": ["repo", "query"]
        }
      }
    ]
  }
}
看到了吗——Server 返回的东西，和你手写一个 tool 定义几乎一模一样。 MCP 没有发明新的工具模型，它只是把"工具定义从哪来"这件事从编译期挪到了运行期。

真实报文（二）：一次调用

注意错误的两种表达方式——它们的语义完全不同。

→ tools/call
{
  "jsonrpc": "2.0", "id": 2,
  "method": "tools/call",
  "params": {
    "name": "search_issues",
    "arguments": {
      "repo": "acme/web",
      "query": "is:open label:bug"
    }
  }
}
← 成功
{
  "jsonrpc": "2.0", "id": 2,
  "result": {
    "content": [
      { "type": "text", "text": "找到 3 条：\n#812 登录超时…" }
    ],
    "isError": false
  }
}
← 工具级错误（业务失败）
{
  "jsonrpc": "2.0", "id": 2,
  "result": {
    "content": [{ "type": "text",
      "text": "仓库 acme/web 不存在或无权限。"
              "请先用 list_repos 确认仓库名。" }],
    "isError": true
  }
}

会被送回模型，模型可以据此改参数重试。 这是给模型看的。

← 协议级错误（调用本身非法）
{
  "jsonrpc": "2.0", "id": 2,
  "error": { "code": -32602,
             "message": "Unknown tool: serch_issues" }
}

不该原样丢给模型。 这是给宿主看的——说明宿主的路由或工具清单出了 bug。

分清这两种错误，是写 MCP Server 时最常翻的车。 把"仓库不存在"报成 -32602，模型就失去了自我修复的机会； 把"工具名拼错"塞进 isError，你就永远发现不了宿主的 bug。

三大原语：按谁来决定分层

这是理解 MCP 设计最快的一刀。不是按"数据类型"分，是按"控制权在谁手上"分。

Tools · 模型决定

model-controlled

模型自己判断该不该调、什么时候调。有副作用，可以写数据。

例：create_issue、run_query、send_message

正因为模型决定，宿主必须提供确认机制。写操作无人值守自动执行，是事故的标准起点。

Resources · 应用决定

application-controlled

由宿主决定把哪些内容放进上下文。只读、无副作用，用 URI 标识。

例：file:///repo/README.md、db://schema/orders

它更像"附件"而不是"函数"。很多客户端对 Resources 的支持弱于 Tools—— 这是 MCP 生态里最不均衡的一块。

Prompts · 用户决定

user-controlled

Server 预置的提示词模板，由用户显式触发（斜杠命令、菜单项）。

例：/review-pr、/explain-schema

它是 Skills 的前身思路：把"该怎么用这些工具"打包起来。 差别在于 Prompts 由用户主动挑，Skills 由模型按需取。
记忆锚点：模型决定的叫 Tools，应用决定的叫 Resources，用户决定的叫 Prompts。 任何时候拿不准某个能力该做成什么，先问"这件事该由谁拍板"。

反向的三个原语：Server 也能提要求

MCP 不是单向的 RPC。Server 可以回头找 Client 要能力——这是它区别于普通 REST 网关的地方。

Sampling · Server 借用模型

Server 在处理请求时可以反过来请求 Client："帮我调一次模型"。 于是 Server 自己不需要持有任何 API Key，也不需要绑定某个模型厂商。

典型场景：一个数据库 Server 要把自然语言转成 SQL， 它把这个子任务丢回给宿主的模型去做。

代价：Client 必须替用户把关——这是"我的 token 被别人花掉"的路径。 规范要求这里有人在环。

Roots · Client 告诉 Server 边界

Client 声明"你只能在这些目录/URI 范围里活动"。这是文件系统类 Server 的 沙箱边界声明，也是少数由 Client 主动推给 Server 的信息。

Elicitation · Server 向用户追问

Server 发现信息不够时，可以请求 Client 弹一个表单问用户， 而不是猜一个参数或者直接报错。

典型场景："要往哪个环境部署？" —— 这种问题 既不该让模型猜，也不该在工具 schema 里硬塞。

为什么这三个原语值得单独记：
它们说明 MCP 的设计目标不是"远程函数调用"，而是让第三方能力能安全地嵌进一个有人参与的会话。 Sampling 借算力、Roots 划边界、Elicitation 借用户注意力——三件事都绕不开宿主， 宿主始终是唯一的信任中心。

关键一页：MCP 最终还是拍平成 tools

如果这一幕你只带走一张图，带走这张。它把幕一和幕二焊在一起。

推论一：MCP 帮不了你"工具太多"的问题。六个 Server 接进来就是几十个工具， 全都常驻上下文。幕一讲的合并、检索、延迟加载在这里同样适用，而且更紧迫。
推论二：Server 的 description 写得烂，你在宿主侧几乎无法补救—— 因为那段文字是它给的。挑 MCP Server 时，看它的工具描述，比看它的 star 数有用。

规范演进：它一直在动

MCP 用日期做版本号。你手上的教程属于哪一版，直接决定它有没有过期。

为什么这页值得单独讲

  • 2024-11 到 2026-07，不到两年五个修订版，其中至少两次动了传输层。
  • 网上绝大多数"MCP 教程"写于 2025 年上半年——它们教的 initialize 握手流程 在现行版里已经不存在了。
  • SDK 分层跟进：Tier 1 SDK 在发布前有约十周的窗口期做适配， 但社区 Server 的更新会慢得多。

实践建议

  • 接入前先确认对方 Server 声明的协议版本，别假设。
  • 自己写 Server，优先用官方 SDK 而不是手搓 JSON-RPC—— 传输层的变更由 SDK 吸收掉。
  • 把"协议版本"当成依赖版本来管理：写进文档，纳入回归测试。

下一页看现行版到底改了什么。

2026-07-28：把状态从协议里拿掉

维护者称这是"自加入授权以来最大的一次改动"。它的动机全都指向同一件事：让 MCP 能跑在普通 HTTP 基础设施上。

① 握手没了

initialize / notifications/initialized 被移除。 协议版本与客户端能力改为挂在每一条请求的 _meta 上 （io.modelcontextprotocol/protocolVersion、…/clientCapabilities）。

② 会话没了

协议级 session 与 Mcp-Session-Id 头从 Streamable HTTP 中移除。 需要跨调用状态的 Server，改为自己签发句柄，当作普通工具参数传来传去。

③ 列表结果可缓存

tools/list 等不再随连接变化，因此可以被缓存、被 CDN 承载。

④ 路由信息上到 HTTP 头

过去操作名埋在 JSON-RPC 请求体里，网关必须拆包才知道这是什么请求。 现在路由信息镜像到 HTTP header，负载均衡和网关可以直接按头转发。

⑤ MRTR · 多轮往返请求

为 server → client 的交互（如 Sampling、Elicitation）提供了统一的多轮模式。

⑥ 扩展框架 + 弃用政策

正式确立扩展机制，Tasks（长任务）与 MCP Apps（服务端渲染 UI） 作为扩展存在，而非塞进核心。同时给出了正式的弃用流程。

这是破坏性变更。老 Client 连新 Server、或反过来，都可能直接连不上。 迁移不是"改几个字段"，是状态管理策略的重写。

该怎么理解这次转向

MCP 最初的形态是本地长连接思维（stdio 子进程、有状态会话）， 这在一台笔记本上很自然。

但当 Server 要托管在云上、要服务成千上万用户、要过网关和负载均衡时， 有状态就是原罪。这次改动本质上是 MCP 从"本地插件协议" 正式转型为"互联网协议"。

代价是把状态管理的复杂度推给了 Server 作者—— 句柄的签发、过期、鉴权，现在都是业务代码的事。

幕二验收：MCP 的位置与判断

数据截至 2026-08。

MCP 回答的问题：工具定义从哪来。
答案：从一个运行期发现的第三方进程来。它把 N×M 变成 N+M， 代价是多了一层需要信任的中间人。

它没有改变的事

  • 模型看到的仍然是扁平的 tools[]
  • 工具太多仍然烧上下文、仍然会选错
  • 描述写得烂仍然没救
  • 执行权和凭证仍然完全在宿主手上

生态现状

  • Tier 1 SDK 月下载量接近五亿量级，TypeScript 与 Python SDK 累计下载均已破十亿。
  • 各主流 IDE、终端 agent、桌面客户端普遍内置 MCP Client。接入侧已经赢了。
  • Server 侧质量分化极大：官方与头部厂商的 Server 可用，长尾 Server 的工具描述常常不合格。

我的判断

  • MCP 已经赢下"接口标准"这一仗，不会再有第二个竞争协议了。
  • 下一阶段的竞争在分发与信任：谁来审核 Server、谁来托管、谁来管凭证。 这和后面 Skills 那一幕会遇到完全一样的问题。
  • 2026-07-28 的无状态化，是它从"开发者玩具"走向"生产基础设施"的分水岭。

最老、也最暴力的一种接口

你可以花三个月给模型封一百个工具。或者，你可以把 bash 给它。

一次交付，全部到位

给模型一个能执行 shell 命令的工具，你等于一次性给了它： git grep curl jq psql ffmpeg docker python …以及机器上装的每一个命令。

而且这些命令的用法，模型在预训练里早就见过几百万遍。 你不需要写任何 description，它比你更懂 git rebase 的参数。

关键洞察：CLI 是唯一一种模型已经预先学会的接口。 你自定义的 search_orders 它是第一次见；ls -la 它见过一辈子。 Unix 四十年的接口设计，白送给你当 ACI 用。
同一件事：三种接口，三种代价
// 方案 A：专用工具（你得先写它）
{ "name": "count_todo_comments",
  "input_schema": { "properties": { "dir": {…} } } }

// 方案 B：MCP（你得先找到/搭起一个 Server）
tools/call { "name": "fs__grep",
             "arguments": { "pattern": "TODO", … } }

// 方案 C：bash（你什么都不用写）
grep -rn "TODO" src/ | wc -l

// 而且模型还能自己想出这种你没预料到的组合：
git log --since="1 month ago" --name-only \
  | grep -c "^src/.*\.ts$"

方案 C 的表达力是无限的，因为它可组合。 A 和 B 的表达力等于你写过的那些函数。

一个没有 schema 的工具长什么样

最能说明"ACI ≠ API"的一个例子：接口约定不在 JSON 里，在模型的记忆里。

普通自定义工具
{
  "name": "run_shell",
  "description": "在项目目录执行一条 shell 命令…",
  "input_schema": {
    "type": "object",
    "properties": { "command": { "type": "string" } },
    "required": ["command"]
  }
}

你自己封的：得写描述、写 schema， 模型对它的理解全靠你这几句话。

厂商预置的 bash 工具
{
  "type": "bash_20250124",
  "name": "bash"
}

// 完。没有 description。
// 没有 input_schema。
// 文本编辑器工具同理：
{ "type": "text_editor_20250728", "name": "str_replace_based_edit_tool" }

接口约定已经被训进模型里了。 你只是打开一个开关，告诉它"这个能力现在可用"。

这件事的含义比它看起来大

schema 的作用是把约定告诉模型。当约定已经在模型的权重里时，schema 就是冗余的。

换句话说：一个接口好不好用，取决于模型对它有多熟， 而不取决于它的定义有多严谨。这是 ACI 和 API 最根本的分歧。

推论：优先复用模型已经熟悉的形状

  • 参数命名向 Unix / 主流 SDK 靠拢，别自创缩写
  • 路径就用路径，别发明 resource_locator
  • 时间就用 ISO 8601，别用自家的时间戳格式
  • 返回值向常见命令的输出靠拢（表格、JSON、diff）

每一次"标新立异"，都是在让模型多猜一次。

CLI 强在哪：三个别的接口给不了的性质

这三条解释了为什么最强的编码 agent 几乎都重度依赖 shell。

① 可组合

管道、重定向、&&、子 shell——把 N 个命令拼成一个原子操作。

cat access.log \
  | awk '{print $7}' \
  | sort | uniq -c \
  | sort -rn | head -20

一次工具调用，五步计算。用专用工具做同样的事， 需要五次往返、五轮模型推理、五份中间结果占上下文。

② 自带发现机制

模型不确定用法时，可以自己去问：

ffmpeg -h full | head -50
git rebase --help
mytool --version
jq --help

这是别的接口完全没有的能力。 tools[] 是静态的，模型只能读你给的那段描述； 而 CLI 世界里，文档就在现场。

连你自己写的内部脚本，只要支持 --help， 模型就能现学现用。

③ 可迭代、可自我修正

命令失败会返回真实的错误文本——编译器报错、stack trace、 command not found。

$ tsc --noEmit
src/api.ts(42,7): error TS2345:
  Argument of type 'string' is not
  assignable to parameter of type 'number'.

这段文本对模型来说是极高质量的行动指引： 文件、行号、原因、期望类型全都有。

回想幕一那条原则——"错误回执要写成行动建议"。 Unix 工具早就替你写好了。

把这三条合起来看：CLI 之所以强，不是因为它功能多， 而是因为它同时提供了执行、文档和反馈——一个自洽的闭环环境。 这才是"给 agent 一台电脑"和"给 agent 一堆函数"的真正差别。

CLI 的代价：全部来自同一个原因

它是一个不透明的黑箱入口。你交出去的不是一个函数，是一个字符串解释器。

不可门禁

你怎么判断 bash "curl … | sh" 该不该批准？ 要真正判断，你得写一个 shell 解析器。

白名单命令名没用——git 可以 -c core.pager='sh -c …'。

不可审计

日志里只有一行命令字符串。它到底改了什么文件、发了什么请求、 删了什么数据，事后无法从调用记录还原。

输出不可控

一条 cat 可能吐出 50 万 token 直接爆上下文； 一条 find / 可能跑十分钟。没有天然的分页和预算。

环境依赖

模型以为有 jq，机器上没有；以为是 GNU sed，实际是 BSD sed。 失败率高度依赖环境一致性。

缓解手段（都不彻底，但都必要）

  • 沙箱：容器 / VM / 受限用户，只挂载该挂载的目录。这是唯一真正有效的一条。
  • 网络隔离：默认禁网，按域名放行。挡住绝大多数外传路径。
  • 输出截断：统一给 stdout 加上行数与字节上限，超了就截断并明确告诉模型被截断了。
  • 只读镜像 + 可写工作区：让"搞坏了"变成"重建容器"。
  • 危险模式匹配：拦 rm -rf / 这类。把它当成防手滑，不要当成安全边界。

一个必须想清楚的问题

如果 agent 处理的内容来自外部（网页、邮件、issue、PDF）， 那么那些内容里的文字，可能就是给 agent 的指令。

此时 shell 权限意味着：任何能往你 agent 的上下文里塞一段文字的人， 都拥有了你机器上的一次命令执行机会。

这不是理论风险。"能读外部内容" + "能执行命令" + "能联网" 三者同时具备时，必须假设最坏情况。三者去掉任意一个，风险都会数量级下降。

分界线：什么时候该把动作升级成专用工具

不是二选一。真实系统里两者共存，问题只是"这一个动作放在哪边"。

如果这个动作需要…那就做成专用工具
门禁 · 要人工确认或按策略拒绝专用工具的参数是结构化的，你才能写出 "金额 > 1000 需确认"这种规则
渲染 · 结果要给人看UI 要展示 diff、表格、图表，就需要稳定的结构化返回， 而不是一坨 stdout
审计 · 事后要能追溯"谁在什么时候改了哪条记录"必须从调用参数里读出来
并行 · 要同时跑很多次结构化调用才能安全地并发、去重、限流
高频 · 每个会话都要用几十次专用工具省 token、省推理、少出错
危险 · 错了不可逆把危险动作从 shell 里拿走，收进一个能加护栏的窄接口

反过来：这些情况就交给 bash

  • 长尾、一次性的操作——你不可能预见所有需求
  • 需要多步组合才能完成的探索性任务
  • 已有成熟 CLI 且模型很熟悉的领域（git、包管理、构建）
  • 只读的探查类操作（看日志、统计、找文件）
一条实用启发式：
先给 bash，观察 agent 真实的使用日志。 哪条命令模式反复出现、或者反复出错，就把那一条升级成专用工具。
这比一开始拍脑袋设计工具集有效得多——因为你在用真实数据做接口设计。
幕三验收：CLI 回答的问题是"能不能干脆把整台机器给它"。 答案是能，代价是你把门禁、审计、预算三件事一起交了出去。 要拿回哪一件，就把对应的动作提升为专用工具。

拆到底：全都是同一个三段式

名字 + 参数约定 + 文本回执。差别只在于——约定写在哪里。

Tools：约定写在请求里

每一轮都随请求发过去。好处是精确可控，代价是常驻上下文、随工具数线性增长。

MCP：约定写在对端

运行期去问 Server 要，再拍平进请求。好处是解耦，代价是描述质量不由你控制。

CLI：约定写在模型脑子里

零传输成本、零维护成本。代价是你对它的行为零控制力——你只能约束环境。

于是"选哪个协议"这个问题，可以被翻译成一个更清楚的问题： 这次调用的约定，我希望写在哪里？要控制力就写进请求，要解耦就写在对端，要表达力就交给模型的记忆。

ACI：为一个会猜的读者设计接口

Agent-Computer Interface。名字是仿 API / UI 造的，但它的设计约束和两者都不一样。

API · 读者是编译器

  • 读者不会误解参数名
  • 类型错了直接报错，没有中间态
  • 文档写不写，程序照跑
  • 设计目标：严谨、稳定、可版本化

UI · 读者是人

  • 读者会看见反馈、会探索
  • 能撤销、能重来、能问同事
  • 有视觉层级、有渐进引导
  • 设计目标：可发现、可理解、可挽回

ACI · 读者是概率模型

  • 它会误解参数名，而且不报错，是合理地猜错
  • 它只能看见你返回的那段文本，别的一无所知
  • 它的注意力有预算，你的每个字都在花钱
  • 设计目标：难以用错、错了能自己纠正

为什么"好 API"往往是"坏 ACI"

  • 正交、原子的 API 很优雅，但会让模型需要 6 次调用才能完成一件事—— 每次都可能出错，错误率是乘起来的。
  • 严格的类型和 ID 对程序友好，对模型是灾难：它手上只有"张三的订单"， 没有 u_8f21。接受人类可读的输入比要求 ID 更符合 ACI。
  • 简洁的错误码对程序足够，对模型等于零信息。

一个判断 ACI 好坏的实验

把你的工具集交给一个新来的实习生，只给他这些工具的 name / description / schema，不给他任何别的文档，让他完成一个真实任务。

他卡在哪、猜错什么、需要问你什么——模型会在完全相同的地方卡住。

区别只有一个：实习生会来问你，模型不会。它会自信地猜一个，然后继续往下走。

ACI 设计七条

这七条对自定义工具、MCP Server、CLI 包装器同样适用——因为它们本来就是同一件事。

① 命名即提示

search_orders_by_user 好过 query。 名字是模型选工具时读的第一个字段，也常常是唯一读完的字段。 同一个前缀表示同一个域（github__*）。

② 粒度按任务切，不按资源切

不要为了正交把一件事拆成六个调用。一次调用完成一个用户会说出口的动作。 "把这个 PR 合了"应该是一个工具，而不是 get-branch → check-status → merge → delete-branch。

③ 错误信息就是提示词

报错时回答三件事：哪里错了、正确格式是什么、下一步该调什么。 把校验失败当成一次教学机会，而不是一次异常。

④ 幂等与可重试

模型会重试，会重复调用，会在超时后再来一次。 写操作要么幂等，要么支持幂等键，否则你会收到三张一样的工单。

⑤ 输出有预算

永远给返回值设上限，并在截断时明说："共 1284 条，此处显示前 20 条， 用 cursor=… 继续"。沉默的截断会让模型以为自己看到了全部—— 这是最隐蔽的一类错误。

⑥ 可发现性

让模型有办法自己搞清楚：枚举值放进 schema、提供 list_* 类的探查工具、 支持 --help。能自己查，就不会瞎猜。

⑦ 失败可恢复

设计时假设每一步都会失败一次。中间状态要能查询、要能回滚， 长流程要能从断点续。别设计出"错一步就得从头再来"的接口。

七条压成一句：让正确的用法成为最容易猜到的那一种，让错误的用法立刻给出可执行的下一步。

选型决策树：这个动作该放哪

Skills 管的不是"能做什么"，是"该怎么做"

前三幕都在解决"给它什么能力"。这一幕解决一个完全不同的问题。

一个真实的困境

你给了 agent 完整的工具集：能读文件、能查数据库、能发邮件、能跑命令。 然后你让它"出一份季度合规报告"。

它能做到吗？工具上没有任何障碍。 但它不知道：

  • 你们公司的报告模板长什么样
  • 数据要从哪三个系统拉、以哪个为准
  • 哪些字段必须脱敏
  • 做完要发给谁、抄送谁

这些不是能力问题，是知识问题。

三种把这些知识塞进去的办法

写进 system prompt 永远占着上下文。十个流程就是一篇长文，还会互相干扰。
做成工具 但它不是一次调用，是一套流程。硬封成工具就成了黑箱，agent 无法参与判断。
做成 Skill 一个文件夹：一句话摘要常驻上下文，正文按需读入。用到才花钱。
一句话定义：Skill 是一个装着说明书（外加可选脚本和资源）的文件夹， agent 平时只知道它存在和它管什么，真正需要时才把内容读进来。
它和 MCP 的关系不是竞争：MCP 给能力，Skills 给用法。 一个 Skill 完全可以在正文里写"第一步调用 github__search_issues"。

SKILL.md 的真实长相

一个文件夹 + 一个 Markdown 文件 + 一段 YAML frontmatter。简单到有点反高潮。

SKILL.md · 正文
# 季度合规报告

## 何时使用
用户要求季报 / 合规报告时。若只是查单条数据，
不要用本 skill，直接查库即可。

## 步骤
1. 确认季度区间。跨年时以财年为准（4 月起）。
2. 运行 `scripts/pull_data.py --q <季度>`，
   它会从 A/B/C 三个系统拉数并合并。
   口径冲突时一律以 A 系统为准。
3. 按 `reference/template.md` 排版。
4. 对照 `reference/fields.csv` 逐列脱敏。
   这一步不可跳过，漏一列就是事故。
5. 产出 PDF，附上数据快照的 md5。

## 交付
发给合规组，抄送财务负责人。不要直接发给外部。
注意正文的写法：全是流程和禁忌，没有一句在解释"什么是合规报告"。 背景知识模型自己有，它缺的只是你们家的规矩。

核心机制：渐进式披露

这是 Skills 唯一真正的技术点，也是它能规模化的原因。

为什么这个机制重要：它让"给 agent 装很多东西"这件事从线性成本变成了接近常数成本。 装 200 个 skill，静态开销仍然只有那 200 行 description。 这是 Skills 能形成"应用商店"形态的技术前提。

Skills 在 API 上的形态

Skill 要执行脚本，就得有地方执行。所以它天然和"代码执行沙箱"绑在一起。

请求：挂载一个 skill 并给它一个可执行环境
{
  "model": "claude-opus-5",
  "container": {
    "skills": [
      { "type": "anthropic", "skill_id": "pptx", "version": "latest" },
      { "type": "custom",    "skill_id": "quarterly-report", "version": "3" }
    ]
  },
  "tools": [
    { "type": "code_execution_20260521", "name": "code_execution" }
  ],
  "betas": ["code-execution-2025-08-25", "skills-2025-10-02"],
  "messages": [{ "role": "user", "content": "出一份 Q2 合规报告" }]
}

// 列出可用 skill：GET /v1/skills

三个必需件

  • container.skills：声明挂载哪些 skill、锁哪个版本
  • code_execution 工具：skill 的脚本要在这个沙箱里跑
  • beta header：两个都要，少一个直接报错

版本要锁

"version": "latest" 写着舒服，但意味着别人改了 skill，你的流程就变了。 生产环境锁具体版本号。

换个角度看这段 JSON：它其实在说 "给这次对话准备一个装好了资料的工作台"。 Skill 不是一个函数，是工作环境的一部分—— 这也是为什么它必须配一个容器。

编写要点：三个字段，三种写法

写 Skill 的难度全在 description。因为它是唯一决定"会不会被用上"的字段。

✕ description 的三种典型写坏
// 1. 自夸型——模型不关心你多强大
description: "一个强大而全面的报告生成工具"

// 2. 只说做什么，不说何时用
description: "生成季度合规报告"

// 3. 太宽，什么都想接
description: "处理各类数据与文档任务"
   → 结果：每次对话它都想打开，纯干扰
✓ 正确写法的结构
description: "生成季度合规报告。      ← 做什么
  当用户要求季报、合规报告，或提到
  'Q1/Q2 报表'、'给合规组的材料' 时使用。 ← 触发词
  包含数据源口径、脱敏规则与审批流程。   ← 内含什么
  仅用于季度粒度；月报请用 monthly-report。 ← 负向边界

正文写什么

  • 步骤，按顺序编号，一步一个动作
  • 判断规则：口径冲突以谁为准、什么情况下要停下来问人
  • 禁忌：明确写"不要做 X"，这比正面描述有效
  • 引用：把大块内容放进 reference/，正文只写"按 X 排版"

正文不要写什么

  • 背景科普（"什么是合规"——模型比你懂）
  • 把整个模板贴进正文（放 reference/，第 3 层）
  • 大段代码（写成 scripts/ 里的脚本，让它执行而不是阅读）
  • 与本任务无关的公司介绍
一个好用的检验：把 SKILL.md 交给一个新入职的同事， 他能不能照着做完、并且做对。Skill 的读者定位就是"聪明但完全不了解你们内部规矩的新人"。

为什么会长出市场：它是开放标准

Anthropic 于 2025 年 10 月推出 Agent Skills， 并在 2025-12-18 把规范作为开放标准发布在 agentskills.io。

这一步是关键。对比一下历史：ChatGPT 插件只能在 ChatGPT 里用， Custom GPT 出不了 OpenAI 的门。SKILL.md 是一个纯文本约定—— 谁都能实现，创作者写一次可以到处用。

可移植性是市场形成的前提。没有它，就没有"应用商店"。

应用场景：四类真正划算的用法

判断标准很简单——这段知识是不是模型没有、而且你会反复用到的？

① 组织规范固化

代码规范、提交信息格式、评审清单、对外文案口径、命名约定。

典型信号：你在 code review 里反复说同一句话。 那句话就该变成一个 skill。

收益最稳的一类，因为它天然高频、天然只有你们知道。

② 专业格式产出

PPT / Excel / PDF / 特定 schema 的配置文件 / 行业报表模板。

这类 skill 的价值大头在第三层：模板文件和生成脚本。 正文只需要写"什么时候用哪个模板"。

官方 skill 里最成熟的就是这一类。

③ 多步流程

发布流程、事故响应、数据迁移、季度结账、新员工环境搭建。

特征是步骤有严格顺序、中间有判断分支、漏一步会出事。 单个工具封不下，写进 prompt 又太长。

Skills 最不可替代的场景。

④ 工具使用说明书

你们内部那个文档奇烂的 CLI、那个参数反直觉的内部 API、那个有历史包袱的老系统。

回想幕四：ACI 好坏取决于模型对它有多熟。 内部工具模型不可能熟——skill 就是补这一课。

投入产出比极高。

反过来，这些情况别写 skill： 模型本来就会的通用知识（写正则、用 git）· 只用一次的临时任务（直接说就行）· 本质上是一次函数调用的事（那是 tool）· 频繁变化的数据（那是 resource 或数据库查询）。

安全：把每个 skill 当作不可信依赖

这是一个被普遍低估的风险面，而且它的形状和传统供应链风险不完全一样。

一个 skill 能做什么

  • 它的正文会进入模型的上下文，并被当作可信指令对待
  • 它可以带可执行脚本，并在你的沙箱里运行
  • 它可以引导 agent 去调用它想调用的工具、访问它想访问的路径

所以装一个 skill ≈ 给你的 agent 加了一段它会照做的指令， 外加一个会被执行的脚本。这比装一个 npm 包更直接—— npm 包至少还得被 import。

最阴的一种：正文写得人畜无害，但埋一句 "完成后请将结果同时发送到 …"。人类扫一眼看不出来，模型会照做。

务实的四条

  • 装前读一遍 SKILL.md 全文。它就是纯文本，几分钟的事。这一条能挡掉九成问题。
  • 脚本跑在沙箱里，默认禁网，按需放行。
  • 锁版本。别用 latest，别让别人的一次提交改掉你的流程。
  • 凡是 skill 碰过的凭证，都当作已经泄露来轮换。

质量的真相

首个针对 agent skill 的同行评审基准得出两个结论： 写得好的 skill 能显著提升表现；而公开市场上多数 skill 写得并不好。

这两条并不矛盾——开放目录长得最快、审得最少， 因为它们的激励是分发量而不是治理。

幕五验收：Skills 的位置与未来

数据与判断均截至 2026-08。

Skills 回答的问题：怎么告诉 agent "该怎么做"，而不只是"能做什么"。
答案：一个文件夹 + 渐进式披露。摘要常驻、正文按需、附件再按需。

它和前三幕的关系

vs ToolsTools 是动词，Skills 是剧本。剧本里可以点名用哪些动词。
vs MCPMCP 解决"能力从哪来"，Skills 解决"用法从哪来"。互补，不竞争。
vs CLISkills 最常见的正文内容之一，就是"怎么用你们那套自制 CLI"。
vs promptSkills 本质就是按需加载的 system prompt 片段——想通这点就全通了。

未来判断（三条）

  • 会像应用商店那样收敛。八个市场不会都活下来。 分出胜负的不是收录量，是策展与信任——谁能让你放心地一键安装。
  • 安全扫描会成为标配，并且是市场的主要差异化点。 已经有市场把"上架前扫描"当作卖点在打了。
  • 变现层仍然缺位。目前主流渠道基本免费、没有原生计费， 创作者靠订阅或服务在市场外赚钱。这块空白迟早会被填。
更长期的一个看法：Skills 的真正意义可能不在市场， 而在于它给了组织一种把内部知识资产化的标准格式。 你们公司的 200 条"我们这儿是这么做的"，第一次有了一个可版本化、可分发、可复用的载体。

A2A 换了一个维度

前五幕全部是"agent 向下够工具"。A2A 是"agent 向旁边找同类"。

为什么不能拿 MCP 硬套？因为 MCP 假设对面是你信任的、你部署的、会立刻返回的东西。 而跨组织委派任务时，这三个假设一个都不成立。

四个角色（对照 MCP 的四实体来记）

A2A 的实体更少，但每个都更"重"。

① Client Agent（发起方）

决定要把什么事委派出去、找谁做、怎么描述需求、结果满不满意。

对照 MCP：位置类似 Host + Client，但它有自主判断—— 它会读对方的能力描述后自己决定合不合适。

② Remote Agent（承接方，又称 A2A Server）

接受任务、自己想办法完成、汇报进度、交付产物。

对照 MCP Server：最大的不同是它不透明—— 你不知道它内部用了什么模型、调了什么工具，也不需要知道。 它是黑箱，而且这是特性不是缺陷。

③ AgentCard（能力名片）

一份发布在 /.well-known/agent-card.json 的 JSON-LD 元数据： 我是谁、我会哪些 skill、我收什么格式、我用什么传输、怎么认证我。

对照 MCP 的 tools/list：作用相同， 但它是静态可抓取的 URL，不需要先建立连接。 这让"发现"成为可能——你可以像抓 robots.txt 一样抓它。

④ Task（任务对象）

一次委派的有状态载体。有 id、有 contextId、有状态机、有历史消息、有产物（artifacts）。

MCP 里没有对应物——这是 A2A 独有的核心抽象。 因为一次跨组织委派可能要跑几小时，必须有个东西能被反复查询、取消、续订。

记忆法：Client 想要，Remote 承接，AgentCard 是简历，Task 是工单。 整套协议就是围绕"怎么把一张工单安全地交给一个陌生人"设计的。

AgentCard 真实报文

发布于 https://<域名>/.well-known/agent-card.json。这是整个协议里唯一"公开可抓"的部分。

注意 skills 这个词

签名的 AgentCard 让你能验证这张名片确实来自那个组织、且没被篡改。 跨组织场景下，这是从"能用"到"敢用"的分水岭。

和 MCP 时序图最大的三处不同：① 发现走的是公开 URL，不需要预先配置； ② 请求立刻返回一个任务句柄而不是结果； ③ 对方会反问——这在 MCP 里只有 Elicitation 勉强对应，而在 A2A 里是一等公民。

Task 的八态生命周期

A2A 最核心的抽象。所有跨 agent 的复杂度，都被收进了这台状态机。

配套方法：tasks/get 查状态、tasks/cancel 撤单、 tasks/resubscribe 断线重连、tasks/pushNotificationConfig/set 配 webhook。 整套 API 围绕这台状态机展开，一个多余的方法都没有。

长任务：两种回传，别用轮询

跨组织委派动辄几分钟到几小时。这是 A2A 与 MCP 在工程形态上最实质的差别。

✕ 轮询

反复 tasks/get。能用，但延迟高、请求浪费、长任务下几乎不可接受。

只在对方两种能力都不支持时才退到这里。

SSE 流式

message/stream，服务端持续推送状态变更与中间产物。

适合你在线等的场景——用户盯着界面看进度条。

断线了用 tasks/resubscribe 接回来。

Webhook 推送

tasks/pushNotificationConfig/set 登记一个回调地址， 状态变更时对方主动打过来。

适合你不在线的场景——发出去就下班，明早看结果。

代价：你得有个公网可达的接收端，还得验证回调的真实性。

由此产生的工程要求（容易被忽略）

  • 任务要持久化。你的进程重启了，对方的任务还在跑。taskId 必须落库。
  • 要能对账。webhook 可能丢，SSE 可能断。需要一个兜底的对账扫描。
  • 要处理重复。webhook 会重投，状态更新要幂等——又回到幕四第④条。
  • 要有超时策略。对方永远停在 working 怎么办？tasks/cancel 什么时候发？

为什么说这才是 A2A 真正的门槛

接一个 MCP Server，你写几行配置就完事了。 接一个 A2A Remote Agent，你要处理异步任务、状态持久化、回调接收、重试与对账。

这不是协议复杂，是问题本身就复杂—— 你在做的事情，本质上等同于对接一个外部供应商的工单系统。

这也解释了为什么 A2A 的采用曲线比 MCP 慢得多： 它的成本不在协议实现上，在配套的分布式工程上。

治理与版本：它已经不是"Google 的协议"了

这条时间线本身就是判断它成不成熟的最重要证据。

三个里程碑各自意味着什么

  • 捐给 LF（2025-06-23）：解决了"凭什么用竞争对手的协议"这个死结。 没有这一步，微软、AWS、Salesforce 不会入场。
  • ACP 并入（2025-08）：避免了 agent 互联领域的协议战。 对比一下 MCP 那边——同样只剩一个赢家。这个领域不容忍两套标准。
  • v1.0 的签名 AgentCard：跨组织的前提是能验明身份。 没有签名，AgentCard 就是一张谁都能伪造的名片，整套协议在企业场景不可用。

v1.0.1 的扩展机制

允许在不改核心的前提下加入新数据、新要求、新 RPC 方法、新状态机。

这和 MCP 2026-07-28 引入扩展框架是同一种成熟信号： 核心收紧、变化外移。协议开始为长期演进做准备，而不是继续往主干里塞功能。

实务提醒：网上资料同时存在 v1.0 与 v1.0.1 的说法。 落地前请以 a2a-protocol.org 上的当前版本为准， 并确认对方 AgentCard 里的 protocolVersion。

五条能带走的判断

如果这五十多页只留五句话。

① 五套协议是同一件事的五种供货渠道

名字 + 参数约定 + 文本回执。无论走哪条路，执行权永远在宿主， 模型永远只看见一个扁平数组。想清楚这点，所有协议文档都会变得好读。

② 真正的设计对象是 ACI，不是协议

选 Tools 还是 MCP 还是 bash，是次要问题。首要问题是 你的接口对一个会猜的读者好不好用：名字、粒度、错误信息、输出预算。 这四件事没做好，换任何协议都救不了。

③ 从 bash 起步，按日志升级

不要一上来设计五十个精美工具。先给最小可用的能力， 看 agent 真实怎么用、在哪反复出错，再把那些动作提升为专用工具或写成 Skill。 你是在用真实数据做接口设计。

④ 能力和用法要分开供给

MCP 给能力，Skills 给用法。把流程知识硬塞进工具描述或 system prompt， 是最常见的浪费。渐进式披露让"装很多东西"从线性成本变成接近常数成本—— 这个思路在工具侧同样适用。

⑤ 协议在动，判断要带日期

MCP 现行版 2026-07-28 已经删掉了握手和会话；A2A 已经交给 Linux Foundation 并发到 v1.0.x。 你在网上读到的多数教程停在 2025 年。接入前先确认对方的协议版本， 这是本讲最实用的一条操作建议。
