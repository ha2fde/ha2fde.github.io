## 第 1 章：它是不是在搜答案？

---

### P3 ｜ "我问它问题，它是不是像搜索引擎一样去查答案？"

**先点破**：不是。默认形态下，它不连数据库、不搜索、没有任何"答案库"。

**架构图**：

```
 你以为的:                        实际上的:
 问题 --> 搜索 --> 找到答案 --> 念给你听     问题 --> 预测下一个词 --> 再下一个 --> ...
 (从已有内容里"找")                        (按概率"编"一段从未存在过的文本)

 +----------------------------------------------------------+
 | 模型只做一件事: 给定上文, 计算"下一个 token 最可能是什么"   |
 +----------------------------------------------------------+
```

**要点**：
1. **生成 vs 检索**是本质区别：搜索引擎从索引里找已存在的网页；模型按概率现场编一段新文本
2. 因为每个词都是"现编"的，所以答案每次可能不同、也可能编出看似合理但不存在的内容
3. 后面所有章节（会变、胡说、记不住）都是这一点的推论

**右下角代码**：

```python
# 模型的全部工作（伪代码）
while not 结束:
    next_token = model.预测下一个(text)  # 只出一个
    text += next_token                   # 接回去再猜
```

---

### P4 ｜ "token 是单词吗？为什么它说话是一个词一个词往外蹦？"

**先点破**：token 不是单词，是文本被切分后的最小单位——可能是一个字、一个词、半个词或一个标点。

**架构图**：

```
 输入: "今天天气"
    |
    v 切分 (tokenizer)
 [今天] [天气]
    |
    v
 +---------------+     下一个 token 的概率分布
 |     模型       | -->  真:0.30  很:0.25  不:0.15  晴:0.10 ...
 +---------------+
    |
    v 选(采样)一个 -> "真"
 [今天] [天气] [真]
    |
    +----> 把新 token 接回输入, 再预测下一个, 循环直到结束
```

**要点**：
1. 模型的词表是固定的（几万~十几万个 token），每次输出 = 从词表里选 1 个
2. "ChatGPT" 这样的词可能被切成 Chat + G + PT 多个 token；中文常按字/词混合切
3. 网页上"打字机"效果的根源：本来就是逐 token 生成，不是特效

**右下角代码**：

```python
from transformers import AutoTokenizer, AutoModelForCausalLM
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
ids = tok("今天天气真", return_tensors="pt")      # 半句话
out = model.generate(**ids, max_new_tokens=20)    # 看它怎么接
print(tok.decode(out[0]))
```

## 第 2 章：它凭什么会"回答问题"？

---

### P5 ｜ "我一问它就会答，是它天生就会聊天吗？"

**先点破**：不是天生的，是"训"出来的。训练分三步，每一步解决一个问题。

**架构图（训练漏斗/时间线）**：

```
 海量互联网文本 (几万亿 token)
      |
      v  [第1步] 预训练: 反复练习"接下一个词"
 ==================>  基础模型 base     (会续写, 不会对话)
      |
      |  对话样本: "问题 -> 好回答" (几万~几百万条)
      v  [第2步] 监督微调 SFT: 学会"问->答"的格式
 ==================>  SFT 模型         (会回答, 未必讨喜)
      |
      |  人类偏好数据: "回答A 比 回答B 好"
      v  [第3步] 偏好对齐: 学会有用 / 礼貌 / 守规矩
 ==================>  对话模型 chat    (你日常用的就是它)
```

**要点**：
1. **预训练**：在海量文本上练"接话"，语言能力和世界知识都在这一步灌进去
2. **SFT（监督微调）**：用"问题→好回答"样本，教它把接话能力组织成"回答"
3. **偏好对齐**：让人类标注哪个回答更好，教它什么回答更讨喜、更安全

**右下角代码**：

```python
# 三步训练（概念伪代码）
base = pretrain(语料, 目标="预测下一个token")
sft  = finetune(base, 数据="问题->好回答")
chat = align(sft, 数据="人类偏好排序")
```

---

### P6 ｜ "开源模型为什么总分 base 版和 chat/instruct 版？"

**先点破**：这正对应上一页的训练三步——base 只做了第 1 步，chat 多做后两步。

**架构图（同一输入，两种输出）**：

```
 同一个输入: "怎么煮咖啡?"

 base 模型 (只预训练)                chat 模型 (预训练+SFT+对齐)
 ------------------------            ---------------------------
 "怎么煮咖啡? 咖啡的种类有很多,       "1. 准备咖啡豆并磨粉
  煮咖啡的方法因地区而异, 常见的       2. 按 1:15 的比例加入热水
  有手冲、意式..."                    3. 90-95 度水温冲泡约 2 分钟"

 (它在"续写这段话", 不像在回答)       (它在"回答这个问题")
```

**要点**：
1. base 模型眼里没有问题/回答之分，你给它问题，它可能续写出更多问题
2. chat/instruct = base + SFT + 对齐，才听得懂"指令"和"提问"
3. 选型经验：聊天、做 Agent 选 instruct/chat 版；要灌自己的领域语料继续训练，可从 base 起步

**右下角代码**：

```python
base = load("Qwen/Qwen2.5-0.5B")            # 只会续写
chat = load("Qwen/Qwen2.5-0.5B-Instruct")   # 会问答
print(base.generate(q))   # 续写出一堆"类似文本"
print(chat.generate(q))   # 给出结构化的回答
```

## 第 3 章：它怎么"记得"我们聊过什么？

---

### P7 ｜ "它记得我两分钟前说的话，是不是有记忆？"

**先点破**：它没有记忆，也不"理解"你。模型本身完全无状态——每次请求都是"第一次见到你"。

**架构图（环形循环）**：

```
 +------------------------------------------------+
 | messages 消息列表 (由聊天程序维护, 不在模型里)    |
 |   system:    "你是简洁的助手"                    |
 |   user:      "我叫小明"                          |
 |   assistant: "你好, 小明"                        |
 |   user:      "我叫什么名字?"                     |
 +-----------------------+------------------------+
                         |
                         v  (1) 整个列表渲染成一整段文本
 +------------------------------------------------+
 | 模型看到的只有这段纯文本                          |
 +-----------------------+------------------------+
                         |
                         v  (2) 生成回复: "你叫小明。"
                         |
                         v  (3) 新回复追加回列表
      messages.append(assistant: "你叫小明。") --+
                                                 |
      下一轮再把更新后的整个列表重新塞给模型 <------+
```

**要点**：
1. "记得"的真相：那句话出现在了这次的输入文本里，仅此而已
2. 对话由三种角色组成：**system**（设定）、**user**（你）、**assistant**（它）
3. 关掉窗口重开 = 历史列表没了 = 它"失忆"了——因为从来就没存在过记忆

**右下角代码**：

```python
messages = [
  {"role": "system",    "content": "你是简洁的助手"},
  {"role": "user",      "content": "我叫小明"},
  {"role": "assistant", "content": "你好，小明"},
]
```

---

### P8 ｜ "消息列表怎么变成模型认得的输入？聊太久会怎样？"

**先点破**：程序负责把消息列表按"聊天模板"渲染成纯文本；窗口装不下时，丢最老的，系统设定永不丢。

**架构图（模板渲染 + 超长截断）**：

```
 messages --> [聊天模板渲染] --> 模型实际看到的文本:
 <|im_start|>system 你是简洁的助手<|im_end|>
 <|im_start|>user 我叫小明<|im_end|> ...

 上下文窗口有限 (如 4K / 32K token), 聊太久装不下:

 system | u1 | a1 | u2 | a2 | u3 | a3 | u4 | a4 | u5(新)
   ^                                                ^
 永不丢                                      从 u1/a1 开始丢

 截断后: system | a2 | u3 | a3 | u4 | a4 | u5  --> 塞给模型
```

**要点**：
1. **聊天模板**：每个模型有自己的格式约定（角色标记、分隔符），渲染错了效果会明显变差
2. **上下文窗口**：模型一次能看的文本有硬上限，窗口大小是模型的重要指标
3. **截断策略**：优先丢最老的历史（所以它会"忘记"聊天开头），system 设定永远保留

**右下角代码**：

```python
text = tok.apply_chat_template(messages, tokenize=False)
while len(tok(text).input_ids) > MAX_LEN:
    history.pop(0)   # 丢最老的一条; system 单独保留
    text = tok.apply_chat_template([sys] + history, tokenize=False)
```

## 第 4 章：为什么同样的问题，答案每次不一样？

---

### P9 ｜ "同一个问题隔一分钟再问，答案怎么变了？"

**先点破**：模型不是"算出唯一答案"，而是"按概率抽样"——每次都在掷一个加权骰子。

**架构图（采样流水线）**：

```
 模型为下一个 token 给出概率分布:
   的:0.50   是:0.20   很:0.10   真:0.05   ...长尾...
        |
        v  [temperature] 温度缩放
   T -> 0 : 分布变尖, 最大者通吃 -> 几乎总选 "的"  (稳定保守)
   T = 0.9: 分布拉平, 小概率词也有出头之日         (发散多样)
        |
        v  [top_p = 0.9] 截断
   只保留累计概率前 90% 的候选池: {的, 是, 很}
        |
        v  [随机采样] 本轮吐出: "很"
        |
        v  [max_new_tokens] 控制这个循环最多再走多少步
```

**要点**：
1. **temperature**：低 → 稳定保守（要事实、要格式时调低）；高 → 发散多样（要创意时调高）
2. **top_p**：只在累计概率前 p 的候选池里抽，砍掉长尾里的烂词，保证多样但不离谱
3. **max_new_tokens**：生成长度上限，防止无限生成，也控制成本

**右下角代码**：

```python
model.generate(**ids, max_new_tokens=50,
               do_sample=True, temperature=0.9, top_p=0.9)
# temperature=0 等价于贪心: 每次都选概率最大的那个
```

## 第 5 章：为什么它会一本正经地胡说八道？

---

### P10 ｜ "它为什么能面不改色地编出不存在的论文和新闻？"

**先点破**：它不知道自己在胡说——因为它的本职工作就是"编最像样的话"，像样 ≠ 真实。

**架构图**：

```
 模型的训练目标:               模型没有的东西:
 +------------------+         +------------------+
 | 说得像人话    [√] |         | 事实核查机制  [X] |
 | 格式像模像样  [√] |         | "我不知道"状态[X] |
 | 语气自信流畅  [√] |         | 说谎的"自觉"  [X] |
 +------------------+         +------------------+

 "请给我 3 篇关于 XX 的论文" -->
 标题像论文、作者像人名、期刊像真的 --> 但可能全是编的 (幻觉)
```

**要点**：
1. **幻觉**不是"说谎"，是生成式本质的副产品：第 1 章讲过，它只负责"编得像"
2. 越是你不懂的领域，幻觉越难被发现——它编什么都很自信
3. 两条主流缓解路线：需要**事实** → 接 RAG（第 6 章）；需要**推理** → 用思维链（下一页）

**右下角代码**：

```python
ask("请给出 3 篇关于 XX 的论文及作者")
# 输出看起来有模有样 -- 请逐条核实, 可能全是幻觉
```

### P11 ｜ "为什么加一句'请逐步思考'，它数学题就对了？"

**先点破**：直接答 = 让它一步跳到结论，没机会"打草稿"；把中间步骤生成出来，每一步都有前文可依赖。

**架构图（并排对比）**：

```
 直接回答                                先思考再回答 (CoT)
 ---------                              -------------------
 Q: 3 人 4 天摘了 72kg 苹果,             Q: 同上 + "请逐步思考"
    平均每人每天摘多少?
    |                                     |
    v                                     v
 一步跳到结论:                            先把草稿写出来:
 "每人每天摘 24 kg"   X                   "4 天共 72kg -> 3 人 1 天摘 18kg
                                           -> 每人每天 18/3 = 6kg"
                                          再下结论: "6 kg"   √

 结论前生成的 token 太少, 等于心算,        中间步骤留在上下文里,
 一步错就全错。                            后续生成有"稿纸"可依赖。
```

**要点**：
1. **思维链 CoT**：让模型先输出推理过程，再输出结论——复杂推理显著变好
2. 原理：生成的每一步都成为上下文的一部分，后面的 token 可以"看着草稿算"
3. 实践口诀：数学题、逻辑题、多步推理，加一句"请一步一步思考"

**右下角代码**：

```python
q = "3个人4天摘了72千克苹果，平均每人每天摘多少？"
a1 = ask(f"{q}\n直接给出答案。")            # 容易错
a2 = ask(f"{q}\n请一步一步思考，再给出答案。")  # 明显变好
```

## 第 6 章：怎么让它知道"它没学过"的东西？

---

### P12 ｜ "它能读我们公司内部文档、今天的新闻吗？"

**先点破**：不能。模型知识截止于训练数据——私有资料、最新消息，它一概不知；而为每份资料重新训练，太贵也不现实。

**架构图（RAG 离线准备，只做一次）**：

```
 思路: 不让模型"背下来", 而是提问时把相关资料"递到它手上"

 内部文档                切块                 向量化               向量库
 ----------            ----------            ----------          ----------
 报销制度.md   -->    [块1][块2]      -->    [0.12 -0.33...] -->  库存(向量+原文)
 考勤规定.md          [块3][块4]             [0.88  0.05...]
 产品手册.md          [块5][块6]             [ ... ]

 (每块几百字; 向量化 = 把文本变成一串数字, 语义越近数字距离越近)
```

**要点**：
1. **知识截止**：训练完成那天之后的世界，模型完全不知道
2. **RAG（检索增强生成）**：把资料切成小块、转成向量存好，随用随取
3. 更新知识 = 往向量库里加文档，不用动模型——便宜且即时生效

**右下角代码**：

```python
chunks = [doc[i:i+200] for i in range(0, len(doc), 200)]  # 切块
vecs = encoder.encode(chunks)   # 每块 -> 一个向量, 存起来备用
```

### P13 ｜ "几万段资料里，怎么找到最相关的那几段？"

**先点破**：问题也变成向量，和库中所有块算"距离"，最近的 Top-K 就是答案素材。

**架构图（RAG 在线问答）**：

```
 "出差住宿报销上限是多少?"
      |
      v 同样向量化 -> 与库中所有向量算相似度
      |
      v Top-K 检索: 块2("住宿报销: 一线城市 500 元/晚...") 最相关
      |
      v 拼进上下文:
 +--------------------------------------------------+
 | 资料: 住宿报销标准: 一线城市 500 元/晚, 二线 400...  |
 | 问题: 出差住宿报销上限是多少?                        |
 | 请根据资料回答。                                     |
 +--------------------------------------------------+
      |
      v 模型基于资料回答: "一线城市上限 500 元/晚"
```

**要点**：
1. **向量化检索**：语义相近 → 向量距离近，不需要关键词完全匹配
2. **拼上下文**：检索结果 + 问题一起塞给模型（用的正是第 3 章的机制）
3. 效果：回答有据可依、能答私有知识、幻觉大减——企业知识库的主流做法

**右下角代码**：

```python
q_vec = encoder.encode([question])
scores = doc_vecs @ q_vec.T              # 余弦相似度
top = chunks[scores.argmax()]            # 取最相关的一段
prompt = f"资料：{top}\n问题：{question}\n请根据资料回答。"
```

## 第 7 章：怎么让它"动手干活"？

---

### P14 ｜ "让它算个账、查个天气、订张票，它行不行？"

**先点破**：它自己不行——模型只会"说"。但你的程序会"做"，让它"说"出要调什么工具就行。

**架构图（function calling）**：

```
 工具说明书 (写进提示词):            模型输出 (只是文本!):
 +------------------------+         { "tool": "calc",
 | name: calc             |           "args": {"expr": "38*27"} }
 | desc: 计算器            |                |
 | params: expr(string)   |                v 程序解析并真正执行
 +------------------------+           result = 1026
                                            |
                                            v 结果以 role=tool 回填
 模型再看着结果, 组织成自然语言回答: "38 乘 27 等于 1026"
```

**要点**：
1. 模型不会算数、不能联网、碰不到你的系统——它只负责决定"该调哪个工具、传什么参数"
2. **function calling**：模型输出结构化调用请求 → 程序真正执行 → 结果回填给模型
3. 分工哲学：**模型负责决策，程序负责执行**——精确的事交给精确的工具

**右下角代码**：

```python
tools = [{"name": "calc", "desc": "计算器", "params": "expr:str"}]
# 模型输出: {"tool": "calc", "args": {"expr": "38*27"}}
result = safe_eval(args["expr"])   # 你的程序真正执行
messages.append({"role": "tool", "content": str(result)})
```

---

### P15 ｜ "调一次工具不够用的任务，它能自己分多步操作吗？"

**先点破**：能——把"思考→行动→观察"循环起来，就是 Agent 的最小内核。

**架构图（ReAct 循环）**：

```
        +--------------------------------------------------+
        |                                                  |
        v                                                  |
 [Thought 思考] --> [Action 调工具] --> [Observation 看结果]
        |                                                  ^
        |  (认为信息够了)            (结果以 role=tool 回填)
        v                                                  |
 [Final 直接回答]         +------- 循环上限保护 (如 5 轮) ------+
```

**要点**：
1. **ReAct 循环**：思考 → 行动 → 观察 → 再思考……直到模型决定直接回答
2. 每轮工具结果以 `role=tool` 消息回填进上下文——复用第 3 章的机制，模型因此"看得到"执行结果
3. Agent = LLM + 工具 + 循环，就这三样；必须加循环上限防止死循环烧钱

**右下角代码**：

```python
for _ in range(5):                              # 循环上限
    out = llm(messages)                         # 思考
    if "Final:" in out: return out              # 决定回答
    name, args = parse_action(out)              # 解析 Action
    result = TOOLS[name](**args)                # 执行
    messages.append({"role": "tool", "content": result})  # 观察回填
```

## 第 8 章：工具从哪来？怎么批量接进来？——MCP / CLI / Skills

---

### P16 ｜ "给 AI 接一个工具，是不是每家工具都得写一套对接代码？"

**先点破**：曾经是。N 个 AI 应用 × M 个工具 = N×M 套胶水代码；现在工具接入正在标准化。

**架构图**：

```
 以前: 每个 AI 应用单独对接每个工具         现在: 统一协议

 AI应用A --\                               AI应用A --+
 AI应用B -----+--> 工具1 2 3 ... M          AI应用B --+--[MCP]--> 工具服务器: 1 2 3 ... M
 AI应用C --/    (N x M 套胶水代码)          AI应用C --+         (每个工具只封装一次)
```

**要点**：
1. 标准化之后：工具只封装一次，任何支持协议的 AI 应用都能用
2. 本章三个概念各管一层：**MCP** 管"怎么接"，**CLI** 是最朴素的工具形态，**Skills** 管"怎么用对流程"
3. 理解这三层，就看懂了当前的智能体工具生态

**右下角代码**：

```python
async with stdio_client("weather_server.py") as c:
    tools = await c.list_tools()   # 不问不知道, 一问全知道
    print([t.name for t in tools]) # ['get_weather', 'get_forecast']
```

### P17 ｜ "MCP、CLI、Skills，到底各是什么？"

**先点破**：三者不是竞争关系，是三个不同层次的东西——协议、工具形态、流程封装。

**架构图（三个概念卡）**：

```
 [MCP: 工具接入标准]        [CLI: 最朴素的工具]         [Skills: 流程封装]
 "工具界的 USB 接口"         "命令本身就是工具"           "可加载的操作手册"
 -------------------        ----------------------      ----------------------
 服务器对外暴露工具列表,     任何命令行命令/脚本          把"怎么做某类任务"的步骤、
 AI 应用按协议发现和调用,    本身就是工具, AI 像人         提示词、配套脚本打包,
 接一次处处可用             一样敲命令, 零封装成本        遇到对应任务按需加载执行
```

**要点**：
1. **MCP（Model Context Protocol）**：开放协议，让任何工具/数据源以统一方式接入任何 AI 应用
2. **CLI**：命令行是 AI 最趁手的工具——有文档、可组合、返回纯文本
3. **Skills（技能包）**：封装的是"流程"而不是"命令"，比单个工具高一层复用

**右下角代码**：

```
skills/整理报销/
├── SKILL.md          # 操作手册: 步骤 + 注意事项
└── scripts/fill.py   # 配套脚本: 手册里会引用它
```

---

### P18 ｜ "这三者怎么配合？"

**先点破**：分层协作——Skills 在流程层，MCP 在接入层，CLI/API 在执行层。

**架构图（三层关系图）**：

```
 +-----------------------------------------------------+
 | Skills    流程层: "报销/发布/写周报"这类任务怎么做     |  按任务触发加载
 +--------------------------+--------------------------+
                            v  流程里会用到
 +-----------------------------------------------------+
 | MCP       接入层: 统一的工具发现与调用协议             |  工具服务器 A / B / C
 +--------------------------+--------------------------+
                            v  协议之下真正干活的
 +-----------------------------------------------------+
 | CLI / API 执行层: 命令行、脚本、HTTP 接口              |  一个个具体工具
 +-----------------------------------------------------+
```

**要点**：
1. 一个 Skill 的操作手册里，可以既调 MCP 工具、也跑 CLI 命令——它是"胶水 + 经验"
2. 工具写成 MCP server：一次开发，所有支持 MCP 的 AI 应用直接可用
3. 流程沉淀为 Skill：把"专家怎么做这件事"固化下来，比模型临时发挥稳定得多

**右下角代码**：

```python
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("demo")

@mcp.tool()
def add(a: int, b: int) -> int:      # 一个工具
    return a + b

mcp.run()   # 任何 MCP 客户端都能发现并调用 add
```

## 第 9 章：怎么让别的程序用上它？

---

### P19 ｜ "除了对着网页聊天，我自己的程序怎么调用它？"

**先点破**：有标准接口——主流服务和本地自建遵循同一套 Chat Completions 契约。

**架构图**：

```
 你的程序                          服务端 (本地 / 云端, 同一契约)
 --------                          --------------------------
   |  POST /v1/chat/completions
   |  { "model": "...",
   |    "messages": [...],         -->  messages 渲染聊天模板
   |    "stream": true }           -->  模型逐 token 推理
   |                               -->  每出一个 token 推一条
   |  <== data: {"choices":[{"delta":{"content":"你"}}]}
   |  <== data: {"choices":[{"delta":{"content":"好"}}]}
   |  <== data: [DONE]
   v
 换本地/换云端 = 只改 base_url + api_key, 业务代码一行不动
```

**要点**：
1. **契约**：`POST /v1/chat/completions`，请求体 `{model, messages, stream}`，返回 `choices` 数组——OpenAI、DeepSeek、本地服务同此格式
2. **流式 = SSE**：服务器把每个 token 作为一条事件推过来（就是第 1 章逐 token 生成的直接暴露）
3. 这意味着：自己用本地小模型搭一个兼容服务，现有所有客户端代码都能直接用

**右下角代码**：

```python
@app.post("/v1/chat/completions")
def chat(req: ChatRequest):
    def stream():
        for tok in model.stream(req.messages):
            yield f"data: {json.dumps(chunk(tok))}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

# 附录：脚本需求清单（细化设计）

### 1. tokenizer_demo.py（第 1 章）
- **输入**：一句中文（默认"今天天气真"，支持命令行传入）
- **输出**：① 切分后的 token 列表（id + 文本对照）② token 数量 ③ 基于前半句的续写结果
- **核心逻辑**：`tokenizer.encode/decode` 逐 token 展示；`model.generate(max_new_tokens=30)` 续写
- **依赖/模型**：transformers + torch；Qwen2.5-0.5B-Instruct

### 2. training_stages_demo.py（第 2 章）
- **输入**：内置同一问题（如"怎么煮咖啡？"）
- **输出**：base 模型的续写结果 vs instruct 模型的问答结果，并排打印
- **核心逻辑**：分别加载 `Qwen2.5-0.5B`（直接续写原文）与 `Qwen2.5-0.5B-Instruct`（走聊天模板），对比输出形态
- **说明**：首次运行下载约 1.5GB；脚本内置 ModelScope 镜像开关注释

### 3. chat_context_demo.py（第 3 章）
- **输入**：模拟 6 轮对话（脚本内置，含 system 设定）
- **输出**：每轮渲染后的模板文本片段、当前 token 数；触发阈值（如 512）时打印截断过程：system 保留、最老消息逐条丢弃
- **核心逻辑**：`apply_chat_template` 渲染 + 长度检查 + 截断策略循环

### 4. sampling_demo.py（第 4 章）
- **输入**：内置同一问题
- **输出**：temperature=0（贪心）与 temperature=0.9（top_p=0.9）各生成 3 次，六条结果对比打印
- **核心逻辑**：`generate` 的 `do_sample / temperature / top_p` 参数组合

### 5. cot_demo.py（第 5 章）
- **输入**：内置一道多步算术题
- **输出**："直接给出答案"与"请一步一步思考"两种提示的输出对比
- **核心逻辑**：同一模型、同一问题、两种 prompt
- **说明**：0.5B 小模型能力有限，重点演示提示法的结构差异；注释中给出换更大模型的方式

### 6. rag_demo.py（第 6 章）
- **输入**：内置 4 段中文资料（报销/考勤/产品/假期）+ 一个相关问题
- **输出**：切块列表 → Top-2 检索结果（含相似度分数）→ 拼接后的完整 prompt → 模型基于资料的回答
- **核心逻辑**：BGE-small-zh-v1.5 向量化 + numpy 余弦相似度 + 拼上下文；不引入向量数据库

### 7. agent_tool_demo.py（第 7 章）
- **输入**：需要计算的提问（如"38 乘 27 再加 100 是多少？"）
- **输出**：每轮 Thought / Action / Observation 日志 + 最终回答
- **核心逻辑**：工具注册表（calc 计算器 + current_date）；提示模型输出 `Action: name(args)`，正则解析执行，`role=tool` 回填；上限 5 轮防死循环

### 8. mcp_skills_demo.py（第 8 章）
- **输入**：MCP 客户端调用
- **输出**：① 工具列表发现结果 ② add / calc 调用结果 ③ skill 演示：读取 SKILL.md 手册，按步骤执行配套脚本
- **核心逻辑**：FastMCP 起 stdio server + 客户端 `list_tools / call_tool`；skill = 一个 markdown 操作流程 + 一个 python 脚本（目录随脚本交付）

### 9. api_server.py（第 9 章）
- **输入**：HTTP `POST /v1/chat/completions`（JSON: model / messages / stream）
- **输出**：非流式返回 `choices` JSON；流式返回 SSE（逐 token delta + `[DONE]`）
- **核心逻辑**：FastAPI + `apply_chat_template` + 逐 token `StreamingResponse`；文件头部附 curl 调用示例注释；字段与 OpenAI 契约对齐
