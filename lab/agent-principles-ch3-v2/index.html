AGENT 原理与实践 · 第三章

从 Chat 到 Agent

一个只会预测下一个词的模型，
是怎么变成会拆任务、会调工具的系统的。
工程课 · 每一步补了什么、代价是什么
← → 翻页　·　O 概览　·　F 全屏

先把起点和终点摆清楚

起点：一个自回归的下一词预测器
给它一段文本，它输出下一个词元的概率分布；采样一个，接到后面，再预测下一个。循环往复。

这就是它做的全部事情。它不知道什么是问题、什么是回答，也不知道自己在跟人说话。
终点：一个能干活的 Agent
给它一个目标，它能拆解步骤、判断自己缺什么信息、发出调用外部工具的请求、拿到结果后接着往下推进，直到任务完成。
这中间的距离，比看上去大得多
「预测下一个词」和「完成一项任务」不是同一类东西。中间隔着五步，每一步都是被上一步的一个具体缺陷逼出来的——这一章就是走这五步。
这条线不是「越来越聪明」
每一步加的都不是智力，而是一个具体缺陷的补丁：什么都不会、只会续写、不会分步想、想完了动不了手、说不清自己要调什么。看清缺在哪，比记住名词有用得多。
每一步都有代价
对齐要付出多样性的损失，思维链要付出 token 和延迟，工具调用要付出一整套接口约定和安全面。这一章会把每一步的代价一并说清楚——只讲收益的讲法会让你高估它。
中间那条边界最重要
整条线上只有一条边界要一直记着：模型负责决定，宿主程序负责执行（就是你用的那个客户端）。后面所有让人困惑的现象——为什么它会「撒谎」说做完了、为什么权限要卡在外面——都能回到这条边界上解释。
另外有三件事，不在这五步里
这五步讲的是能力怎么补出来的。真跑起来还有三件事不属于任何一步，却决定它跑不跑得动：这个圈要转多少轮、凭什么算干完了、上下文那点预算怎么花——本章一并讲。

预训练结束，你拿到的是什么

一个基座模型（base model）。训练目标从头到尾只有一个——把给它的文本合理地续下去。
拿它当聊天机器人用，会这样
你输入： 法国的首都是哪里？ 它续写： 法国的首都是哪里？ 德国的首都是哪里？ 意大利的首都是哪里？ 以上问题请在课后完成。
它没有出错。在训练语料里，一行问句后面接着另一行问句是极其常见的模式——习题册、问卷、试卷。它给出了一个统计上非常合理的续写。
它缺的到底是什么
不是知识，也不是能力。它知道法国的首都是巴黎——换个写法就能逼出来：

「法国的首都是」→「巴黎」

它缺的是一个「我在对话，我应该回答」的行为约定。这个约定在预训练目标里从来没有出现过，所以它无从习得。
这是整条链上的第一个缺口
能力有了，但没有一个稳定的接口把能力取出来。你得靠精心构造前缀去「骗」它进入正确的续写模式——这在当时确实是主要用法，也确实难用。下一步补的就是这个。
另外记住一件事：「续写」这个底层动作，后面一直没变
后面三步改的都是它续写什么，不是它在续写。今天你和它对话，它做的仍然是把这段对话按格式续下去——只是被训得会在该停的地方停下来。
那它的能力是从哪来的：全是「预测下一个词」这个压力的副产品
要预测准「他把水倒进杯子里，杯子__」，得懂物理；预测准「23 × 7 ＝ __」，得会算；预测准「这段代码报错的原因是__」，得真读懂这段代码。预测下一个词是手段，不是目的——要在足够多样的文本上把这件事做好，模型被迫在内部建立起关于世界、语言和逻辑的表示。

第一步：把「对话」变成一种文本格式

关键的一招是：不改变模型做的事，只改变喂给它的文本长什么样。模型依然只会续写——但如果所有训练样本都遵循同一套格式，续写就等于回答。
# 对话被写成带角色标记的一段纯文本 <|system|> 你是一个有帮助的助手。 <|user|> 法国的首都是哪里？ <|assistant|> 巴黎。<|end|>
推理时，宿主程序（客户端）把对话拼成这个格式，一直拼到 <|assistant|> 为止，然后让模型续写；模型吐出 <|end|> 就停。

「一轮对话」这件事，本质上是宿主用模板拼字符串拼出来的。模型自始至终只是在续写。
监督微调（SFT）
拿几万到几十万条人写的高质量对话，按上面的格式组织好，在基座模型上继续训练。训练目标不变，还是预测下一个词元——变的只是数据。

训完之后，模型学会了：看到 <|assistant|> 就该开始给答案，而不是接着编问题。chat 就是这么出来的。
这一步的性价比高得惊人
相比预训练动辄上万亿词元，SFT 的数据量小了好几个数量级，算力也少得多。

因为它不教任何新知识，只教一个行为约定。能力早就在预训练里长好了，这一步只是装了个把手。
顺带解释一个现象
不同厂商的模型对话模板不同（角色标记、分隔符、系统提示的位置都不一样）。用错模板，模型表现会明显变差——这也是换模型时最难查的一类问题：模型是好的，接口也通，但对话被拼成了它没见过的样子。
一个容易被忽略的细节：角色标记不是普通文本
<|system|> 这类标记是词表里的专用词元，不是「小于号加 system」这几个字符。你在输入框里原样打出来，分词器会把它切成一串普通词元，拼不出那个标记——所以用户没法凭字面伪造一个系统角色。

但它挡住的只是字面伪造：用户仍然可以在自己那一段里写「忽略上面的规则」。那是语义层面的事，词元管不着。

但 SFT 不够：有些事没法用「标准答案」教

SFT 的机制决定了它的上限
SFT 是模仿：给一个输入，给一个人写的标准答案，让模型学着复现。

问题是——大量问题没有唯一的标准答案，只有「这个比那个好」。「帮我写一封委婉的拒绝邮件」，好回答有无数种，人也写不出那个「唯一正确」的版本。

更麻烦的是「不该做什么」：你没法通过示范正确行为，来教会它拒绝一个危险请求——示范里根本不会出现那个场景。
换一种监督信号：比较
让模型对同一个问题生成多个回答，请人排序（这个比那个好）。人做排序比写范文容易得多，也可靠得多。

用这些排序数据训练一个奖励模型，让它学会给任意回答打分；再用强化学习，让语言模型朝着「奖励模型给分更高」的方向调整。
这一步真正改变了什么
· 有用：不再答非所问、不再糊弄了事
· 诚实：不确定时更倾向于说不确定，而不是编一个（只是倾向，没有根治）
· 无害：学会拒绝明确有害的请求

这三条不是靠示范教会的，是靠大量「A 比 B 好」的比较逼出来的。
代价必须说清楚，这是工程课
· 能力上有损耗：为了行为可控，模型在某些任务上的原始表现会比基座模型下降
· 过度拒绝：把无害请求误判成有害，这是最常见的用户抱怨
· 倾向于迎合：奖励模型是拿人的偏好训的，而人偏好被赞同——模型会学到「顺着用户说」比「指出用户错了」得分更高
· 把偏好写进了模型：什么算好回答，最终由标注群体和标注规范决定
今天这一步已经不止一种做法
上面这套「先训一个奖励模型、再用强化学习去调」是最早也最经典的路线，代价是要多训一个模型，而且强化学习那一段调起来并不稳。后来出现了直接拿成对偏好数据去调模型的做法（DPO 一类），把奖励模型这一环整个跳过，工程上简单得多，如今用得很广。
但换掉的只是「怎么把偏好灌进去」，上面那四条代价一条都没换掉——只要监督信号最终来自人的偏好，迎合、过度拒绝、标注群体的影响就都还在。

chat 有了，下一个缺口：它不会「想」

对话形态解决了「怎么把话说出来」，但没解决「怎么把事想清楚」。经典的失败长这样：
问：食堂原有 23 个苹果，用掉 20 个后 又买了 6 个，现在有几个？ 直接回答 答：27 个。　　　　　　　　✗ 加一句「请一步步思考」 答：原有 23 个，用掉 20 个还剩 3 个， 又买了 6 个，3 + 6 = 9。 现在有 9 个。　　　　　✓
同一个模型，同一道题。差别只在于允不允许它把中间步骤写出来。
为什么会这样：一个结构性的限制
模型每生成一个词元，就是把输入过一遍那 N 层网络——层数是固定的，题目再难也不会多给它几层。

所以：如果答案必须一步吐出来，那么这道题能用的全部计算，就压在生成那一个词元的这一次前向里。

而写出中间步骤，等于把推理摊在几十上百个词元上——每多写一个词元，就多过一遍完整的网络。可用的计算量是按词元数量线性增加的。
还有第二重作用
写出来的中间步骤会进入后续词元的上下文，成为模型自己能看到的输入。「还剩 3 个」这句话一旦写出来，后面就可以直接用它，不必在一次前向里凭空存住。

相当于把要记的东西挪到了纸面上。
顺着这条限制，能推出两件事
一、能摊开的题才吃得到这个红利。让它张口就报 47×83，整个乘法得挤在一次前向里做完，很容易错；让它列竖式，同一个模型基本不会错——竖式把这道题摊成了几十个词元，每个词元都换来一次完整的前向。

二、多写词元买到的是计算量，不是知识。它本来就不知道的事实，推理链再长也推不出来，只会把这个空缺包装得更像模像样。缺计算，写长点有用；缺信息，写多长都没用。

思维链：从提示技巧到训进模型里

思维链（Chain of Thought）这件事，经历了三个明显不同的阶段。理解这三阶段，比记住「让它一步步思考」这句咒语重要得多。
① 举例子诱导
在提示里放几个带完整推理过程的示范题，模型照着这个格式续写，自然也会写出推理过程。

代价：每次请求都要带上这些例子，占上下文、花钱；而且例子的写法很影响效果。
② 一句话触发
发现根本不用给例子，加一句「让我们一步一步来思考」就能触发同样的行为。

原因：这类措辞在训练语料里高度关联着详细的推导文本，这句话把模型引到了那个分布上。

代价：不稳定，靠措辞碰运气。
③ 训练进模型
既然「先推理再回答」普遍更好，就直接用大量带推理过程的数据去训练，让模型默认就这么干，不必用户提示。

进一步地，用「最终答案对不对」作为奖励信号去强化——让模型自己摸索出什么样的推理路径更容易得到正确答案。
代价这一栏，第三阶段最值得说
推理过程要占大量输出词元，而输出词元是最贵的。一道题的成本可能是直接回答的十几倍，延迟也一样。所以现在的产品普遍会按任务难度决定要不要展开推理——简单问题上强行推理是纯浪费。
一个要打破的误解
写出来的推理过程不保证是模型内部真实的计算路径。它是生成出来的文本，可能出现「过程有错但答案对」或「过程看着对但答案错」。

把它当作可读的中间产物，不要当作可信的解释。
第三阶段还带来一个计费上的变化
训进模型之后，推理写不写、写多长是模型自己定的，你事先并不知道这一次要花多少；而这部分词元按输出计费，是价目表上最贵的一档。
更麻烦的是可见性：不少接口只把推理过程的摘要返回给你，原始的那一大段看不到，但照样计进账单。所以做成本估算时，按「问题多长、答案多长」去算会严重偏低——中间那段看不见的才是大头。

推理模型：把「多想一会儿」变成一个能调的旋钮

第三阶段训到最后，出现了一类新模型：它默认先花大量词元自己想，想完了才开口。
多了一条加能力的路
以前想让它更强只有一个办法——把模型练大，投入以亿计、周期以月计。现在多了一条：同一个模型，在回答时多花算力。这条路按次付费、随时可调，不用等下一代模型。
是训出来的，不是提示出来的
长思维链里模型会自己说「等一下，这里不对」，会验算、会推翻重来。这套行为来自用「最终答案对不对」当奖励的训练——不是你在提示里写「一步步思考」能换来的。
它成了你手上的一个参数
客户端和接口上那个 thinking / reasoning effort 档位，调的就是允许它想多久。第一章那些配置项里，这一个对效果和账单的影响都最大。
什么时候该开，什么时候是纯浪费
值得开：数学、代码调试、多步规划——对错能被判定、且一步想不完的题。　纯浪费：翻译、改写、分类、闲聊，把账单和延迟乘十几倍换不来任何提升。另外，写出来的思考过程仍然不保证是它真实的计算路径——当中间产物看，别当解释看。

会想了，但想的全是脑子里的东西

纯推理撞到的三堵墙
  • 知识是冻结的。模型的知识停在训练数据的截止时间。问它今天的事，它要么说不知道，要么编一个——而且编得很像真的。
  • 推理链会跑偏且无从纠正。中间某一步错了，后面全部建立在错误之上。它没有任何外部参照可以发现自己错了。
  • 它不能改变任何东西。推理再漂亮，输出的还是一段文本。文件没被改、邮件没被发、代码没被跑。
缺的东西可以一句话概括
它缺一条通往外部世界的通路——既包括读（获取它不知道的信息），也包括写（对世界产生影响）。

而且这条通路必须嵌进推理过程里，不能是「先查完再推理」。因为它经常是推到一半才发现自己缺什么。
从这里开始，性质变了
前面三步（预训练、对齐、思维链）都是在改造模型本身。

从这一步开始，重点转到模型和外部之间的关系——模型怎么表达它想做什么，谁来执行，结果怎么回来。

这也是「Agent」这个词开始有意义的地方。
这三堵墙不是同一类问题
你把今天的新闻贴进上下文，第一堵墙就矮了一截；把参考答案也贴进去，第二堵也能挡一挡。但第三堵挡不住——不管往里塞多少东西，它的输出仍然只是一段文本：文件没被改、代码没被跑。

所以下一步补的是「能不能动手」，不是「知不知道」。前者是结构上缺一块，后者只是喂得够不够。

ReAct：把「想」和「做」交替起来

ReAct 的做法非常朴素：在提示词里教模型按固定格式交替输出「思考」和「行动」，然后由外部程序把行动的结果贴回去。
Thought: 我需要知道这家公司现任 CEO Action: search["某公司 CEO"] ─── 以下由外部程序填入 ─── Observation: 现任 CEO 为 …… Thought: 还需要知道其任职起始时间 Action: search["某公司 CEO 上任时间"] ─── 以下由外部程序填入 ─── Observation: 于 ×××× 年就任 Thought: 信息齐了，可以作答 Action: finish["……"]
循环是怎么转起来的
① 模型续写到 Action: 那一行
② 外部程序把生成停下来，用字符串解析把动作名和参数抠出来
③ 外部程序真的去执行（当年多半就是调一个 API）
④ 把结果拼成 Observation: 一行，接到文本后面
⑤ 让模型接着续写

模型全程只做了一件事：续写。停下来、解析、执行、贴回去——全是外面那个程序干的。
它解决的问题
推理不再是闭门造车：每一步都可以拿外部的真实结果来校正。同时，「行动」这个环节让模型第一次能对外部产生影响。

Agent 那个「思考 → 行动 → 看结果」的循环，形态在这里就定下来了。
这是 2022 年的做法，但形态一直留到了今天
当时接口层什么都没有：没有工具定义的格式，没有存放调用参数的字段，模型也没被训练过要遵守任何约定。手上只有提示词，于是只能约定几个关键词，再让外面的程序去做字符串匹配。

今天你在各种框架里看到的「思考 → 调用 → 看结果」，形态就是在这里定下来的。后来换掉的其实只有中间那一步：解析不再靠猜，改成接口来保证。

ReAct 全靠自觉，代价在这里

整套机制建立在一个假设上：模型会老老实实按你约定的格式输出。而这个假设不成立的时候比你想的多。
格式随时会破
模型可能写成 Action：（中文冒号）、可能把参数的引号漏掉、可能在 Action 后面又多写了一段解释。

解析靠的是字符串匹配，一破就整轮失败。
参数没有类型
动作参数就是一段自由文本。该传数字它传了中文描述，该传日期它传了「下周三」——没有任何东西能在调用之前拦住它。
工具说明只能写在提示里
有哪些工具、各自怎么用，全部写成散文塞进提示词。工具一多，这段提示会长得吓人，而且每一轮都要重发一遍。
停不住
要靠外部程序盯着输出流，一看到 Observation: 就强行截断，否则模型会自己把观察结果也编出来，然后基于幻想的结果继续推理。
把问题归纳一下
这四条其实是同一件事的四个面：「模型想调用什么」这件事，是用自然语言表达的，而自然语言没有任何结构保证。

解法的方向因此很清楚——把它变成有结构的、模型被训练过要遵守的、接口层面就能校验的东西。
这四条今天并没有消失，只是换了地方
支持工具调用的模型和接口把它们大部分接管了。但只要你绕开接口自己搭一套，四条会原样重来一遍——在提示词里写「请用 JSON 回复，格式如下」，然后自己去解析模型吐出来的那段文本：格式会破、参数没类型、说明得每轮重发，它还会顺手把结果一起编出来。
判断方法很简单：看「模型想调用什么」这件事，走的是接口里一个有结构的字段，还是一段需要你自己去猜的自然语言。是后者，这一页的四条你一条都躲不掉。

工具调用：把这件事做进训练和接口

变化一：工具说明不再靠散文
工具变成接口上的一等参数——请求里有专门的字段声明有哪些工具、每个工具接受哪些参数、参数是什么类型。

模型在训练时就见过大量这种形式的输入，知道该怎么读它、怎么用它。
变化二：调用意图是结构化输出
模型不再吐一行 Action: search[...]，而是输出一个结构化的调用意图：工具名一个字段，参数一个字段，还带一个调用标识用来和结果配对。

响应里还会带一个明确的状态，告诉宿主「我这轮不是在说话，是在请求调用」——不用再猜、不用再截断。
变化四：格式还能被硬性锁死
训练只让它倾向于照格式来，仍然会偶尔多个逗号、少个引号。约束解码把这件事变成硬的：按照事先给定的结构，逐个词元算出「下一个合法的只可能是这几个」，其余全部置零再采样——不合法的输出在采样那一步就生不出来。这也是结构化输出今天能当接口用、而不只是「一般都对」的原因。
变化三：模型被专门训练过
什么时候该调工具、该调哪个、参数怎么填、拿到结果后怎么继续——这些都进了训练数据，不再依赖提示词里的示范。

这也解释了一个常见现象：没有经过这项训练的模型，接上去就是不会调工具，跟提示词写得好不好无关。
但有一件事一点没变
模型从不执行任何东西。

它输出的始终只是「我想调用 X，参数是 Y」这个意图。真正去发网络请求、去读文件、去跑命令的，永远是宿主程序——也就是你装在机器上的那个客户端。

结果拿回来之后，宿主再把它拼进上下文，让模型接着往下走。

这也解释了那个最让人恼火的现象：它说「已经处理好了」，其实什么也没发生。它输出的本来就只是文本——宿主没执行、或者执行失败没回传，它都无从知道，照样能续写出一句像模像样的完成汇报。

这条边界是后面所有权限设计、审批设计、安全设计的立足点：能不能做、准不准做，决定权在宿主手上，不在模型手上。

还有一层：工具结果回填进上下文之后，和你的系统提示词就是同一段无差别的文本——模型看不到「这段来自网页、那段来自你」。一份被读进来的文档里如果写着「忽略之前的指示」，它照样当指示读。提示注入的根就在这里。

一次完整往返，谁在做什么

这张图只画谁在什么时候做什么。中间那份「调用意图」和「结果」具体长什么样、字段怎么定义、由谁来写这份约定——是接口层的问题，本章不展开。

另外，图上为了看得清只画了一次调用。实际一轮里模型常常一次给出好几个调用意图，互不依赖的那些宿主会并发执行——这是把多步任务的墙上时间压下来的主要手段，也是「它看起来同时在查三个地方」的真实来源。

一次往返之外：这个圈转几十轮会发生什么

真实任务从来不是一次往返，是同一个圈转十几到几十轮。轮数一多，两个上一页看不见的问题就冒出来了。
① 模型说「做完了」
最常用，也最不可靠。它输出的只是文本——「我已经处理好了」和真的处理好了，在它那里没有任何区别。这句话只能当信号，不能当判据。
② 轮数 / 词元 / 时间上限
兜底闸门，必须有。没有它，一次解析失败就能让循环空转到把当天预算烧光。触发上限时要把现场留下来，别静默收工。
③ 人叫停
长任务必须留这个口子，而且要能在任意一轮中断，不是只能等它跑完。审批点具体卡在哪一步，是上生产时才需要细抠的事。
让它不越跑越歪，靠的是这三件事
插校验点：每隔几轮跑一次测试、编译或断言，把「我觉得对」换成「机器说对」。　能把错的那轮摘掉：错误结论留在轨迹里会被后面每一轮反复读到，越读越确信。　能拆就拆：20 步一口气跑完，不如拆成 4 段 5 步、每段都有验收——0.95²⁰ 很惨，但四个 0.95⁵ 各自补救，就完全不同了。

最后一个缺口：它凭什么认为自己干完了

ReAct 的 Observation 解决的是「拿外部结果校正推理」，不解决「这件事到底做成没有」。整条链上，这是最后一个、也是最少被讲清的缺口。
这条线，解释了一个你早就观察到的现象
为什么 Agent 在写代码上像换了个物种，在别的事情上还是那样？不是因为模型更懂代码，是因为代码这个领域自带一整套机器可判定的反馈——编译器、测试、类型检查、运行结果。它能自己跑、自己看红绿、自己改，一轮一轮往对的方向收敛。换成写一份市场分析，没有任何东西能告诉它错了。
判据现成的
写代码：跑测试、看编译。让它每改完一处就自己跑一遍，红了接着改——这是今天 Agent 最靠谱的用法。
判据要自己造
查数据：让它把 SQL 和命中行数一起交出来，你能复算；而不是只丢给你一句「已核对，共 47 条」。
判据造不出来就别装
写东西、做判断：明确把人放进环里。硬让它自评，只会得到一个它自己也不信的「已完成」。

横向的那条线：上下文工程

前面五步是纵向的链条，一步接一步。上下文工程不在这条链的任何一环上——它横穿全部五步。
为什么它是横向的
因为不管走到哪一步，模型每一次前向计算唯一能看到的东西，就是那段输入文本。

· 对话历史 —— 是上下文
· 思维链写出来的推理 —— 是上下文
· 工具的定义和调用结果 —— 是上下文
· 系统提示、检索来的资料 —— 都是上下文

每一步补上的能力，最终都要落到「往上下文里放什么」这件事上。
一次 Agent 请求的上下文里都有什么
系统提示角色、规则、输出约定
工具定义有哪些工具、怎么用
检索来的资料文档片段、代码片段
对话历史之前的往返
本轮的执行轨迹推理、调用、结果，逐轮累积
当前指令用户这次说的话
这里有一个硬约束
上面这些东西共用同一个上下文窗口，而窗口是有限的。

更要命的是它们互相挤占：工具定义多占 5K，能留给资料和历史的就少 5K。上下文工程本质上是一个预算分配问题——而且是每一轮都在变的预算。
还有一条和钱直接相关：前缀缓存
上面这张表最终是按顺序拼成一段文本的。推理服务会把算过的前缀缓存住，下一轮命中就不必重算——命中的那部分又便宜又快。

代价是它只认前缀：开头改一个字，后面全部作废。所以不变的放最前（系统提示、工具定义），每轮都在变的放最后，别在系统提示里塞当前时间这种每轮都不一样的东西。

四种操作，把预算管起来

写出去
把不必每轮都看的东西移出上下文，存到外面——笔记文件、任务清单、中间产物落盘。

需要时再读回来。

典型：让 Agent 把计划写进一个文件，而不是让计划一直挂在对话里被反复重发。
选进来
每一轮只把这一轮真正需要的东西放进去。

· 按需检索相关文档，而不是全塞
· 工具多的时候按需加载工具定义
· 只带相关的历史片段

典型：让 Agent 自己去读文件，而不是预先把整个代码库塞给它。
压缩
历史长到装不下时，把旧的部分总结成一段摘要，用摘要替换原文。

风险：摘要必然丢信息，而且丢掉的往往是当时看着不重要、后来才要用的细节。

好的做法是保留关键决定和未完成事项的原文，只压缩过程叙述。
隔离
把任务拆给各自独立上下文的多个执行单元，每个只看自己那一摊，最后把结果汇总。

好处：单个上下文不会被撑爆，互相之间也不会干扰。

代价：它们看不见彼此，容易重复劳动或做出互相矛盾的决定。
这四种操作解决的是同一个矛盾
模型需要足够的信息才能做对事，但信息越多它越容易做错事。——不只是装不下的问题，塞太多本身就会降低效果。下一页说这个。
这四件事，没有一件是模型自己会做的
上下文里放什么、什么时候该把历史压掉、哪一段该拆出去，全部由宿主侧的代码决定。模型只会读你递给它的那一段文本然后续写——它看不到被你写出去的笔记，也不知道自己刚被压缩过。

所以「上下文工程」这个名字里的工程两个字是实的：它是你要写的调度逻辑，不是一句更好的提示词。
实际用起来是四种混着上
一次任务里通常是：计划一开始就写出去落成文件，资料按需选进来，历史长了做一次压缩，要读大量原文的活隔离出去单独跑。

次序上有个经验：能不放进来的就别先放进来——「选进来」做得好，后面三种操作的压力都会小很多；反过来先塞满再拼命压缩，丢的信息最多。

塞满上下文为什么反而更差

「窗口有 200K，那我就塞 200K」——这是最常见也最贵的误解。
中间的内容会被忽略
把关键信息放在很长上下文的中段，模型找到它的概率明显低于放在开头或结尾。

这不是它偷懒——注意力权重要分给全部位置，位置越多，每个位置能分到的注意力越稀薄。

实用推论：最重要的指令放最后，最稳定的内容放最前。
无关内容会干扰判断
上下文里有一段和当前任务无关但看起来相似的内容，模型很可能被它带偏——它没法可靠地区分「这段是给我参考的」和「这段是噪声」。

尤其是过时的旧版本代码、被推翻过的早期结论。
错误会被自己滚雪球
Agent 的执行轨迹会一直留在上下文里。如果第 3 轮做了个错误判断，它会作为「事实」被第 4、5、6 轮反复读到，越读越确信。

人类会怀疑自己的旧结论；模型看到的只是上下文里写着的东西。
所以这一节的判断标准是这句
上下文工程不是「怎么塞进去更多」，是「怎么让该在的在、不该在的不在」。

这条判断在你自己搭 Agent 时会反复用到——每次想往提示里再加一段之前，先问：这段东西不在的话，模型这一步会不会做错？不会，就别加。
这三条都不用靠感觉，是能测出来的
把同一个任务跑三组——原样一组、把关键指令挪到最后一组、把明显无关的资料删掉一组，每组各跑十次，比成功率。差别通常大到不需要统计学就能看出来。
另外值得单独测一次的是工具定义：把这一轮用不上的工具从定义里摘掉，看成功率变不变——工具一多，模型选错工具的概率涨得比想象中快。
做过这一遍你多半会发现一件反直觉的事：删掉东西带来的提升，常常比再加一段说明更大。而加东西是所有人的第一反应，删东西不是。

子 Agent：什么时候该把任务拆出去

上一页说了塞满会变差。最直接的解法往往不是压缩，是不让一个上下文承担全部——把一段活连同它要读的东西一起交出去，只把结论收回来。
什么时候值得拆
子任务要读很多东西，但只需要交回很少的结论——查资料、扫一遍代码库、把十个文件各看一眼。读进去的原文留在子上下文里，主上下文只多一段话。
什么时候不该拆
子任务之间需要互相看见的时候。它们各说各话，你拿到三段互相矛盾的结论也没法判谁对。另外：拆一次多一次调用，账单和延迟都往上走。
交代得写清楚
子 Agent 看不见你和主 Agent 说过的任何话。任务、判定标准、要交回什么格式，都得在派它出去的那一刻写明——交代不清，收回来就是一段没法用的自由发挥。
注意这里说的「子 Agent」是什么
是同一套系统里、主 Agent 自己开出来的执行单元——共用同一套工具、同一份权限、由同一个宿主调度，本质上是上下文的一种切分方式。至于两个各自独立、互不隶属的 Agent 之间怎么互相发现、怎么协作，那是接口层要定的另一套约定，不在本章范围内。

端到端走一遍：让它改一个 bug

前面每一节单独拿出来都不难。真实的样子是它们同时在起作用——用一个最常见的任务串一遍。
整个过程里模型只做了一件事
从头到尾，它都只是在反复地「读一段文本、写一段文本」。日志是宿主 grep 的，配置是宿主改的，测试是宿主跑的。你看到的那种「它在干活」的感觉，是宿主按它的意图把动作真的做了出来——这条边界一次都没有被跨过。
这一遍里，哪些是你能调的
思考档位开多高、上下文里留什么、多少轮之后必须停、拿什么当验收判据——这四件事全在你手上，和换不换模型无关。同一个模型，这四件事设得好不好，跑出来的结果可以差很远——「同样的模型，别人跑得动我跑不动」，多半就差在这里，不差在模型上。
换成一件没有测试的事，第 ⑦ ⑧ 步就不存在
整条链会在「它说改好了」这里断掉，后面全靠你自己看。能不能自动跑下去，取决于这件事有没有一个机器能判的判据——不取决于模型聪不聪明。这也是为什么同一个 Agent 在代码仓库里能连着跑几十轮，换到写材料上就只能一段一段交给你确认。

整条链回看：每一步补了什么，代价是什么

这一步上一步差什么这一步补什么代价
预训练没有任何语言能力用下一词预测这一个目标，把世界知识、语言、逻辑一起学进去算力和数据的门槛极高；知识冻结在训练截止点
对齐到对话只会续写，问它问题它接着编问题用对话模板 + 监督微调装上把手；用偏好比较调行为能力上有损耗；会过度拒绝；倾向于迎合用户
思维链答案一步吐出，难题的可用计算量被卡住把推理摊到多个词元上，同时把中间结论写成一段可读的文本输出词元大增，成本和延迟按倍数上去
ReAct推理全在脑内，拿不到外部信息也改变不了任何东西在提示词里约定思考与行动交替，由外部程序执行并回填结果格式随时会破、参数没类型、工具说明只能塞提示里
工具调用调用意图用自然语言表达，没有任何结构保证工具进接口、意图变结构化输出，并且模型被专门训练过依赖模型具备这项能力；接口本身要有一套约定
多轮循环（工程侧，不在链上）让这个圈自己转下去，并且规定它什么时候必须停每一步的出错概率按轮连乘，上下文越滚越长
自我验证（工程侧，不在链上）把「到底做成没有」交给机器判：测试、编译、断言判据造不出来的领域，只能把人放回环里
上下文工程（横向，不在链上）管理每一轮到底把什么放进那段有限的输入里压缩会丢信息、隔离会失去全局视野，没有免费的解法

这一章讲到哪儿为止

你现在应该能做到的
  • 说清一个只会预测下一个词的架构，是被哪五个具体缺陷推着变成会干活的系统的
  • 解释「对话」为什么本质上是宿主拼字符串拼出来的，以及为什么对话模板换错了模型会变差
  • 解释思维链为什么有效——它增加的是可用计算量，不是聪明程度
  • 说清工具调用把 ReAct 靠自觉维持的那套，落进了训练和接口里——但循环本身没变
  • 说出模型和宿主的那条边界：模型只输出调用意图，执行的永远是宿主
  • 说清这个圈为什么必须由外面规定它什么时候停——每一步的成功率是连乘的，二十轮之后 0.95 会变成 0.36
  • 说清「它凭什么认为自己干完了」：判据能不能被机器判，决定了这件事能不能放手让它自己跑——这也是同一个 Agent 在代码上能连轴转、换到写材料就只能一段一段等你点头的原因
这一章刻意停在这里
工具调用这一节讲到「模型能输出调用意图、执行的是宿主」就停了。下面这些明确不在本章范围内：

· 那份调用意图具体长什么样——字段怎么定义、参数的类型约定怎么写、真实报文的结构
· 工具是怎么被接上来的——它可以是宿主里内置的一个函数，也可以来自一个外部服务，这中间有一整套约定
· 多个 Agent 之间怎么互相委派

这些属于接口怎么定义与传递的范畴，是独立的一层，需要单独讲。

本章交付的是：能力是怎么一步步长出来的。接口层怎么组织，是另一个问题。
如果只带走一句话
从 Chat 到 Agent，模型本身并没有发生质变——变的是它周围那一圈东西：怎么把历史拼给它、怎么让它先想再答、怎么把它的输出接到真实动作上、怎么在窗口装不下时挑该留什么。
所以当一个 Agent 表现不好时，先怀疑的应该是这一圈，而不是模型不够强——这一圈里能改的东西，比换模型多得多，也便宜得多。
