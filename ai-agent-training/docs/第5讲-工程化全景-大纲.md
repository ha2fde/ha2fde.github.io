# —— 模块A：能力支柱 ——

## P04 第2章·上：Agent 完整能力拼图（核心图）

**① 疑惑**：Agent 不就是"思考→行动→观察"的循环吗，还缺什么？
**② 回答**：核心循环只是发动机。要上路，还需要六根支柱撑起整个车身。

**③ 拼图（核心循环居中、六支柱围绕）**：

```
                 ┌───────────┐
                 │  记 忆     │  记得住：跨会话记住上下文
                 └───────────┘
   ┌───────────┐                ┌───────────┐
   │  安 全     │                │  治 理     │
   │ 守得住：防攻击越权│          │ 管得住：审计审批成本│
   └───────────┘                └───────────┘
        │      ┌─────────────┐      │
        │      │  核心循环    │      │
        │      │ 思考→行动→观察│      │
        │      └─────────────┘      │
   ┌───────────┐                ┌───────────┐
   │  观 测     │                │  评 测     │
   │ 看得见：每步可追踪│          │ 量得出：质量可持续衡量│
   └───────────┘                └───────────┘
                 ┌───────────┐
                 │ 人机协同   │  信得过：关键闸口留给人
                 └───────────┘
```

**④ 落地提示**：做技术选型时，先问"这六根支柱各自用什么组件承接"，而不是先选模型。

---

## P05 第2章·下：六大支柱一句话速览

**① 疑惑**：六根支柱分别解决什么问题，先有个全貌。
**② 回答**：一句话记住每根支柱——后面四章逐个展开。

**③ 速览表**：

| 支柱 | 解决什么问题 | 一句话 | 常见承接组件 |
|---|---|---|---|
| 记忆 | 会话结束就"失忆" | 短期靠上下文，长期靠外部存储 | 向量库 / 文件 / 数据库 |
| 安全 | 会干活就可能"被带坏" | 防注入、防越权、防泄露 | 沙箱 / 白名单 / 最小权限 |
| 治理 | 出了事说不清、管不住 | 可审计、可审批、可算账 | 审计日志 / 审批流 / 配额 |
| 观测 | 黑盒运行，出问题无法定位 | 每一步调用都可追踪 | Trace / 日志 / 成本监控 |
| 评测 | 改了prompt不知道变好变坏 | 用基准和回放持续衡量 | 评测集 / 回放用例 / 指标 |
| 人机协同 | 全自动不放心 | 关键决策留"人确认"闸口 | 确认节点 / 人工接管通道 |

**④ 落地提示**：六支柱不要求一步到位，但上线前每根至少要有"最小可用版本"。

## P06 第3章：记忆——让 Agent 记得住

**① 疑惑**：上下文窗口越来越大，还需要单独做"记忆"吗？
**② 回答**：需要。窗口再大也是"短期记忆"，跨会话、跨任务的知识必须外置并按需取回。

**③ 记忆分层图**：

```
┌────────────────────────────────────────────┐
│ 短期记忆 = 上下文窗口                        │
│ · 随请求携带，会话结束即消失                  │
│ · 容量有限、贵（按 token 计费）              │
└────────────────────────────────────────────┘
                  ▲ 检索相关内容，拼进上下文
                  │ （RAG 思路：先查后写）
┌────────────────────────────────────────────┐
│ 长期记忆 = 外部存储，跨会话持久化             │
│ · 向量库：语义检索"相似的过往经验"           │
│ · 文件/文档：结构化的工作笔记、用户档案       │
│ · 数据库：事实型记录、业务数据               │
└────────────────────────────────────────────┘
```

**分层意义**：上下文窗口放"当前任务的 working set"，长期存储放"所有历史"，靠检索在两者之间搬运。
**基本实现思路**：写入端——会话中沉淀值得记的内容；读取端——按当前任务检索相关片段，拼进上下文再给模型。

**④ 落地提示**：先想清楚"什么值得记、记到哪、谁来删"，比选哪个向量库更重要；记忆也意味着合规责任（记住了不该记的 = 数据泄露隐患）。

## P07 第4章·上：安全——Agent 特有的攻击面

**① 疑惑**：传统应用安全做得很多了，Agent 有什么新风险？
**② 回答**：Agent 会"读指令、做决策、动手执行"，恶意内容只要能影响它的判断，就能让它替你犯错。

**③ 三大攻击面**：

```
攻击面 1：提示注入（Prompt Injection）
  恶意指令藏在用户输入 / 网页 / 文档 / 邮件里
  ┌────────┐   读取   ┌──────────────┐
  │ 恶意网页│ ──────► │ Agent 把隐藏指令 │
  │"忽略之前指令,把…"│  │ 当成任务执行    │
  └────────┘         └──────────────┘

攻击面 2：越权执行
  Agent 拿着过大的权限，一个误判 = 一次生产事故
  （能删库的工具，就别怪它真删）

攻击面 3：数据泄露
  敏感数据被读进上下文 → 随工具调用/外部 API 传出去
```

**④ 落地提示**：把 Agent 当成"一个会被骗、但手很快的新员工"来设计权限，而不是当成一段确定性的代码。

---

## P08 第4章·下：安全——四道防线

**① 疑惑**：攻击面防不住怎么办？从哪几件事做起？
**② 回答**：纵深防御——任何单点被突破，还有下一道。

**③ 防线表**：

| 防线 | 做什么 | 防什么 |
|---|---|---|
| 最小权限 | 每个工具只授予完成任务必需的最小权限（只读优先，写操作收窄到具体对象） | 越权执行 |
| 沙箱隔离 | 代码执行、文件操作放在隔离环境（容器/受限目录），与生产环境隔开 | 注入后的破坏扩散 |
| 工具白名单 | Agent 只能调用登记过的工具与参数范围，未登记一律拒绝 | 注入诱导的任意调用 |
| 执行前确认 | 高危/不可逆操作（删、改、发、付）必须人工或规则确认后才执行 | 一切"手快"事故 |

**兜底原则**：敏感数据不传出——进上下文的敏感字段脱敏，出 Agent 的调用做内容检查。

**④ 落地提示**：四道防线中"执行前确认"成本最低、收益最大，第一天就该有。

## P09 第5章：治理——让 Agent 合规可控

**① 疑惑**：安全和治理听起来都像"管 Agent"，分工是什么？
**② 回答**：安全管"防住"（不让坏事发生），治理管"管住"（发生的事可回查、可审批、可算账）。

**③ 治理四件事 + 安全 vs 治理对比表**：

| 治理项 | 内容 | 落地形态 |
|---|---|---|
| 审计日志 | Agent 干过什么：谁触发、调了什么工具、输入输出、结果如何 | 全量留痕、可回查 |
| 审批流 | 高危操作需人批准才能执行 | 分级审批、与工单系统打通 |
| 合规要求 | 数据处理符合监管与内部制度（如 GDPR 类法规一句话：涉及个人数据即受约束） | 数据分级、留存策略 |
| 成本治理 | token 用量监控、消费上限、异常告警 | 配额 + 预算告警 |

| 维度 | 安全 | 治理 |
|---|---|---|
| 目标 | 防住：阻止坏事发生 | 管住：发生的事可控可溯 |
| 视角 | 攻击者视角（别人怎么害我） | 管理者视角（我怎么看住它） |
| 典型手段 | 沙箱、白名单、最小权限 | 审计、审批、配额 |
| 失效后果 | 被注入、越权、泄露 | 出了事说不清、算不清、停不下 |

**④ 落地提示**：审计日志是治理的地基——没有留痕，审批、合规、成本全是空中楼阁。

## P10 第6章·上：观测——每一步都看得见

**① 疑惑**：Agent 说"任务失败了"，怎么知道它卡在哪一步？
**② 回答**：把 ReAct 循环的每一步都落成 trace：调了哪个工具、输入什么、输出什么、花了多少 token。

**③ Trace 示意图**：

```
一次任务执行 = 一条 Trace
┌──────────────────────────────────────────────┐
│ Step 1  思考:需要先查订单   → 工具: query_order │
│         输入:{order_id}  输出:{...}  12ms  320tok│
│ Step 2  思考:需要退款审批   → 工具: request_appr│
│         输入:{...}  输出:{待审批}   8ms  210tok │
│ Step 3  思考:等待人工确认   → 状态: PAUSED      │
└──────────────────────────────────────────────┘
          三条监控线：Trace(步骤) · 日志(事件) · 成本(token/费用)
```

**观测三件套**：Trace 看"过程"、日志看"事件"、成本监控看"账单"。

**④ 落地提示**：观测是后面"评测"的数据来源——没有 trace 积累，评测集和回放用例都无从谈起。

## P11 第6章·下：评测——没有评测就谈不上上线

**① 疑惑**：改了 prompt 或换了模型，怎么证明 Agent 变好了而不是变坏了？
**② 回答**：靠持续评测：基准测试定水平，回放用例防回归，用指标说话。

**③ 评测闭环**：

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 建评测集  │ → │ 基准测试  │ → │ 回放用例  │ → │ 指标看板  │
│ 真实任务+ │   │ 新版本跑一 │   │ 历史trace │   │ 任务完成率│
│ 期望结果  │   │ 遍,比基线 │   │ 重放防回归│   │ 错误率/成本│
└──────────┘   └──────────┘   └──────────┘   └──────────┘
      ▲                                            │
      └──────────── 不达标 → 改 prompt/模型 → 重新评测 ──┘
```

**核心指标**：任务完成率、错误率（幻觉/误调用）、平均步数、单任务成本。
**一句话**：没有评测，"迭代"就是掷骰子；有评测，每次改动才敢上线。

**④ 落地提示**：评测集不必大，从 20~50 个真实高频任务开始，比追求覆盖面更重要。

# —— 模块B：协议生态 ——

## P12 第7章：为什么需要协议

**① 疑惑**：工具对接写点适配代码不就行了，为什么要"协议"？
**② 回答**：N 个 Agent × M 个工具 = N×M 套专用代码；标准化后变成 N+M——接一次，处处可用。

**③ 对比图**：

```
没有协议：N×M 灾难                有了协议：N+M
┌─────┐ ╲  ┌────┐               ┌─────┐    ┌────────┐    ┌────┐
│Agent1│ ╲ ╲│工具A│              │Agent1│───┐│        │┌───│工具A│
│Agent2│──╲─│工具B│              │Agent2│───┤│ 标准协议 │├───│工具B│
│Agent3│─╲ ╲│工具C│              │Agent3│───┘│        │└───│工具C│
└─────┘  ╲ ╲└────┘               └─────┘    └────────┘    └────┘
 每对组合一套专用代码              各自只实现一次标准接口
```

**④ 落地提示**：这就是为什么 MCP / Skills / A2A 会出现——它们不是新概念发明，是工程量倒逼出来的标准。

## P13 第8章·上：四层协议全景（本模块核心图）

**① 疑惑**：MCP、Skills、A2A、Function Calling 满天飞，它们谁管哪层？
**② 回答**：各管一层、互不重叠——从"模型怎么调工具"到"Agent 怎么够 Agent"，一层一个标准。

**③ 四层协议图**：

```
┌────────────────────────────────────────────────┐
│ 互连层  A2A (Agent2Agent)                       │
│         Agent 之间互相发现、通信、协作           │
├────────────────────────────────────────────────┤
│ 流程层  Agent Skills                            │
│         把"怎么完成一类任务"打包成可复用技能      │
├────────────────────────────────────────────────┤
│ 工具层  MCP (Model Context Protocol)            │
│         Agent 与外部工具/数据源的统一接入协议     │
│         类比："工具的 USB 接口"                  │
├────────────────────────────────────────────────┤
│ 模型层  Function Calling / Tool Use             │
│         各家 API 原生的"模型请求调工具"机制      │
└────────────────────────────────────────────────┘
        越往下越靠近模型，越往上越靠近生态
```

**④ 落地提示**：记住一句话——Function Calling 是机制，MCP 标准化"够工具"，Skills 封装"怎么干"，A2A 解决"够 Agent"。

## P14 第8章·下：四层协议对比表

**① 疑惑**：四层分别标准化了什么"东西"？
**② 回答**：模型层标准化"调用格式"，工具层标准化"工具接入"，流程层标准化"任务做法"，互连层标准化"Agent 间协作"。

**③ 对比表**：

| 层 | 协议 | 标准化的对象 | 谁提出/推动 | 一句话定位 |
|---|---|---|---|---|
| 模型层 | Function Calling / Tool Use | 模型请求调工具的格式 | 各家模型厂商原生 | "模型想调工具"的原生机制 |
| 工具层 | MCP | Agent ↔ 工具/数据源的接入 | Anthropic 提出并开源，主要厂商跟进 | 工具的 USB 接口 |
| 流程层 | Agent Skills | 完成一类任务的步骤+提示词+脚本 | Anthropic 等推动的开放标准 | 把"怎么干"打包复用 |
| 互连层 | A2A | Agent ↔ Agent 的发现与通信 | Google 提出 | Agent 够 Agent |

注：各协议归属与进展变化快，一律以官方/标准组织最新公告为准。

**④ 落地提示**：四层不是竞争关系而是互补关系——一个成熟系统通常会同时用到其中三层以上。

## P15 第9章·上：MCP 来龙去脉——为什么是它

**① 疑惑**：工具接入方案那么多，为什么行业共识落在 MCP 上？
**② 回答**：它踩中了三个点：开放开源、厂商中立、恰好出现在 Agent 爆发、所有人都被 N×M 问题折磨的时间窗口。

**③ 演进脉络**：

```
Function Calling（单点工具调用）
      │  各家格式不一，接工具要写专用代码
      ▼
MCP（工具接入标准化）
      │  Anthropic 提出并开源 → OpenAI / Google / Microsoft
      │  等主要厂商相继采纳 → 进入标准化托管
      ▼
Skills（流程封装）→ A2A（Agent 互联）
      一层层从"一个工具"走向"整个生态"
（具体归属与最新进展以官方 / Linux 基金会消息为准）
```

**④ 落地提示**：系列《破冰指南》份已讲过 MCP 基本概念，本份记住结论——它是当前工具接入的事实标准方向，投入适配不亏。

## P16 第9章·下：MCP 基本结构

**① 疑惑**：接入 MCP，系统里到底多了哪些角色？
**② 回答**：两个角色一种语言——Server 提供能力，Client（Agent 侧）消费能力，之间用 JSON-RPC 通信。

**③ 结构图**：

```
┌──────────────────┐          ┌──────────────────┐
│   MCP Client     │          │   MCP Server A   │
│   (Agent 侧)     │──JSON-RPC──► 工具 / 资源 / 提示词 │
│                  │          └──────────────────┘
│  · 发现可用工具    │          ┌──────────────────┐
│  · 发起调用       │──JSON-RPC──►   MCP Server B   │
│  · 拿到结果进上下文│          │ 另一个工具/数据源  │
└──────────────────┘          └──────────────────┘
 Server 提供三类能力：
 · 工具(Tools)：可执行的动作    · 资源(Resources)：可读的数据
 · 提示词(Prompts)：预置的交互模板
```

**④ 落地提示**：接新工具时优先找现成 MCP Server；自己封装 Server 时，工具粒度宁细勿粗——描述写得越清楚，Agent 调得越准。

## P17 第10章：Agent Skills——封装"怎么干一件事"

**① 疑惑**：工具都能调了，为什么还需要"技能包"？
**② 回答**：MCP 回答"能调什么工具"，Skills 回答"这件事怎么干"——把步骤、提示词、配套脚本打包，Agent 按任务加载。

**③ 结构 + 对比表**：

```
一个 Skill = 一个带元数据的目录
┌────────────────────────────┐
│ 元数据：名称 / 说明 / 触发条件 │ ← Agent 据此判断"何时用"
│ 步骤文档：完成任务的流程指引   │ ← 告诉 Agent "怎么干"
│ 配套脚本：确定性环节直接执行   │ ← 能写死的就别让模型猜
└────────────────────────────┘
```

| 维度 | MCP | Agent Skills |
|---|---|---|
| 封装对象 | 工具与数据（"能调什么"） | 流程与方法（"怎么干"） |
| 形态 | 在线服务，Client/Server 通信 | 目录+文档+脚本，按需加载 |
| 复用粒度 | 单个能力 | 一整类任务 |
| 关系 | 互补：Skill 的步骤里可以调 MCP 工具 | 互补：Skills 是 MCP 之上的方法论 |

**④ 落地提示**：团队里"老师傅的经验"最适合沉淀成 Skill——流程写进文档、确定性环节写成脚本，模型只处理真正需要判断的部分。

## P18 第11章：A2A 与多 Agent 协作

**① 疑惑**：我公司有客服 Agent、财务 Agent、IT Agent，它们怎么互相派活？
**② 回答**：靠 A2A——Agent 之间互相发现、发任务、交换结果的协议；和 MCP 的区别一句话：MCP 是"Agent 够工具"，A2A 是"Agent 够 Agent"。

**③ 示意图 + 其他标准一句话表**：

```
┌──────────┐   发现/委派任务    ┌──────────┐
│ 客服 Agent │ ────A2A────────► │ 财务 Agent │
│ (团队A/厂商X)│ ◄────返回结果──── │ (团队B/厂商Y)│
└──────────┘                   └──────────┘
   跨团队、跨厂商的 Agent 协作，不必共享内部实现
```

| 标准 | 一句话定位 |
|---|---|
| OpenAPI | 传统 API 描述规范，工具接口的"老路子"，至今仍可作为底层描述 |
| AGNTCY | Cisco 主导的 Agent 互操作协议，与 A2A 并存竞争，格局以官方进展为准 |
| OAuth / 授权协议 | Agent 代表用户访问资源时的授权依据（"它是替谁在操作"） |

（A2A 已进入标准托管流程，具体以官方为准；本份不对比各家协议优劣，讲清定位与关系即可。）

**④ 落地提示**：多 Agent 协作前先想清"任务边界和结果契约"——协议解决通信，解决不了职责划分不清。

## P19 第12章·上：落地评估权威框架——Gartner AI 成熟度模型

**① 疑惑**：公司该从哪开始搞 Agent？凭感觉上还是有个章法？
**② 回答**：用业界公认的 Gartner AI 成熟度模型给自己"量体温"——Gartner 是独立第三方分析师机构，该模型是全球企业 IT 规划的行业标准参考，不绑定任何厂商生态。

**③ 模型结构图**：

```
        Gartner AI 成熟度模型 = 5 个级别 × 7 个支柱
┌─────────────────────────────────────────┐
│ 7 个评估支柱（每支柱按 1~5 级分别评估）：    │
│  1 AI战略与愿景   2 数据基础              │
│  3 治理与合规     4 技术架构与平台         │

│  7 文化与组织                             │
├─────────────────────────────────────────┤
│ 5 个成熟度级别：                           │
│  L1 认知 → L2 活跃 → L3 运营 → L4 系统化 → L5 变革 │
└─────────────────────────────────────────┘
   每个组织得到一张"7 支柱 × 级别"的雷达式体检单
```

**④ 落地提示**：不要只问"我们在第几级"，要按支柱分别问——数据基础在 L2、战略喊到 L4，是最常见的错位。

## P21 第13章·上：五级别详解

**① 疑惑**：每级的"典型状态"和"晋级动作"是什么？
**② 回答**：见表——先定位，再补课。

**③ 详解表**：

| 级别 | 一句话特征 | 典型状态 | 晋级动作 |
|---|---|---|---|
| L1 认知 | 认识到潜力但无正式战略 | 实验零散、依赖个别热情员工、无数据治理基础 | 建立高层共识，选定 1~2 个候选场景 |
| L2 活跃 | 孤岛式试点 | 爱好者驱动、缺乏统一战略与共享治理 | 把试点经验收编，立统一战略与最小治理 |
| L3 运营 | AI 整合进特定业务工作流 | 有明确用例与初步标准，数据实践开始规范化 | 扩展用例面，补齐平台与可观测性 |
| L4 系统化 | AI 驱动多数工作流 | 催生新数字化业务模式，AI 是运营根基而非工具 | 流程级重设计，组织与人才体系化 |
| L5 变革 | AI 深植企业 DNA | 持续驱动创新、新商业模式与文化转型 | 持续进化，保持组织敏捷 |

**④ 落地提示**：自评时找"最拖后腿的支柱"定级别，而不是找"做得最好的"——木桶效应在成熟度上格外灵验。

## P23 第13章·下：怎么用 + 风险警示 + 切入点

**① 疑惑**：评完级之后呢？以及，从哪些场景切入最稳？
**② 回答**：四步循环用起来；避开"跳级"这个失败主因；从高频、有数据、流程标准的场景切。

**③ 使用方式 + 警示 + 切入点**：

```
使用四步：
  按支柱对现状打分 → 定位当前级别 → 找与下一级的差距 → 制定针对性投资

⚠ 跳级是失败主因：
  跳过治理直接上自动化 = 同时踩中所有跳过的级别的坑
  Gartner 警示：相当比例（约 40%）的 agentic AI 项目
  可能因治理/观测/ROI 不清晰而被终止（数据以 Gartner 原文为准）
```

**五个典型切入点**（高频 + 数据已有 + 流程标准）：

| 场景 | 为什么适合先切 |
|---|---|
| 智能客服与工单 | 高频、流程标准、效果易量化 |
| 财务对账与报表 | 规则明确、数据现成、人力消耗大 |
| 知识管理与 RAG 研究 | 数据已沉淀、试错成本低 |
| IT 告警分诊 | 高频重复、有历史工单可训练评测 |
| 编码 Agent | 工具链成熟、团队接受度高 |

**④ 落地提示**：第一个场景的成功标准是"跑通全流程 + 建立评测"，而不是"做得多惊艳"。
