你可能的疑惑 ｜ 调个大模型而已，为什么有「裸调 API / 用 SDK / 上框架」三种写法？
关键差异 ｜ 三条路线不是替代关系，是光谱——差别只在「样板代码谁写、循环谁管、状态谁存」。
路线帮你解决你要付出的代价
直接调 API零依赖、完全掌控、任何语言都能写请求体、tool_calls 解析、循环、重试全自己写

一句话 ｜ 先想清楚任务复杂度，再决定站在光谱的哪一格——下一页把光谱画出来。

你可能的疑惑 ｜ 框架里神秘的 Agent，底层到底在干嘛？
关键差异 ｜ 底层只有一次普通 POST：把 messages + tools 塞进请求体，从返回里找 tool_calls。
┌────────────────────────┐          ┌───────────────────────────────────┐
│ POST /chat/completions │                                  │ choices[0].message                │
│ messages: [...历史...] │                          ──→  │ ├ 有 tool_calls → 执行工具      │
│ tools: [...工具...]    │                                  │ │   结果回填 messages → 再 POST │
└────────────────────────┘          │ └ 无 tool_calls → 即答案        │
                                                              └───────────────────────────────────┘
一次普通 HTTPS 请求 —— Agent 的一切魔法，都是围绕这次 POST 的封装
import requests
resp = requests.post(
    f"{BASE_URL}/chat/completions",
    headers={"Authorization": f"Bearer {API_KEY}"},
    json={"model": MODEL, "messages": messages,
          "tools": tools})
msg = resp.json()["choices"][0]["message"]
if msg.get("tool_calls"): ...  # 全靠自己
  • 优点　完全掌控、零抽象、所见即所得
  • 缺点　循环 / 重试 / 流式全自己写
  • 何时用　一次调用、学原理、框架不适配的边缘场景
一句话 ｜ 所有框架底层都是这一个 POST——记住它，后面所有封装都不再神秘。

你可能的疑惑 ｜ SDK 和裸调 API 相比到底省了什么？是不是用了 SDK 就算会跑 Agent 了？
关键差异 ｜ SDK 只封装「怎么跟模型说话」（请求/流式/重试/类型），不封装「怎么思考」（循环与回填）。
裸调 API 你要管的                                   SDK 帮你管掉的
┌────────────────────┐        ┌─────────────────────────┐
│ 拼 JSON / header   │                            │ client.chat.completions │
│ 鉴权 / 超时 / 重试 │                            │ .create() 一把梭        │
│ SSE 流式解析       │                     ──→ │ 内置重试与超时          │
│ 解析返回 JSON      │                            │ stream=True 迭代器      │
│ 手写 Agent 循环    │                            │ 类型化 msg.tool_calls   │
└────────────────────┘        └─────────────────────────┘
✖ SDK 不管「流程」—— 循环与回填仍是你的代码 → 下一章
from openai import OpenAI
client = OpenAI(base_url=BASE_URL,
                api_key=API_KEY)
resp = client.chat.completions.create(
    model=MODEL, messages=messages,
    tools=tools)
msg = resp.choices[0].message
if msg.tool_calls: ...  # 流程仍自己写
一句话 ｜ SDK 省的是「通信样板」，不是「Agent 流程」——从 SDK 到 Agent，只差一个你亲手写的循环。

手写一个 Agent：ReAct 主循环核心结构

7/19
你可能的疑惑 ｜ ReAct 听懂了，写成代码长什么样？
关键差异 ｜ 所谓 Agent =「发消息+工具描述 → 有工具调用就执行回填，没有就输出」的 while 循环。
[messages] ──→ [LLM 推理] ──→ 要调工具吗?
   ▲              ├ 是 → [执行工具] → 结果回填 → 再推理
   │              └ 否 → [输出最终回答，结束]
   └────────── 循环继续

调试：每轮打印「调哪个工具 → 参数 → 回填」
messages = [{"role": "user", "content": task}]
llm = client.chat.completions.create
while True:
    msg = llm(model=MODEL, messages=messages, tools=tools).choices[0].message
    messages.append(msg)
    if not msg.tool_calls: return msg.content
    for c in msg.tool_calls:
        messages.append({"role": "tool", "tool_call_id": c.id, "content": run_tool(c)})
一句话 ｜ 全部秘密在 messages 的追加方式 —— 完整可跑版（含计算器工具）见附录脚本 sdk_react_demo.py。

框架化的通用 ReAct：声明工具即可，20 行 → 5 行

8/19
你可能的疑惑 ｜ 既然循环是固定的，为什么每个项目都要重抄一遍？
关键差异 ｜ 框架把「谁都一样」的循环收走了：你只声明模型和工具，循环、回填、异常处理全由执行器包办。
第 4 章：手写（~20 行）                               第 5 章：框架执行器（~5 行）
┌────────────────────┐          ┌─────────────────────┐
│ while True:        │                              │ create_react_agent( │
│   请求 LLM         │                      ──→  │   model, tools)     │
│   解析 tool_calls  │                              │ agent.invoke(task)  │
│   查表执行工具     │                              │                     │
│   回填 role='tool' │                              │ 循环 / 回填 / 异常  │
│   判断结束条件     │                              │ 框架全包            │
└────────────────────┘          └─────────────────────┘
from langgraph.prebuilt import (
    create_react_agent)
# 声明工具即可，循环框架全包
agent = create_react_agent(
    model, tools=[calc])
result = agent.invoke({
    "messages": [("user", "12*(3+4)=?")]})
一句话 ｜ 框架第一层价值 = 通用 ReAct 执行器；代价：行为细节藏进框架，调试要学会看它的日志。

更复杂的任务：ReAct vs Plan-and-Execute
开发 Agent：从直接调 API 到用框架编排
9/19
你可能的疑惑 ｜ 任务一复杂，ReAct「走一步看一步」走到迷路，怎么办？
关键差异 ｜ ReAct 把计划藏在模型脑子里（边想边做）；Plan-and-Execute 把计划变成显式对象（先规划、再执行、偏了可重规划）。
ReAct（边想边做）                                                   Plan-and-Execute（先谋后动）
┌────────────────────────────┐        ┌─────────────────────────────────┐
│ 想→做→看→想→做→看→答 │                                    │ ①规划：任务 → [步1, 步2, 步3] │
│ 每一步由最新观察决定       │                                    │ ②执行：步1✓ → 步2✓ → 偏离? │
│ 计划不可见，随时可变       │                                    │ ③重规划：改计划 → 继续执行    │
│ 适合：探索型、路径未知     │                                    │ ④汇总：各步结果 → 最终答案    │
│ 例：排查故障、开放式调研   │                                    │ 适合：可预分解的多步任务        │
└────────────────────────────┘        └─────────────────────────────────┘
一句话 ｜ 先问「任务的步骤在出发前能不能列出来」——能列用 Plan，列不出用 ReAct，真实系统常混用。

10/19
你可能的疑惑 ｜ 两种范式各有什么代价？怎么按任务特征选？
关键差异 ｜ 范式没有优劣，只有适配：看任务是否可预分解、能否容忍计划隐式。
维度ReActPlan-and-Execute
思考方式边想边做，计划隐式先谋后动，计划显式
计划修正每步天然可变通过「重规划」节点显式修正

适合任务探索型、步骤不可预知可预分解、步骤间有依赖
典型风险绕圈、跑偏不自知计划错了执行全错（需重规划兜底）
一句话走一步看一步先画地图再上路
一句话 ｜ 选错范式的代价比选错框架大 —— 先定范式，再选实现。
第 7 章
LangGraph：把流程画成图 —— Node / Edge / State
开发 Agent：从直接调 API 到用框架编排
11/19
你可能的疑惑 ｜ 范式一多、分支一多，while 里全是 if/else，怎么管？
关键差异 ｜ 不再用 if/else 描述流程，而是声明成图：节点是函数、边是流转规则、State 是共享数据。
if/else 写法（流程埋在代码里）                                LangGraph 写法（流程是显式的图）
┌──────────────────────────┐      ┌──────────────────────────────────────────────────┐
│ while True:              │                                │ START → plan → act → sum → END               │
│   if 该规划: ...         │                                │          ▲       │                             │
│   elif 该执行: ...       │                                │          └───────┘ 偏离? 回 plan 重规划 │
│   elif 该问人: interrupt │                                │ State={task, plan[], results[]}                  │
│   else: break            │                                │ 流程 = 画出来的，可断可回放                      │
│ 流程 = 脑补出来的        │                                └──────────────────────────────────────────────────┘
└──────────────────────────┘
g = StateGraph(AgentState)
g.add_node("plan", plan); g.add_node("act", act)
g.add_node("sum", summary)
g.add_edge(START, "plan"); g.add_edge("plan", "act")
g.add_edge("act", "sum")
app = g.compile(checkpointer=MemorySaver())
app.invoke({"task": task})  # 传 thread_id 即可断点续跑
  • 图的收益　断点恢复（checkpointer）、执行可回放
  • 　人审（interrupt）、可视化排错
  • 对比　if/else 把流程埋在代码里，图把流程变成资产
一句话 ｜ 图一旦显式化，断点恢复、回放、人审（interrupt）就是免费的 —— 完整示例见附录脚本 langgraph_plan_demo.py。

你可能的疑惑 ｜ 同一个任务，SDK 手写和 LangGraph 图编排的代码结构到底差在哪？
关键差异 ｜ SDK 手写 = 流程控制在你手里（循环+if/else）；LangGraph = 只写节点函数，流转由图接管。
SDK 手写（流程在你代码里）                                               LangGraph（流程在图里）
┌─────────────────────────────────┐   ┌────────────────────────────────────────┐
│ while 循环                      │                                    │ START → router(LLM 决定去哪)          │
│   ├ LLM 决定下一步             │                                    │                 ├→ calc_node ─┐    │
│   ├ if 要算数 → calc()        │                                    │                 └→ dict_node ─┤    │
│   ├ if 要查词 → dict_lookup() │                                    │                                  ▼    │
│   └ 结果回填，继续循环         │                                    │                      merge_node → END │
│ 结束条件：自己判断              │                                    │ State={expr, calc, word, answer}       │
└─────────────────────────────────┘   └────────────────────────────────────────┘
# 写法A：SDK 手写（节选）
while True:
    msg = call_llm(msgs, tools)
    if not msg.tool_calls: break
    msgs += run_tools(msg)
print(msg.content)
# 写法B：LangGraph（节选）
g = StateGraph(S)
g.add_node("calc", calc); g.add_node("dict", lookup)
g.add_node("merge", merge)
g.compile().invoke({"expr": "23*47"})
一句话 ｜ A 的每一行你都能改，B 的每个节点你都能换 —— A 赢在小任务，B 赢在任务会长大。

步骤做什么要点
① 定义任务与边界明确输入/输出，什么坚决不做边界比能力更重要
② 列出所需工具每个工具一句话：名字、参数、返回工具描述质量决定一半效果
③ 选流程范式可预分解 → Plan；探索型 → ReAct见第 6 章对照表
④ 选实现层级API / SDK / 框架按第 8 章决策树走
⑤ 实现 + 打印中间步骤每轮「调了什么、参数、结果」必须可见看不见中间步骤 = 无法调试
⑥ 加安全护栏工具白名单、参数校验、轮次/成本上限护栏先于上线
⑦ 观测与迭代记录轨迹，按失败案例反哺提示词与工具90% 问题出在工具描述和任务边界
一句话 ｜ 90% 的问题出在工具描述和任务边界，不在框架 —— 别急着换框架，先看轨迹。
