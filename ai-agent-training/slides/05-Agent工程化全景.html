六大支柱一句话速览

你可能的疑惑六根支柱分别解决什么问题？先有个全貌。
支柱解决什么问题一句话常见承接组件

05/26

记忆：让 Agent 记得住

你可能的疑惑上下文窗口越来越大，还需要单独做"记忆"吗？

需要。窗口再大也是短期记忆；跨会话、跨任务的知识必须外置，并按需取回。

┌──────────────────────────────────────────┐
│ 短期记忆 = 上下文窗口                      │
│ · 随请求携带，会话结束即消失                │
│ · 容量有限、贵（按 token 计费）            │
└──────────────────────────────────────────┘
              ▲ 检索相关内容，拼进上下文
              │ （RAG 思路：先查后写）
┌──────────────────────────────────────────┐
│ 长期记忆 = 外部存储，跨会话持久化           │
│ · 向量库：语义检索"相似的过往经验"         │
│ · 文件/文档：工作笔记、用户档案            │
│ · 数据库：事实型记录、业务数据             │
└──────────────────────────────────────────┘

分层意义：窗口放"当前任务的 working set"，长期存储放"所有历史"，靠检索在两者之间搬运。基本实现：写入端沉淀值得记的内容，读取端按任务检索片段拼进上下文。

落地提示：先想清楚"什么值得记、记到哪、谁来删"，比选哪个向量库更重要；记忆也意味着合规责任。
06/26

安全：Agent 特有的攻击面

你可能的疑惑传统应用安全做得很多了，Agent 有什么新风险？

Agent 会"读指令、做决策、动手执行"——恶意内容只要能影响它的判断，就能让它替你犯错。

攻击面 1：提示注入（Prompt Injection）
  恶意指令藏在用户输入 / 网页 / 文档 / 邮件里
  ┌─────────┐  读取  ┌───────────────────┐
  │ 恶意网页 │ ─────► │ Agent 把隐藏指令    │
  │"忽略之前指令…"│    │ 当成任务执行       │
  └─────────┘        └───────────────────┘

攻击面 2：越权执行
  Agent 拿着过大的权限，一个误判 = 一次生产事故
  （能删库的工具，就别怪它真删）

攻击面 3：数据泄露
  敏感数据被读进上下文 → 随工具调用 / 外部 API 传出去
落地提示：把 Agent 当成"一个会被骗、但手很快的新员工"来设计权限，而不是当成一段确定性的代码。
07/26

安全：四道防线（纵深防御）

你可能的疑惑攻击面防不完，从哪几件事做起？

纵深防御——任何单点被突破，还有下一道。

防线做什么防什么
最小权限每个工具只授予完成任务必需的最小权限（只读优先，写操作收窄到具体对象）越权执行
沙箱隔离代码执行、文件操作放在隔离环境（容器 / 受限目录），与生产环境隔开注入后的破坏扩散
工具白名单只能调用登记过的工具与参数范围，未登记一律拒绝注入诱导的任意调用
执行前确认高危 / 不可逆操作（删、改、发、付）必须经确认后才执行一切"手快"事故

兜底原则：敏感数据不传出——进上下文的敏感字段脱敏，出 Agent 的调用做内容检查。

落地提示：四道防线中"执行前确认"成本最低、收益最大，第一天就该有。
08/26

治理：让 Agent 合规可控

你可能的疑惑安全和治理听起来都像"管 Agent"，分工是什么？

安全管"防住"（不让坏事发生），治理管"管住"（发生的事可回查、可审批、可算账）。

治理四件事内容
审计日志谁触发、调了什么工具、输入输出、结果如何——全量留痕可回查
审批流高危操作需人批准，分级审批、与工单系统打通
合规要求数据处理符合监管与内部制度（GDPR 类法规一句话：涉及个人数据即受约束）
成本治理token 用量监控、消费上限、异常告警
维度安全治理
目标防住：阻止坏事发生管住：发生的事可控可溯
视角攻击者视角管理者视角
手段沙箱、白名单、最小权限审计、审批、配额
失效后果被注入、越权、泄露说不清、算不清、停不下
落地提示：审计日志是治理的地基——没有留痕，审批、合规、成本全是空中楼阁。
09/26

观测：每一步都看得见

你可能的疑惑Agent 说"任务失败了"，怎么知道它卡在哪一步？

把 ReAct 循环的每一步都落成 trace：调了哪个工具、输入什么、输出什么、花了多少 token。

一次任务执行 = 一条 Trace
┌────────────────────────────────────────────────┐
│ Step 1  思考:需要先查订单  → 工具: query_order    │
│         输入:{order_id} 输出:{...}  12ms  320tok │
│ Step 2  思考:需要退款审批  → 工具: request_appr   │
│         输入:{...}  输出:{待审批}   8ms   210tok  │
│ Step 3  思考:等待人工确认  → 状态: PAUSED         │
└────────────────────────────────────────────────┘
        三条监控线：Trace(步骤) · 日志(事件) · 成本(token/费用)

观测三件套：Trace 看"过程"、日志看"事件"、成本监控看"账单"。

落地提示：观测是"评测"的数据来源——没有 trace 积累，评测集和回放用例都无从谈起。
10/26

评测：没有评测就谈不上上线

你可能的疑惑改了 prompt 或换了模型，怎么证明 Agent 变好了而不是变坏了？

靠持续评测：基准测试定水平，回放用例防回归，用指标说话。

┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 建评测集  │ → │ 基准测试  │ → │ 回放用例  │ → │ 指标看板  │
│ 真实任务+ │   │ 新版本跑一 │   │ 历史trace │   │ 任务完成率│
│ 期望结果  │   │ 遍,比基线  │   │ 重放防回归│   │ 错误率/成本│
└──────────┘   └──────────┘   └──────────┘   └──────────┘
      ▲                                            │
      └────────── 不达标 → 改 prompt/模型 → 重新评测 ──┘

核心指标：任务完成率、错误率（幻觉 / 误调用）、平均步数、单任务成本。没有评测，"迭代"就是掷骰子；有评测，每次改动才敢上线。

落地提示：评测集不必大，从 20~50 个真实高频任务开始，比追求覆盖面更重要。

为什么需要协议：接一次，处处可用

你可能的疑惑工具对接写点适配代码不就行了，为什么要"协议"？

N 个 Agent × M 个工具 = N×M 套专用代码；标准化后变成 N+M——接一次，处处可用。

没有协议：N×M 灾难                  有了协议：N+M
┌─────┐ ╲  ┌────┐                ┌─────┐   ┌────────┐   ┌────┐
│Agent1│ ╲ ╲│工具A│               │Agent1│──┐│        │┌──│工具A│
│Agent2│──╲─│工具B│               │Agent2│──┤│ 标准协议 │├──│工具B│
│Agent3│─╲ ╲│工具C│               │Agent3│──┘│        │└──│工具C│
└─────┘  ╲ ╲└────┘                └─────┘   └────────┘   └────┘
 每对组合一套专用代码                各自只实现一次标准接口
落地提示：MCP / Skills / A2A 不是新概念发明，是工程量倒逼出来的标准。

四层协议全景：各管一层，互不重叠

你可能的疑惑MCP、Skills、A2A、Function Calling 满天飞，它们谁管哪层？

从"模型怎么调工具"到"Agent 怎么够 Agent"，一层一个标准。

┌──────────────────────────────────────────────┐
│ 互连层  A2A（Agent2Agent）                     │
│         Agent 之间互相发现、通信、协作          │
├──────────────────────────────────────────────┤
│ 流程层  Agent Skills                           │
│         把"怎么完成一类任务"打包成可复用技能     │
├──────────────────────────────────────────────┤
│ 工具层  MCP（Model Context Protocol）          │
│         Agent 与外部工具/数据源的统一接入协议    │
│         类比："工具的 USB 接口"                 │
├──────────────────────────────────────────────┤
│ 模型层  Function Calling / Tool Use            │
│         各家 API 原生的"模型请求调工具"机制     │
└──────────────────────────────────────────────┘
          越往下越靠近模型，越往上越靠近生态
落地提示：一句话——Function Calling 是机制，MCP 标准化"够工具"，Skills 封装"怎么干"，A2A 解决"够 Agent"。
13/26

四层协议对比

你可能的疑惑四层分别标准化了什么"东西"？

模型层标准化调用格式，工具层标准化工具接入，流程层标准化任务做法，互连层标准化Agent 间协作。

层协议标准化的对象谁提出 / 推动一句话定位
模型层Function Calling / Tool Use模型请求调工具的格式各家模型厂商原生"模型想调工具"的原生机制
工具层MCPAgent ↔ 工具 / 数据源的接入Anthropic 提出并开源，主要厂商跟进工具的 USB 接口
流程层Agent Skills完成一类任务的步骤 + 提示词 + 脚本Anthropic 等推动的开放标准把"怎么干"打包复用
互连层A2AAgent ↔ Agent 的发现与通信Google 提出Agent 够 Agent

注：各协议归属与进展变化快，一律以官方 / 标准组织最新公告为准。

落地提示：四层是互补不是竞争——一个成熟系统通常会同时用到其中三层以上。
14/26

MCP 来龙去脉：为什么是它

你可能的疑惑工具接入方案那么多，为什么行业共识落在 MCP 上？

它踩中了三个点：开放开源、厂商中立，且恰好出现在 Agent 爆发、所有人都被 N×M 问题折磨的时间窗口。

Function Calling（单点工具调用）
      │  各家格式不一，接工具要写专用代码
      ▼
MCP（工具接入标准化）
      │  Anthropic 提出并开源 → OpenAI / Google / Microsoft
      │  等主要厂商相继采纳 → 进入标准化托管
      ▼
Skills（流程封装）→ A2A（Agent 互联）
      一层层从"一个工具"走向"整个生态"

（具体归属与最新进展以官方 / Linux 基金会消息为准）
落地提示：MCP 基本结构与可运行演示详见第 3 讲第 8 章；本讲记住结论——它是当前工具接入的事实标准方向，投入适配不亏。
15/26

MCP 基本结构：Server + Client

你可能的疑惑接入 MCP，系统里到底多了哪些角色？

两个角色一种语言——Server 提供能力，Client（Agent 侧）消费能力，之间用 JSON-RPC 通信。

┌──────────────────┐          ┌──────────────────┐
│   MCP Client     │          │   MCP Server A   │
│   （Agent 侧）   │─JSON-RPC─►│ 工具/资源/提示词  │
│                  │          └──────────────────┘
│  · 发现可用工具    │          ┌──────────────────┐
│  · 发起调用       │─JSON-RPC─►│   MCP Server B   │
│  · 结果进上下文   │          │ 另一个工具/数据源  │
└──────────────────┘          └──────────────────┘
 Server 提供三类能力：
 · 工具(Tools)：可执行的动作   · 资源(Resources)：可读的数据
 · 提示词(Prompts)：预置的交互模板
落地提示：接新工具优先找现成 MCP Server；自己封装时工具粒度宁细勿粗——描述写得越清楚，Agent 调得越准。
16/26

Agent Skills：封装"怎么干一件事"

你可能的疑惑工具都能调了，为什么还需要"技能包"？

MCP 回答"能调什么工具"，Skills 回答"这件事怎么干"——步骤、提示词、配套脚本打包，Agent 按任务加载。

一个 Skill = 一个带元数据的目录
┌───────────────────────────┐
│ 元数据：名称/说明/触发条件  │← Agent 据此判断何时用
│ 步骤文档：完成任务的流程指引 │← 告诉 Agent 怎么干
│ 配套脚本：确定性环节直接执行 │← 能写死的别让模型猜
└───────────────────────────┘
维度MCPAgent Skills
封装对象工具与数据流程与方法
形态在线服务，C/S 通信目录+文档+脚本，按需加载
复用粒度单个能力一整类任务
关系互补：Skill 的步骤里可以调 MCP 工具
落地提示：团队里"老师傅的经验"最适合沉淀成 Skill——流程写进文档、确定性环节写成脚本，模型只处理真正需要判断的部分。
17/26

A2A 与多 Agent 协作

你可能的疑惑公司有客服 Agent、财务 Agent、IT Agent，它们怎么互相派活？

靠 A2A——Agent 之间互相发现、发任务、交换结果。与 MCP 的区别一句话：MCP 是"Agent 够工具"，A2A 是"Agent 够 Agent"。

┌──────────┐  发现/委派任务  ┌──────────┐
│ 客服 Agent │────A2A─────►│ 财务 Agent │
│(团队A/厂商X)│◄───返回结果───│(团队B/厂商Y)│
└──────────┘              └──────────┘
 跨团队、跨厂商协作，
 不必共享内部实现
其他标准一句话定位
OpenAPI传统 API 描述规范，工具接口的"老路子"
AGNTCYCisco 主导的 Agent 互操作协议，与 A2A 并存竞争
OAuthAgent 代表用户访问资源时的授权依据

A2A 已进入标准托管流程，具体以官方为准；本份不对比协议优劣，只讲清定位与关系。

落地提示：多 Agent 协作前先想清"任务边界和结果契约"——协议解决通信，解决不了职责划分不清。

落地评估权威框架：Gartner AI 成熟度模型

你可能的疑惑公司该从哪开始搞 Agent？凭感觉上，还是有个章法？

用业界公认的 Gartner AI 成熟度模型给自己"量体温"——Gartner 是独立第三方分析师机构，该模型是全球企业 IT 规划的行业标准参考，不绑定任何厂商生态。

      Gartner AI 成熟度模型 = 5 个级别 × 7 个支柱
┌───────────────────────────────────────┐
│ 7 个评估支柱（每支柱按 1~5 级分别评估）： │
│  1 AI战略与愿景    2 数据基础           │
│  3 治理与合规      4 技术架构与平台      │
│  5 人才与技能      6 业务流程整合        │
│  7 文化与组织                           │
├───────────────────────────────────────┤
│ 5 个成熟度级别：                         │
│  L1 认知 → L2 活跃 → L3 运营 → L4 系统化 → L5 变革 │
└───────────────────────────────────────┘
  每个组织得到一张"7 支柱 × 级别"的体检单
落地提示：不要只问"我们在第几级"，要按支柱分别问——数据基础在 L2、战略喊到 L4，是最常见的错位。

五级别阶梯：每一级都是下一级的地基

你可能的疑惑五个级别各自长什么样？

从"零散实验"到"AI 即业务"，逐级演进。

                                          ┌──── L5 变革 ────┐
                                          │ AI 深植企业 DNA  │
                                ┌──── L4 系统化 ────┐         │
                                │ AI 驱动多数工作流   │         │
                      ┌── L3 运营 ──┐                 │         │
                      │ AI 进特定流程 │                 │         │
            ┌─ L2 活跃 ─┐           │                 │         │
            │ 孤岛式试点 │           │                 │         │

五级别详解：特征 · 状态 · 晋级动作

你可能的疑惑每级的"典型状态"和"晋级动作"是什么？
级别一句话特征典型状态晋级动作
L1 认知认识到潜力但无正式战略实验零散、依赖个别热情员工、无数据治理基础建立高层共识，选定 1~2 个候选场景
L2 活跃孤岛式试点爱好者驱动、缺乏统一战略与共享治理收编试点经验，立统一战略与最小治理
L3 运营AI 整合进特定业务工作流有明确用例与初步标准，数据实践开始规范化扩展用例面，补齐平台与可观测性
L4 系统化AI 驱动多数工作流催生新数字化业务模式，AI 是运营根基而非工具流程级重设计，组织与人才体系化
L5 变革AI 深植企业 DNA持续驱动创新、新商业模式与文化转型持续进化，保持组织敏捷
落地提示：自评时找"最拖后腿的支柱"定级别，而不是找"做得最好的"——木桶效应在成熟度上格外灵验。

七支柱快照：1 / 3 / 5 级三档

你可能的疑惑七个支柱各自从 L1 到 L5 是怎么演进的？

抓住 1 / 3 / 5 级三档快照，中间状态自行内插。

支柱L1 快照L3 快照L5 快照
AI 战略与愿景无战略，零散想法有用例路线图，高层支持AI 即业务战略核心，投资持续
数据基础数据散乱不可用重点场景数据规范化数据资产化，质量与治理体系化
治理与合规无护栏初步标准与审批全生命周期治理，护栏自动化

怎么用 + 风险警示 + 切入点

你可能的疑惑评完级之后呢？从哪些场景切入最稳？

使用四步

  1. 按支柱对组织现状打分
  2. 定位当前级别（可按部门分别评）
  3. 找到与"下一个级别"的差距
  4. 制定针对性投资

⚠ 跳级是失败主因

跳过治理直接上自动化 = 同时踩中所有跳过的级别的坑。Gartner 警示：相当比例（约 40%）的 agentic AI 项目可能因治理 / 观测 / ROI 不清晰而被终止（数据以 Gartner 原文为准）。

五个典型切入点为什么适合先切
智能客服与工单高频、流程标准、效果易量化
财务对账与报表规则明确、数据现成、人力消耗大
知识管理与 RAG 研究数据已沉淀、试错成本低
IT 告警分诊高频重复、有历史工单可训练评测
编码 Agent工具链成熟、团队接受度高

筛选原则：高频 + 数据已有 + 流程标准。

落地提示：第一个场景的成功标准是"跑通全流程 + 建立评测"，而不是"做得多惊艳"。
