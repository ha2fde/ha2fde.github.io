44第三章 · 机制
第 1 节 · 它在搜答案吗

我问它问题，它是不是像搜索引擎一样去查答案？

不是。默认形态下，它不连数据库、不搜索，没有任何"答案库"。

你以为的问题 → 搜索 → 找到答案 → 念给你听从已有内容里“找”
≠
实际上的问题 → 预测下一个词 → 再下一个 → …按概率“编”一段从未存在过的文本
模型只做一件事给定上文，计算“下一个 token 最可能是什么”

要点

  1. 生成 vs 检索是本质区别：搜索引擎从索引里找已存在的网页；模型按概率现场编一段新文本
  2. 每个词都是"现编"的，所以答案每次可能不同，也可能编出看似合理但不存在的内容
  3. 后面所有章节（会变、胡说、记不住）都是这一点的推论
主干代码 · 伪代码# 模型的全部工作（伪代码）
while not 结束:
    next_token = model.预测下一个(text)  # 只出一个
    text += next_token                   # 接回去再猜

45第三章 · 机制
第 1 节 · 它在搜答案吗

token 是单词吗？为什么它说话是一个词一个词往外蹦？

token 不是单词，是文本被切分后的最小单位——可能是一个字、一个词、半个词或一个标点。

输入“今天天气”
→
切分 tokenizer[今天] [天气]
→
模型下一个 token 的概率分布真 .30　很 .25　不 .15　晴 .10 …
采样选中「真」[今天] [天气] [真]
循环把新 token 接回输入，再预测下一个，直到结束

要点

  1. 模型词表固定（几万~十几万个 token），每次输出 = 从词表里选 1 个
  2. "ChatGPT" 可能被切成 Chat + G + PT 多个 token；中文常按字/词混合切
  3. 网页上"打字机"效果的根源：本来就是逐 token 生成，不是特效
主干代码 · 加载模型看续写from transformers import AutoTokenizer, AutoModelForCausalLM
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
ids = tok("今天天气真", return_tensors="pt")      # 半句话
out = model.generate(**ids, max_new_tokens=20)    # 看它怎么接
print(tok.decode(out[0]))

第 2 节 · 它凭什么会回答

我一问它就会答，是它天生就会聊天吗？

不是天生的，是"训"出来的。训练分三步，每一步解决一个问题。

系列衔接 ｜ 训练方法的历史脉络（embedding → Transformer → 预训练），详见第二章《从计算机到 GPT》
海量互联网文本几万亿 token
↓第 1 步 · 预训练：反复练习「接下一个词」
基础模型 base会续写，不会对话
↓第 2 步 · 监督微调 SFT：几万~几百万条「问 → 好回答」，学会问答格式
SFT 模型会回答，未必讨喜
↓第 3 步 · 偏好对齐：人类偏好数据「回答 A 比 B 好」，学会有用 / 礼貌 / 守规矩
对话模型 chat你日常用的就是它

要点

  1. 预训练：在海量文本上练"接话"，语言能力和世界知识都在这一步灌进去
  2. SFT（监督微调）：用"问题→好回答"样本，教它把接话能力组织成"回答"
  3. 偏好对齐：让人类标注哪个回答更好，教它什么回答更讨喜、更安全
主干代码 · 概念伪代码# 三步训练（概念伪代码）
base = pretrain(语料, 目标="预测下一个token")
sft  = finetune(base, 数据="问题->好回答")
chat = align(sft, 数据="人类偏好排序")

47第三章 · 机制
第 2 节 · 它凭什么会回答

开源模型为什么总分 base 版和 chat/instruct 版？

这正对应训练三步——base 只做了第 1 步，chat 多做后两步。

同一个输入“怎么煮咖啡？”
base 模型 · 只预训练“怎么煮咖啡？咖啡的种类有很多，煮咖啡的方法因地区而异，常见的有手冲、意式……”它在「续写这段话」，不像在回答
vs
chat 模型 · 预训练 + SFT + 对齐“1. 准备咖啡豆并磨粉　2. 按 1:15 的比例加入热水　3. 90–95 度水温冲泡约 2 分钟”它在「回答这个问题」

要点

  1. base 模型眼里没有问题/回答之分，给它问题，它可能续写出更多问题
  2. chat/instruct = base + SFT + 对齐，才听得懂"指令"和"提问"
  3. 选型经验：聊天、做 Agent 选 instruct/chat 版；灌领域语料继续训练可从 base 起步
主干代码 · 同题对比base = load("Qwen/Qwen2.5-0.5B")            # 只会续写
chat = load("Qwen/Qwen2.5-0.5B-Instruct")   # 会问答
print(base.generate(q))   # 续写出一堆"类似文本"
print(chat.generate(q))   # 给出结构化的回答

48第三章 · 机制
第 2 节 · 它凭什么会回答

训练时，模型不会把"提问"也一起学进去吗？

不会。SFT 的样本是整段对话，但 loss 只在 assistant 的回答上计算——模型看到全部，只被教"怎么回答"。

SFT 训练样本 = 一段渲染好的对话文本
<|im_start|>system 你是助手 <|im_end|>
← 看到，但不学（被 mask）
<|im_start|>user 法国的首都是什么？<|im_end|>
← 看到，但不学（被 mask）
<|im_start|>assistant 巴黎。<|im_end|>
← 只在这里算 loss
机制prompt 部分的 label 置为 -100（框架的 ignore_index），这些 token 不参与损失计算 —— 自然学不到「怎么提问」

要点

  1. 模型看到整段对话，但只在 assistant token 上计算损失、回传梯度
  2. 等于明确告诉模型："别学怎么提问，只学怎么回答"
  3. 这就是指令微调让 Base 学会当助手的核心机关——本页与 QLoRA 页并自第六章工程部分
代码 · labels 掩码
labels = [-100]*len(prompt_ids) + answer_ids # -100 = 不算 loss loss = model(input_ids, labels=labels).loss # 只有回答部分产生梯度

第 3 节 · 它怎么"记得"

它记得我两分钟前说的话，是不是有记忆？

它没有记忆，也不"理解"你。模型本身完全无状态——每次请求都是"第一次见到你"。

messages 消息列表由聊天程序维护，不在模型里
  • system“你是简洁的助手”
  • user“我叫小明”
  • assistant“你好，小明”
  • user“我叫什么名字？”
↓(1) 整个列表渲染成一整段文本
模型看到的只有这段纯文本它并不知道「列表」的存在
↓(2) 生成回复「你叫小明。」　(3) messages.append(assistant: …) 追加回列表
循环下一轮再把更新后的整个列表重新塞给模型 —— 所谓「记忆」就是这么来的

要点

  1. "记得"的真相：那句话出现在了这次的输入文本里，仅此而已
  2. 对话由三种角色组成：system（设定）、user（你）、assistant（它）
  3. 关掉窗口重开 = 历史列表没了 = 它"失忆"——因为从来就没存在过记忆
主干代码 · 消息列表messages = [
  {"role": "system",    "content": "你是简洁的助手"},
  {"role": "user",      "content": "我叫小明"},
  {"role": "assistant", "content": "你好，小明"},
]

51第三章 · 机制
第 3 节 · 它怎么"记得"

消息列表怎么变成模型认得的输入？聊太久会怎样？

程序把消息列表按聊天模板渲染成纯文本；窗口装不下时，丢最老的，系统设定永不丢。

渲染messages → [聊天模板] → 模型实际看到的一整段文本
<|im_start|>system 你是简洁的助手<|im_end|><|im_start|>user 我叫小明<|im_end|> ...
上下文窗口有限（如 4K / 32K token），聊太久装不下
system永不丢u1a1u2a2u3a3u4a4u5 新
截断从最老的 u1 / a1 开始丢，剩下的重新拼成一段塞给模型

要点

  1. 聊天模板：每个模型有自己的格式约定（角色标记、分隔符），渲染错了效果会明显变差
  2. 上下文窗口：模型一次能看的文本有硬上限，窗口大小是模型的重要指标
  3. 截断策略：优先丢最老的历史（所以会"忘记"开头），system 设定永远保留
主干代码 · 组装上下文text = tok.apply_chat_template(messages, tokenize=False)
while len(tok(text).input_ids) > MAX_LEN:
    history.pop(0)   # 丢最老的一条; system 单独保留
    text = tok.apply_chat_template([sys] + history, tokenize=False)

第 3 节 · 它怎么"记得"

messages 里的 role 字段，模型真的看得到吗？

看不到。模型根本没有"角色"字段——apply_chat_template 把消息列表翻译成一段带特殊标记的连续文本，"角色"只是训练时学出来的文本模式。

程序里维护的 messages[ {"role":"system", "content":"你是助手"}, {"role":"user", "content":"法国的首都是什么?"}, {"role":"assistant", "content":"巴黎。"}]
→

apply_chat_template()对模型来说这就是一段普通文本，「角色」是训练时学会的文字规律

  1. apply_chat_template() 就是 SFT 时手工拼字符串的自动化——左右两边完全等价
  2. "角色"不是模型内置概念，是训练数据里反复出现的文本模式

53第三章 · 机制
第 4 节 · 答案为何每次不同

同一个问题隔一分钟再问，答案怎么变了？

模型不是"算出唯一答案"，而是按概率抽样——每次都在掷一个加权骰子。

模型为下一个 token 给出概率分布
的 .50是 .20很 .10真 .05…长尾…
temperature
T → 0：分布变尖，最大者通吃，几乎总选「的」（稳定保守）；T = 0.9：分布拉平，小概率词也有出头之日（发散多样）
top_p = 0.9
截断，只保留累计概率前 90% 的候选池：{的, 是, 很}
随机采样
在候选池里抽 —— 本轮吐出「很」
max_new_tokens
控制这个循环最多再走多少步

要点

  1. temperature：低 → 稳定保守（要事实、要格式时调低）；高 → 发散多样（要创意时调高）
  2. top_p：只在累计概率前 p 的候选池里抽，砍掉长尾烂词，多样但不离谱
  3. max_new_tokens：生成长度上限，防止无限生成，也控制成本
主干代码 · 一行 generatemodel.generate(**ids, max_new_tokens=50,
               do_sample=True, temperature=0.9, top_p=0.9)

第 5 节 · 一本正经地胡说

为什么加一句"请逐步思考"，它数学题就对了？

直接答 = 一步跳到结论，没机会"打草稿"；思维链 CoT 让它把中间步骤写出来。

直接回答Q：3 人 4 天摘了 72kg 苹果，平均每人每天摘多少？一步跳到结论：“每人每天摘 24 kg”　✗结论前生成的 token 太少，等于心算，一步错就全错
→
先思考再回答（CoT）Q：同上 +「请逐步思考」先把草稿写出来：“4 天共 72kg → 3 人 1 天摘 18kg → 每人每天 18/3 = 6kg”，再下结论：“6 kg”　✓中间步骤留在上下文里，后续生成有「稿纸」可依赖

要点

  1. 思维链 CoT：让模型先输出推理过程，再输出结论——复杂推理显著变好
  2. 原理：生成的每一步都成为上下文的一部分，后面的 token 可以"看着草稿算"
  3. 实践口诀：数学题、逻辑题、多步推理，加一句"请一步一步思考"
主干代码 · 两种提示对比q = "3个人4天摘了72千克苹果，平均每人每天摘多少？"
a1 = ask(f"{q}\n直接给出答案。")              # 容易错
a2 = ask(f"{q}\n请一步一步思考，再给出答案。")  # 明显变好

  3. 分工哲学：模型负责决策，程序负责执行——精确的事交给精确的工具

MCP、CLI、Skills，到底各是什么？

三者不是竞争关系，是三个不同层次的东西——协议、工具形态、流程封装。

MCP · 工具接入标准「工具界的 USB 接口」服务器对外暴露工具列表，AI 应用按协议发现和调用，接一次处处可用
CLI · 最朴素的工具「命令本身就是工具」任何命令行命令 / 脚本本身就是工具，AI 像人一样敲命令，零封装成本
Skills · 流程封装「可加载的操作手册」把「怎么做某类任务」的步骤、提示词、配套脚本打包，遇到对应任务按需加载执行

要点

  1. MCP（Model Context Protocol）：开放协议，让任何工具/数据源以统一方式接入任何 AI 应用
  2. CLI：命令行是 AI 最趁手的工具——有文档、可组合、返回纯文本
  3. Skills（技能包）：封装的是"流程"而不是"命令"，比单个工具高一层复用

这三者怎么配合？

分层协作——Skills 在流程层，MCP 在接入层，CLI/API 在执行层。

Skills流程层：「报销 / 发布 / 写周报」这类任务怎么做按任务触发加载
MCP接入层：统一的工具发现与调用协议工具服务器 A / B / C
CLI / API执行层：命令行、脚本、HTTP 接口一个个具体工具
自上而下：流程里会用到协议，协议之下才是真正干活的一个个具体工具

  2. 工具写成 MCP server：一次开发，所有支持 MCP 的 AI 应用直接可用
  3. 流程沉淀为 Skill：把"专家怎么做这件事"固化下来，比模型临时发挥稳定得多

  3. 自己用本地小模型搭兼容服务，现有客户端代码直接能用

def chat(req: ChatRequest):
    def stream():
        for tok in model.stream(req.messages):
            yield f"data: {json.dumps(chunk(tok))}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
