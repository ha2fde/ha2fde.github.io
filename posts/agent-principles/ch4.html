先看清这一章的结构：三组，不是一串

下面要讲六样东西。把它们排成一串会读错——它们不在同一个层次上，解决的也不是同一个问题。分成三组来看：
第一组 · 同一族的三样
tools　·　MCP　·　CLI

都在回答同一个问题：模型怎么让一台机器替它做事。

差别在于那份约定写在哪儿、由谁维护、怎么传过来。讲完三样之后要抽共通点。
第二组 · 抽象层
ACI（Agent–Computer Interface）

它是从上面那三样里抽出来的概念：接口是写给概率模型看的，不是写给编译器看的、也不是写给人看的。

它不是这一章的总纲——第三组那两样不归它管。
第三组 · 各换了一个维度
Skills：管的是该怎么做，不是能做什么。它不给你新能力，它给做法。

A2A：对端不是一台机器，是另一个 agent。

这两样不要硬塞进 ACI 的框子里，塞进去就理解错了。
这一章的深度标准，先说在前面
五样具体机制（tools / MCP / CLI / Skills / A2A）都要讲到同样的深度——你要能徒手画出它的角色关系和一次完整往返、能看懂它的真实配置或报文、能说出它什么时候不该用。不允许有哪一样是含糊过去的。ACI 是抽象层，不适用这个要求。

tools：一份工具定义长什么样

工具定义是随请求发过去的，三个部分：
{ "name": "get_weather", "description": "查询某个城市的当前天气。 city 用中文城市名，不要带「市」字。 查不到会返回 not_found。", "input_schema": { "type": "object", "properties": { "city": { "type": "string", "description": "城市名，如「杭州」" }, "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] } }, "required": ["city"] } }
name模型用来指明「我要调哪个」的标识
description写给模型看的说明。它是模型判断「什么时候该用这个」的唯一依据
input_schema参数的结构约定，用 JSON Schema 表达：有哪些字段、什么类型、哪些必填、枚举值是什么
这里面藏着这一章的第一个要点
schema 约束的是形状，description 约束的是用法。

schema 能保证 city 是个字符串，但保证不了它是个合理的城市名；能保证 unit 只能取两个值之一，但保证不了模型知道该取哪个。

剩下那部分，全靠 description 那段自然语言。
所以有一句话要记住
description 就是接口文档，而且是唯一的那份。模型看不到你的代码、注释和内部约定，它只看得到这一段。

一次完整往返：真实报文

① 宿主程序（客户端）发请求，带上工具定义和用户消息
{ "model": "...", "tools": [ { "name": "get_weather", ... } ], "messages": [ {"role": "user", "content": "杭州今天多少度"} ] }
② 模型返回——注意它没有执行任何东西
{ "stop_reason": "tool_use", "content": [ {"type": "text", "text": "我查一下杭州的天气。"}, { "type": "tool_use", "id": "toolu_01A...", "name": "get_weather", "input": {"city": "杭州", "unit": "celsius"} } ] }
③ 宿主执行完，把结果作为一条新消息发回去
"messages": [ {"role": "user", "content": "杭州今天多少度"}, {"role": "assistant", "content": [ ...上面那段... ]}, {"role": "user", "content": [ { "type": "tool_result", "tool_use_id": "toolu_01A...", "content": "28°C，多云" } ]} ]
三个必须看清的细节
· stop_reason 明确告诉宿主这轮不是在说话，是在请求调用——不用猜、不用解析文本
· tool_use_id 是配对用的。模型可以一次发起多个调用，结果回来时靠这个 id 对上号
· 结果是拼进消息历史再整体重发的。所谓「多轮」，仍然是每次把全部历史发一遍——一次工具往返，账单上是两次完整的历史重发

description 怎么写：正反对照

写坏的
"description": "查询订单"
模型无从判断的问题：
· 查的是哪个系统的订单？
· 参数该传订单号还是用户 ID？
· 查不到时会返回什么，是空还是报错？
· 历史订单和进行中的订单都能查吗？

结果：模型要么不敢用它，要么乱传参数试一次，失败后再试一次——每一次试错都是一整轮往返的钱和时间。
写对的
"description": "按订单号查询订单详情，覆盖近 24 个月的 订单。order_id 是 18 位数字字符串，用户 说的『订单号』通常就是它。 查不到返回 {\"error\": \"not_found\"}， 此时应当询问用户确认订单号，不要重试。 本工具只读，不修改任何数据。"
多写了四类信息：
· 边界——覆盖多长时间、只读还是会改数据
· 参数怎么来——用户话里的哪个东西对应它
· 失败长什么样，以及失败之后该干嘛
· 不该做什么——「不要重试」这种反向指令非常有效
一条能直接用的判断标准
把 description 单独拿出来给一个没见过你系统的人看，他能不能只凭这段话正确调用这个工具？不能，模型也不能。

反过来说：Agent 表现不好时，先去看工具的 description，再去怀疑模型。这里的投入产出比通常是最高的。

tools 的边界：工具变多之后，和什么时候不该用

工具一多就出问题
全部工具定义每一轮都要重发。几十个工具就是好几 K 的固定开销，而且：

· 选择变难——功能相近的工具一多，模型选错的概率显著上升
· 挤占上下文——本该留给资料和历史的预算被工具定义吃掉

常见对策：按场景分组只加载当前需要的一批；或者做一个「检索工具的工具」，先让模型说要干什么，再按需把相关工具定义放进去。
还有一个控制项
接口上通常可以指定本轮允不允许调工具、必须调工具、还是必须调某一个。这在你已经知道下一步该干什么时很有用——不要什么都交给模型决定：能由代码确定的事，就别多花一轮让它猜。
tools 什么时候不该用
  • 你自己就知道该调什么的时候。固定流程里的固定步骤，直接写代码调，别绕一圈让模型来决定——那是白花一轮往返的钱，还多一份不确定。
  • 动作不可逆且没有确认环节的时候。模型给出的是概率性的意图，参数写错的可能永远不为零。删除、转账、发布这类动作，中间必须有宿主的确认或人工审批。
  • 工具数量已经失控的时候。几十上百个工具全塞进去，模型的选择准确率会掉得很难看。这时候要重新想工具该怎么切分，而不是继续加。
  • 返回内容极大的时候。一个返回几万行日志的工具，会一次性把上下文冲垮。要么在宿主侧先过滤、分页、摘要，要么把结果落盘只回一个引用。

MCP 要解决的问题：N × M

tools 解决了「模型怎么表达调用意图」，但没解决「这些工具是怎么来的」。每个客户端要接每个外部系统，都得各自写一遍适配。
MCP 是什么
模型上下文协议（Model Context Protocol）。它规定了一套标准化的接口，让「提供工具和数据的一方」和「使用它们的一方」之间只需要遵守同一份约定。底层用的是 JSON-RPC 2.0——一个已经存在很久的通用远程调用格式，不是新发明的报文体系。
它和 tools 的关系，必须先说清
MCP 不是 tools 的替代品。MCP 服务器提供的工具，最终仍然要被客户端拍平成一个普通的 tools 数组，随请求发给模型。模型根本不知道 MCP 的存在——它看到的和上一节那个 get_weather 没有任何区别。MCP 解决的是工具怎么被接进来，不是工具怎么被调用。这两层不要混。

四个角色，一张图分清

误解一：Agent 就是 Client
不是。Agent 是跑循环的那个，Client 是宿主里专门维护一条 MCP 连接的那个组件。一个 Agent 背后可以挂好几个 Client。
误解二：Server 就是原始服务
不是。Server 是一层适配：它把某个已有系统包装成 MCP 的形状。文件系统 Server 不是文件系统，它是文件系统前面那层壳。
误解三：Server 一定在远端
不一定。大量 Server 就是本机上的一个子进程，通过标准输入输出通信，根本不走网络。「Server」在这里指的是角色，不是部署位置。

一次完整往返：从配置文件到报文

① 你写的配置：告诉客户端去哪儿把 Server 拉起来
{ "mcpServers": { "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/docs"] } } }
② 客户端问 Server 有哪些工具
{"jsonrpc":"2.0","id":1,"method":"tools/list"}
③ Server 回工具清单，结构和 tools 一样
{"jsonrpc":"2.0","id":1,"result":{ "tools":[{ "name":"read_file", "description":"读取指定路径的文件内容", "inputSchema":{"type":"object", "properties":{"path":{"type":"string"}}, "required":["path"]}}]}}
④ 客户端把这批工具拍平进发给模型的 tools 数组，模型选中后返回调用意图。客户端把它翻译成一次 MCP 调用
{"jsonrpc":"2.0","id":2,"method":"tools/call", "params":{ "name":"read_file", "arguments":{"path":"/Users/me/docs/a.md"} }}
⑤ Server 去读文件，把结果按 MCP 格式回来
{"jsonrpc":"2.0","id":2,"result":{ "content":[{"type":"text","text":"文件内容……"}], "isError":false }}
⑥ 最后一步，回到上一节
客户端把这段结果包成一条普通的 tool_result 消息，拼进上下文再发给模型。

整条链上，模型只见过 tools 这一种形态。MCP 全程发生在客户端和 Server 之间。
协议原文与官方服务器实现见 modelcontextprotocol.io/specification（核对日期 2026-08）

MCP 的三种基本件，按「谁决定」分层

MCP 提供的不止工具。这三种基本件（官方文档里叫 primitives / 原语）的真正区别不在于内容，而在于谁来决定它什么时候被用——这是理解 MCP 设计的关键。
Tools　→ 模型决定
可执行的动作。放进上下文后，由模型自己判断什么时候调、调哪个。

这是唯一会主动改变外部状态的一类，因此也是权限设计的重点对象。

tools/list　tools/call
Resources　→ 应用决定
可读取的数据，比如一个文件、一条数据库记录、一份日志。

模型不能自己去取——由宿主决定把哪些资源放进上下文。

它是「给模型看的材料」，不是「给模型用的动作」。

resources/list　resources/read
Prompts　→ 用户决定
预置好的提示词模板，通常暴露成用户可以主动选的一个命令或菜单项。

由用户触发，模型和应用都不会自己去用它。

prompts/list　prompts/get
为什么这个分层重要
因为它把「控制权在谁手上」写进了协议本身，而不是留给每个实现自己约定。

实践中最常见的错误是把本该是 Resources 的东西做成了 Tools——于是模型开始自作主张地到处翻数据，上下文被无关内容塞满，行为也变得难以预测。

判断标准：这件事该不该由模型自己决定要不要做？不该，就别做成 Tool。
两种传输方式
· 标准输入输出：Server 作为宿主的子进程跑在本机，通过管道通信。不走网络，天然只有本机能访问，是本地工具最常见的形态。
· HTTP：Server 是一个远端服务，走网络，需要处理鉴权、多租户、连接保持等一整套问题。

协议规范一直在修订，传输层与会话模型是变动最多的部分——接入前先看当前版本的规范。

MCP 的边界：它省了什么，又贵在哪儿

MCP 值不值得上，取决于你到底在哪一侧。它省的是「对接」的成本，不是「调用」的成本——如果你只有一个应用要接一个服务，那点对接成本本来就很低，MCP 换来的只有额外的进程和额外的故障面。
这些场景，接 MCP 是划算的
  • 同一份能力要给多个宿主用。公司内部的知识库、工单系统、部署平台，接一次，所有 Agent 产品都能用——这是 N × M 里那个 M 真实存在的情况。
  • 要用别人已经写好的 Server。数据库、浏览器、云平台，社区已有现成实现，接一个配置就能用，自己重写没有意义。
  • 能力的提供方和使用方不是同一批人。平台团队维护 Server，业务团队接就行，两边靠协议对接，各自发版互不影响。
  • 希望用户自己能装。Server 是可分发的单元，用户改一个配置文件就能给自己的 Agent 加能力，不需要你改代码重新发版。
    • 这些场景，别为了用而用
  • 只有你自己的一个应用要用。直接在宿主里写成 tools 更短、更快、更好调试。多套一层协议只是把一个函数调用变成了跨进程通信。
  • 这个动作要严格门禁。Server 是一层外部依赖，权限校验、审计、限流都得你自己在 Server 里补齐，不会因为用了 MCP 就自动有。
  • 对延迟敏感。多一次跨进程或跨网络往返，在高频调用的路径上会被放大。
  • 为了「显得规范」。协议不产生能力，它只是让能力更好分发。没有分发需求，它就是纯成本。
    • 一句话判断
    能力要跨宿主复用，就上 MCP；只服务一个宿主，就写成 tools。这条线和「哪个技术更先进」无关，只和你有几个使用方有关。

    还有一件事要一起记住：装一个别人写的 Server，等于在你的机器上跑别人的代码，而且它自报的工具说明会原样进入模型的上下文。来源不明的 Server，和来源不明的第三方依赖是同一类东西。

    CLI：最老、也最暴力的一种接口

    前面两样都是先定义、再调用：你把每个动作写成一份 schema，模型在这份清单里挑。CLI 走的是完全相反的路——不定义任何具体动作，直接把一个命令行交给模型。
    它的工具定义短得离谱
    // 一个 bash 工具，全部定义就这些 { "name": "bash", "description": "在一个持久的 shell 会话里执行命令", "input_schema": { "type": "object", "properties": { "command": {"type": "string"} }, "required": ["command"] } }
    一个字符串参数，没有枚举，没有取值范围，没有任何结构。schema 在这里几乎什么都没约束住。
    那约定写在哪儿？
    写在模型自己脑子里。

    git status 是什么意思、grep -rn 怎么用、退出码 0 表示成功——这些没有一条写在工具定义里，全都来自模型的预训练知识。

    换句话说：接口文档就是几十年积累下来的 Unix 惯例，它早就在训练数据里了。

    这也解释了为什么 CLI 这条路一上来就能用：它不需要你教，只需要你允许。
    交出去的不是一个工具，是一整个工具箱
    一旦给了 bash，模型能用的就不止一条命令：文件读写、进程管理、网络请求、版本控制、包管理、以及机器上装的每一个程序。你写一条工具定义，换来的是整个操作系统。

    CLI 强在哪儿：三条别的方案给不了的东西

    ① 可组合
    管道、重定向、循环，让模型可以一次调用完成多步工作，中间结果不必回到上下文里过一遍。
    # 一次调用，四步 grep -rl TODO src/ \ | xargs wc -l \ | sort -rn \ | head -5
    同样的事情用专用工具做，是四次往返、四段回执、四轮 token。
    ② 自带发现机制
    模型不确定用法时，可以自己去问——不需要你把文档预先塞进上下文。
    rg --help man tar some-tool --version
    这是 tools 和 MCP 都没有的：那两样的接口说明必须提前全量注入，用不用得上都占着上下文。CLI 是按需取用。
    ③ 覆盖面无上限
    机器上装了什么，模型就能用什么。新增能力不需要改 Agent 的任何代码——装个包就行。
    这一条在编程类任务上尤其关键：编译、测试、格式化、依赖管理、版本控制，本来就全部以命令行的形式存在，没有任何一样需要重新包装。
    共同的根源
    这三条都来自同一件事：命令行是几十年来为「人以外的调用者」优化过的接口——它本来就是给脚本用的，纯文本进、纯文本出、行为可预测。模型只是又一个脚本作者。

    CLI 的代价：四条，每一条都很实在

    ① 不可门禁
    工具定义只说了「执行一条命令」。你无法在参数层面判断这条命令要做什么——同一个 bash 调用，可能是查文件，也可能是删目录。

    做关键词黑名单挡不住：命令有无数种等价写法，变量拼接、编码、换个工具都能绕过去。

    要么信任整个 shell，要么别给。中间态很难做对。
    ② 难审计
    tools 的调用记录是结构化的：工具名、参数、结果，天然可以统计、告警、回放。

    CLI 的记录只有一串命令文本。「这个 Agent 今天访问了哪些数据」这类问题，从日志里答不出来。
    ③ 错误面大
    专用工具的失败模式是有限的几种，可以逐个写好提示。

    shell 的失败模式无穷：命令不存在、权限不足、路径不对、参数格式变了、环境变量缺失、交互式程序卡住等着输入。

    其中「卡住等输入」最麻烦——它不报错，只是永远不返回。
    ④ 输出吃 token
    命令行的输出是给人看的，不是给上下文优化的。一个 npm install 能刷几百行进度，一次 cat 大文件能直接把上下文占满。

    专用工具可以在返回前裁剪、分页、只挑要紧字段；bash 的回执是原样返回的，除非你在宿主侧另外做截断。
    注意这四条的共同点
    它们全都是「schema 没约束住」的直接后果。CLI 的强和 CLI 的险是同一件事的两面：约定不在接口里，所以既没有上限，也没有护栏。

    什么时候把一条命令升级成专用工具

    这不是二选一。真实的做法通常是底下留着 bash，把少数几件事拎出来做成工具。判断标准就四条，命中任意一条就该拎出来。
    触发条件为什么 bash 做不了拎出来之后变成什么
    要门禁参数是自由文本，无法在调用前判断这次操作的范围和影响。一个参数受限的工具：路径只能在指定目录下、操作只能是枚举里的那几种，越界在宿主侧直接拒绝。
    要渲染回执是纯文本。用户在界面上看到的只能是一段命令输出。工具返回结构化结果，宿主拿去画表格、画差异、画进度——模型看到的和用户看到的可以不是同一份东西。
    要审计日志里只有命令文本，事后统计和告警都做不了。每次调用都是一条结构化记录：谁、什么时候、动了哪个对象、结果如何。
    要并发shell 会话是有状态的：当前目录、环境变量、正在跑的进程。多个任务共用一个会话会互相干扰。无状态的工具调用，参数自带全部上下文，可以安全地并行发起。
    典型的分工
    编程类 Agent 几乎都是这个形态：文件读写、内容检索做成了专用工具（要渲染差异、要限制路径、要能并行），其余一切交给 bash（编译、测试、包管理、版本控制）。
    反过来的错误
    给每条常用命令都包一个工具，包出几十个只是转发字符串的壳。它们既没带来门禁也没带来结构，只是把工具清单撑大、把上下文占满、让模型更难选对。没命中上面四条，就别包。

    三样对齐着看：差别只在一处

    tools、MCP、CLI 到这里都讲完了。把它们放进同一张表，会发现绝大多数格子是一样的——真正不同的只有一行。
    toolsMCPCLI
    谁定义能力宿主程序的开发者Server 的开发者（可以是别人）没人专门定义，机器上装了什么就是什么
    怎么传到模型面前请求里的 tools 数组Client 取回后，拍平进同一个 tools 数组就一条 bash 工具，也在这个数组里
    模型看到什么完全一样：一份工具清单——名字、说明、参数形状
    谁执行完全一样：宿主程序。模型只发起，从不执行
    结果怎么回去完全一样：一段文本，作为下一轮的输入
    约定写在哪儿写在 schema 和 description 里，随请求一起发过去同上，只是这份说明来自另一个进程写在模型的预训练知识里，请求里几乎没有
    读出来的结论
    三样东西不是三种技术，是同一种技术的三种约定分发方式：写在请求里（tools）、由另一个进程供给（MCP）、早就在模型脑子里（CLI）。
    所以「该用 tools 还是 MCP」这个问题问错了方向——真正该问的是：这份约定该由谁维护、要发给几个使用方。

    抽象层：接口是写给一个概率模型看的

    既然三样东西在结构上是同一件事，那就值得给这件事一个名字：Agent 与外部世界之间的那层接口。它既不是 API，也不是 UI——因为读它的既不是编译器，也不是人。
    读者是谁读错了会怎样因此设计时优化的是
    API另一段程序不会读错。类型不匹配在编译期或运行期直接报错，行为是确定的。严谨、不重不漏、性能。字段名短一点无所谓，反正调用方是照文档固定写好的。
    UI人人会犹豫、会点错，但人能看懂上下文，能从界面布局、图标、颜色里补全没写出来的信息。直观、可发现、可撤销。信息可以放在视觉层面，不必全写成文字。
    ACI一个概率模型会读错，而且是概率性地读错。同一份接口，十次里可能有九次用对、一次用错，且错法不固定。
    它看不到颜色和布局，只能看到你写下的那些字。    		让「用对」的概率尽可能高。所以：名字要能望文生义，说明要写清什么时候用，错误信息要能指导下一步。
    这个视角改变的是什么
    工具用不好，第一反应往往是「模型不行」。但换成这个视角，问题会变成：这份接口，一个只读到这些字的读者，有多大把握用对？
    ——大多数时候，答案是接口写得不够，而不是模型能力不够。而接口是你能改的。

    由这一条推出来的六个设计习惯

    下面每一条都不是凭经验总结的偏好，而是「读者是概率模型」这一条的直接后果——括号里是它对应的推理。
    ① 名字要能望文生义
    × exec_op　√ search_orders_by_email

    （模型是靠字面语义选工具的，名字本身就是最强的一条提示。）
    ② 按任务切，不按接口切
    按用户想完成的一件事切，不要按后端接口切。三个必须按顺序调的工具，不如一个工具。

    （每多一次调用，就多一次选错的机会；顺序约束只存在于说明里，模型不一定遵守。）
    ③ 错误信息就是提示词
    × Error: invalid input
    √ date 必须是 YYYY-MM-DD，你传的是「上周五」。今天是 2026-08-06。

    （回执会原样进上下文，成为模型下一步的依据——它是你影响下一步的最直接手段。）
    ④ 尽量做成可重试的
    同样的参数调两次，结果应该一样；写入类操作最好带上一个由调用方给的标识，重复提交能被识别。

    （模型会重试——超时、看不懂回执、或者单纯忘了自己调过。这是常态，不是异常。）
    ⑤ 给回执定预算
    返回前就截断、分页、只留要紧字段，并在结尾写清「共 N 条，此处显示前 20 条」。

    （上下文是有限资源，而且塞得越满，模型的判断质量越差——这一点在长任务里尤其明显。）
    ⑥ 让它能自己查
    提供一个能列出可选值、看示例、试运行的入口，而不是把所有可能性罗列在说明里。

    （说明是常驻上下文的，写得越全越占位置；能查的东西按需取用，只在需要时才花 token。）
    怎么验证一份接口写得好不好
    把工具定义原样贴给模型，问它「这个工具是干什么的、什么时候该用、给我三个调用例子」。它答偏了，就是接口写得不够——这个检查一分钟就能做完，比事后从失败日志里倒推快得多。

    Skills 换了一个维度：管的是「该怎么做」

    前面三样解决的都是同一个问题：让模型能做某件事。但真实工作里，「能做」之后往往还差一大截——它做得了，只是没按你们的规矩做。
    工具解决的问题：能不能做
    「读文件」「查数据库」「发请求」——没有工具，这些事根本发生不了。

    工具的说明写的是接口：参数是什么形状、返回什么、有什么限制。
    Skills 解决的问题：怎么做才算对
    「写周报要用这个模板、这几个字段必填、口径按财务的定义」——这些事没有工具也能做，只是做出来不对。

    Skills 写的是流程与规范：先做什么、按什么格式、有哪些禁忌、遇到什么情况怎么处理。
    为什么不干脆全写进系统提示词
    因为规范会越堆越多。十几套流程全写进系统提示词，结果是每一次对话都要为所有流程付 token，而其中绝大多数这次根本用不上；同时它们还会互相干扰，模型可能把 A 流程的规矩用到 B 任务上。
    Skills 的核心机制就是解决这个：让规范平时不占地方，用到的时候才读进来。
    形式上它极其朴素
    一个 Skill 就是一个文件夹：里面有一份 Markdown 说明文件，可以再带上模板、示例、脚本等附件。没有编译，没有注册中心，没有专门的运行时——它就是给模型看的一份文档，外加它可能用得上的几个文件。

    它长什么样，以及关键的一层机制

    一份说明文件的开头，是一段元信息，再接正文：
    --- name: weekly-report description: 生成部门周报。当用户要求写周报、 周会材料，或提到「本周进展」时使用。 --- # 部门周报写法 ## 取数 1. 从工单系统拉本周关闭的工单 2. 口径以「关闭时间」为准，不是创建时间 3. 跨部门协作的工单只算主责方 ## 格式 按 `templates/weekly.md` 的结构写， 四个板块顺序不能调整……
    分层加载：只有一句话是常驻的
    第一层　平时只有 name 和 description 在上下文里。几十个字，十几个 Skill 加起来也只是很小一段。

    第二层　模型判断这次用得上，才把正文读进来。正文可以写得很长很细，因为它不用的时候不占任何位置。

    第三层　正文里提到的模板、示例、脚本，再按需读取。可以放得很大——几十页的规范文档、几百行的脚本，都不影响平时的开销。
    于是 description 成了唯一被「看见」的字段
    模型决定要不要读正文，依据只有这一句话。所以它必须写触发条件（什么情况下该用），而不是写自我介绍（这个技能有多厉害）。

    × 一个强大的报告生成工具
    √ 当用户要求写周报、周会材料，或提到「本周进展」时使用

    写一个 Skill：四条要点

    ① description 写触发条件
    上一页已经说了原因，这里补一句实操：把你能想到的用户说法都列进去。「周报 / 周会材料 / 本周进展 / 这周做了啥」——它是靠字面匹配上下文的，说法覆盖得越全，该触发时越不会漏。
    ② 正文写流程，不写背景
    模型缺的不是「为什么要写周报」，是「按什么口径、什么顺序、什么格式」。

    删掉所有铺垫，直接写步骤、写规则、写反例。正文是操作手册，不是介绍文档。
    ③ 长的东西放附件
    完整模板、长示例、参考数据放成单独文件，正文里只写「按 templates/weekly.md 的结构写」。

    这样正文保持短、好读，大块内容只在真要用时才读进来。
    ④ 确定性的步骤写成脚本
    格式转换、数据清洗、字段校验这类每次都一样、且容错要求高的步骤，写成脚本让模型去执行，比让它每次现写更稳。

    判断标准：这一步允不允许每次结果略有不同？不允许，就别交给模型现做。
    一个容易被忽略的前提
    Skills 要能读文件、执行脚本，底下必须已经有对应的工具——文件读取、命令执行。
    它不是工具的替代品，是叠在工具之上的一层。先有能力，再谈规范。

    什么时候用它，什么时候别用

    适合做成 Skill 的四类
  • 组织内部的规范。代码风格、文档模板、命名约定、评审清单——写下来一次，所有人的 Agent 都照着做。
  • 有固定产出格式的活。报告、合同、配置文件、数据报表，格式错了就算内容对也不能用。
  • 步骤多且顺序要紧的流程。发布流程、事故处理、数据迁移，漏一步或者顺序错了后果都不小。
  • 某个工具的正确用法。工具本身的 description 篇幅有限，复杂用法、常见坑、组合技可以单独写一份。
    • 不该用的三种情况
  • 只有一两条规则。直接写进系统提示词更省事，多一层文件只是多一层间接。
  • 规则改得很频繁。每周都要改的东西放成文件，很容易改了这份忘了那份，最后没人知道哪份是准的。
  • 其实缺的是工具。「它查不到数据」不是规范问题，写一百页 Skill 也没用——该加的是工具。
    • 安全上必须说清的一件事
    一个 Skill 里可以带脚本，而这些脚本是要在你的机器上执行的。所以装一个别人写的 Skill，和装一个第三方依赖是同一件事——来源不明就别装，装之前先把文件看一遍，尤其是脚本部分。
    它形式上只是几个文本文件，这一点很容易让人放松警惕。

    A2A：对面不再是工具，是另一个 Agent

    前面所有内容都有一个共同假设：对面是确定的。函数会返回、命令会退出、Server 会应答，行为可预期。A2A 换掉的正是这个假设——对面也是一个模型驱动的东西。
    调用一个工具委派给一个 Agent
    对面是什么一段确定的程序另一个 Agent，自己会规划、会用工具、会犯错
    你交出去的一组参数一个目标——怎么达成由对方自己决定
    什么时候返回毫秒到秒级，同步等着就行可能几分钟、几小时，中途还可能回来问你要信息
    结果是什么一个确定的返回值一份产出，可能是文件、报告、也可能是一段说明为什么做不了
    能不能重试通常可以，结果一致重试结果可能不同，且中间可能已经产生了副作用
    为什么这值得单独一套协议
    因为上面五行里，没有一行能靠「再定义一个工具」解决。
    一个可能跑几小时、中途要追问、状态会变化、结果不确定的调用，用「发请求—等返回」这个模型根本装不下——它需要的是任务的概念，不是调用的概念。

    四个概念，和一份自我介绍

    发起方
    需要把一件事委派出去的那个 Agent。它要先找到合适的对象，再把目标交出去。
    受托方
    接下这件事的远端 Agent。它怎么做、用什么工具，发起方完全不知道也不需要知道。
    能力名片
    受托方公开的一份自我介绍：我是谁、能做什么、怎么找到我、要什么凭证。发起方靠它做判断。
    任务
    这次委派的载体。它有自己的标识和状态，可以被查询、被取消，可以跨越很长时间存在。
    名片放在一个约定好的位置
    通常是域名下的一个固定路径，比如 /.well-known/agent-card.json。知道域名就能拿到名片，不需要事先注册或者互相配置——这一点和网站的图标、证书用的是同一个思路。
    名片大致是这个样子（字段以当前规范为准）：
    { "name": "Invoice Auditor", "description": "审核发票合规性并出具结论", "url": "https://acme.example/a2a", "version": "1.2.0", "capabilities": { "streaming": true, "pushNotifications": true }, "skills": [{ "id": "audit-invoice", "name": "发票合规审核", "description": "检查金额、税率、抬头、 附件是否齐全，返回问题清单", "tags": ["finance", "compliance"] }], "securitySchemes": { /* 鉴权方式 */ } }
    注意最后一项：跨组织调用，凭证怎么给是必须在名片里说清楚的事。

    任务的一生：为什么它必须有状态

    因为委派的结果不是「返回值」，而是一个会随时间变化的对象。发起方需要能查它、能催它、能撤它——所以任务被定义成了一个有明确状态的东西。
    「等待补充信息」是关键的一态
    工具调用里没有对应物：被调用方反过来向调用方提问。这只在对面也是 Agent 时才会发生，也是整套协议里最能说明「这不是 RPC」的地方。
    长任务怎么等
    两种办法：保持连接持续接收进度，或者留一个回调地址，对方状态变了主动通知。前者适合几分钟，后者适合几小时以上——毕竟没人能挂着连接等一晚上。
    产出不只是一段文本
    任务可以带回结构化的产出：文件、表格、图片、结构化数据。这也是「任务」和「消息」的区别——消息是对话，任务是交付物。

    A2A 的现实：什么时候它是对的，什么时候不是

    这是本章里离日常最远的一样。它解决的问题真实存在，但要成立需要几个前提，而这些前提今天多数团队还没凑齐。
    它真正对上的场景
  • 跨组织。你要用的能力在另一家公司手里，对方不可能把内部工具和数据开给你——但可以对外接一个任务。
  • 跨团队且各自独立演进。受托方换了模型、改了流程，发起方完全不受影响，因为契约只是「能做什么」。
  • 确实需要对方自己判断。如果这件事能写成确定的步骤，那它本来就该是个工具，不该是个 Agent。
    • 这些情况别用
  • 都在你自己的系统里。直接函数调用或者内部服务调用，快得多也好查得多。跨进程的协议是为了跨边界，不是为了分层。
  • 任务能确定地描述。那就是工具，用工具。
  • 对结果要求确定。一个 Agent 委派给另一个 Agent，不确定性是相乘的：两边各有一成出错概率，整体就接近两成。
  • 还没把单个 Agent 跑稳。先让一个 Agent 在生产里可靠跑起来，再谈让它们互相调用。
    • 诚实的现状判断
    跨组织的 Agent 协作，卡住的从来不是协议格式，而是信任、计费、责任归属和审计——「对方的 Agent 把事情办砸了算谁的」，这不是一份 JSON 能回答的问题。
    所以这一节的价值不在于让你今天就接上，而在于让你知道这个方向的问题被定义成了什么形状：能力名片、任务状态、跨域鉴权——等你真的需要时，你知道该找什么。
    相关规范与生态仍在快速变化，接入前请以官方规范的当前版本为准。

    五样东西放进同一张坐标系

    开头说过：这不是一串并列的技术。现在可以把那句话补完——它们分布在两个维度上：横轴是「接的是谁」，纵轴是「约定写在哪里」。
    接的是谁约定写在哪里解决的问题什么时候选它
    tools本进程内的代码请求里的 schema 与说明让模型能做事能力只服务你这一个宿主
    MCP另一个进程同上，但由那个进程供给让能力可以跨宿主分发同一份能力要给多个使用方
    CLI整个操作系统模型的预训练知识里用最低成本换最大覆盖面要广度、不要门禁的场景
    Skills——（不接新东西）按需读入的文档与附件让已有能力按规矩用能做但做得不对的时候
    A2A另一个 Agent能力名片 + 任务状态让不确定的委派可管理跨组织、且对方必须自己判断
    前三样是同一族
    tools、MCP、CLI 在模型眼里是同一样东西：一份工具清单。它们只是把接口说明放在了不同的地方。选哪个，取决于这份说明由谁维护、要发给几个人。
    Skills 叠在它们之上
    它不新增任何能力，只约束已有能力的用法。所以它永远是第二步——先确认工具够了，再用它解决「做得不对」。顺序反了，写多少规范都没用。
    A2A 在另一个坐标上
    前四样的对面都是确定的；只有它的对面也是一个会自己规划、会犯错的东西。这个差别大到必须有任务状态、跨域鉴权这一整套机制——它不是「更高级的 MCP」。

  • MCP：它解决的 N × M 问题、四个角色分别是谁、从配置文件到报文的完整流程、三种基本件按「谁决定」的分层、以及什么场景纯属浪费。
  • CLI：为什么它几乎不需要接口定义、强在哪三条、代价是哪四条、什么时候该把一条命令升级成专用工具。
  • 抽象层：这三样在结构上是同一件事，差别只在「约定写在哪儿」；以及由「读者是概率模型」推出的六个设计习惯。
  • Skills：它管的是「该怎么做」、分层加载机制、编写的四条要点、以及把它当第三方依赖看待的理由。
  • A2A：为什么委派给 Agent 装不进「调用」这个模型、四个概念与能力名片、任务状态的一生、以及为什么它今天还离你很远。
